LAMP-stack & Nextcloud

In het vorige hoofdstuk serveerde je statische HTML met Apache. Nu bouw je daar bovenop een volwaardige solution stack: Linux + Apache + MariaDB + PHP. Als concrete toepassing installeer je Nextcloud — een open-source cloudplatform dat alle vier de lagen tegelijk gebruikt. Tot slot kraak je examen-oefeningen en optioneel een paar diepere "Op verkenning"-uitdagingen.

📋 Scenario

Je server (10.10.10.1, webserverXX.pxl.lan) draait al met DHCP, DNS en Apache uit de vorige hoofdstukken. Een collega vraagt of jullie een eigen cloud-omgeving kunnen draaien voor de afdeling — bestanden delen, agenda, video-calls — zonder afhankelijk te zijn van Google Drive of OneDrive. Je kiest voor Nextcloud, dat een complete LAMP-stack nodig heeft. Aan het eind kan je vanaf clientXX in de browser inloggen op http://webserverXX.pxl.lan en met meerdere accounts werken. Vervang overal XX door je eigen servernummer.

Deel 1 — Apache klaarmaken voor Nextcloud
Apache Taak 01
Nextcloud downloaden en uitpakken
▶

Anders dan een gewone website plaatsen we Nextcloud niet in /var/www/html, maar in een eigen submap /var/www/nextcloud. Dat is een conventie van Nextcloud zelf en houdt je standaard html-map vrij voor andere sites.

# httpd zou al draaien uit het vorige hoofdstuk — controleer: sudo systemctl status httpd # laat httpd door de firewall (zone "internal" voor 10.10.10.0/24) sudo firewall-cmd --add-service=http --zone=internal --permanent sudo firewall-cmd --reload cd /var/www # download de laatste stable van nextcloud.com sudo wget https://download.nextcloud.com/server/releases/latest.tar.bz2 # uitpakken (let op: -j = bzip2, niet -z = gzip) sudo tar -xjvf latest.tar.bz2 ls -d nextcloud cd ~
💡 Waarom .tar.bz2? Tar bundelt een hele directorystructuur tot één bestand; bzip2 (vlag -j) comprimeert het. Voor .tar.gz gebruik je -z. Vergeet je de juiste vlag, dan krijg je een cryptische foutmelding over het magic-byte.
✔ Verificatie ls /var/www/nextcloud/ toont onder andere de mappen apps/, config/, core/ en het bestand index.php.
Apache Taak 02
Een VirtualHost voor Nextcloud schrijven
▶

Omdat Nextcloud niet in de standaard DocumentRoot staat, moet Apache weten waar hij moet kijken. Maak een eigen configbestand in /etc/httpd/conf.d/ — alles in die map wordt automatisch ingelezen.

sudo nano /etc/httpd/conf.d/nextcloud.conf
<VirtualHost *:80> DocumentRoot /var/www/nextcloud ServerName webserverXX.pxl.lan <Directory /var/www/nextcloud/> Require all granted AllowOverride All Options FollowSymLinks MultiViews </Directory> </VirtualHost>
# altijd eerst syntax checken vóór je apache herlaadt sudo httpd -t sudo systemctl reload httpd
💡 Wat doet elke directive?
  • DocumentRoot — waar de website-bestanden staan.
  • ServerName — welke hostname matcht met deze vhost (de Host:-header van de browser).
  • Require all granted — iedereen mag de site bekijken (geen IP-restrictie).
  • AllowOverride All — Nextcloud mag z'n eigen .htaccess-bestanden gebruiken (URL-rewrites, beveiliging, …). Zonder dit werkt Nextcloud niet correct.
  • FollowSymLinks — Apache mag symlinks volgen (Nextcloud gebruikt die intern).
  • MultiViews — Apache mag raden welk bestand je bedoelt als de extensie ontbreekt (b.v. /about → about.php).
✔ Verificatie httpd -t antwoordt Syntax OK. Surf je nu naar http://webserverXX.pxl.lan, dan krijg je waarschijnlijk een 403 Forbidden of een PHP-fout — dat is normaal, we hebben nog geen PHP en SELinux blokkeert nog. Eerst de database.
Deel 2 — MariaDB (de "M")
MariaDB Taak 03
Installeer MariaDB-server (en weet wat er al staat)
▶

RHEL bevat soms al mysql-pakketten. Je kan op een RHEL-gebaseerd systeem niet zowel MySQL als MariaDB tegelijk geïnstalleerd hebben — ze claimen dezelfde bestandsnamen en services. Check eerst, verwijder zo nodig, en installeer MariaDB Server.

# wat is er al? rpm -qa | grep -Ei 'maria|mysql' # is er een mysql-server pakket geïnstalleerd? dan eerst weg: # sudo dnf remove mysql-server -y # installeer mariadb-server (de daemon), niet alleen mariadb (de client) sudo dnf install mariadb-server -y sudo systemctl enable --now mariadb sudo systemctl status mariadb
💡 MariaDB ↔ MySQL MariaDB is een fork van MySQL door de oorspronkelijke ontwikkelaars, gestart toen Oracle MySQL overnam. Het is volledig open-source en (op het commando-niveau) compatibel: het commando heet nog steeds mysql, configfiles staan in /etc/my.cnf.d/, de poort is nog steeds 3306. Voor 99% van de toepassingen is het inwisselbaar.
ℹ Andere DBMS'en: SQLite is wereldwijd het #1 meest geïnstalleerde DBMS (zit in elke Android/iOS-app), MySQL/MariaDB is #2. PostgreSQL is een object-relational alternatief (LAPP-stack), bekend om strengere standaarden en uitgebreidere features dan MySQL.
✔ Verificatie systemctl status mariadb → active (running). ss -tlnp | grep 3306 toont MariaDB luisterend op localhost.
MariaDB Taak 04
Beveilig de installatie met mariadb-secure-installation
▶

Vlak na installatie staat MariaDB open: geen root-wachtwoord, anonieme gebruikers, een test-database, remote root toegestaan. Het script mariadb-secure-installation loopt deze punten één voor één af.

sudo mariadb-secure-installation

De vijf stappen die het script doorloopt:

  1. Current root password → leeg laten (Enter), er is er nog geen.
  2. Switch to unix_socket authentication? → Enter (= ja). Dan logt root in via z'n Linux-account in plaats van een wachtwoord.
  3. Change the root password? → Y, daarna een wachtwoord ingeven (in de les: pxl; in een echte omgeving uiteraard sterker).
  4. Remove anonymous users? → Enter (= ja).
  5. Disallow root login remotely? → Enter (= ja).
  6. Remove test database? → Enter (= ja).
  7. Reload privilege tables? → Enter (= ja). Dit dwingt MariaDB om de nieuwe rechten meteen toe te passen zonder restart.
💡 Waarom FLUSH PRIVILEGES? MariaDB cachet de gebruikers- en rechten-tabellen in het geheugen voor snelheid. Wijzig je iets aan accounts of rechten, dan moet je expliciet de cache verversen — anders zien je sessie de wijziging niet. Het script doet dit voor je aan het eind.
✔ Verificatie Probeer mariadb -u root: dat moet werken via Unix-socket. mariadb -u root -h 127.0.0.1 -p vraagt om je net ingestelde wachtwoord.
MariaDB Taak 05
Maak een database + gebruiker voor Nextcloud
▶

Een applicatie moet nooit als root verbinden met de database. Het golden rule is: één database, één gebruiker met enkel rechten op die database. Als Nextcloud later gehackt wordt, kan de aanvaller alleen de Nextcloud-database aanvallen — niet de rest van je server.

sudo mariadb -u root
MariaDB [(none)]> CREATE DATABASE nextcloud CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci; MariaDB [(none)]> CREATE USER 'ncuser'@'localhost' IDENTIFIED BY 'SterkWachtwoordHier'; MariaDB [(none)]> GRANT ALL PRIVILEGES ON nextcloud.* TO 'ncuser'@'localhost'; MariaDB [(none)]> FLUSH PRIVILEGES; MariaDB [(none)]> EXIT;
💡 Waarom utf8mb4 en niet utf8? In MySQL/MariaDB betekent utf8 historisch gezien maximaal 3 bytes per teken — geen emoji of zeldzame Aziatische tekens. utf8mb4 is "echt" 4-byte UTF-8 en kan alles aan. Nextcloud vraagt dit expliciet; sla je documenten met emoji op zonder utf8mb4, dan krijg je "Incorrect string value"-errors.
💡 Wat is 'ncuser'@'localhost'? MariaDB identificeert een account altijd als gebruiker + host. 'ncuser'@'localhost' mag enkel verbinden vanaf dezelfde machine. Maakte je 'ncuser'@'%', dan mag het account vanaf elk IP komen. Voor Nextcloud op dezelfde server is localhost exact wat je wil — strakker is veiliger.
Hint: SQL-commando's eindigen op ;. Mis je die en druk je Enter, dan komt er een nieuwe regel met -> als prompt en MariaDB blijft wachten. Typ alsnog ; en Enter. Wil je gewoon afbreken? Typ \c. Wil je uit de prompt? EXIT; of \q.
✔ Verificatie mariadb -u ncuser -p → wachtwoord invoeren → de prompt moet veranderen in MariaDB [(none)]>. Doe dan SHOW DATABASES; — je ziet enkel information_schema en nextcloud. Geen mysql systeem-database (want je hebt geen rechten). Perfect.
Deel 3 — PHP (de "P")
PHP Taak 06
Installeer PHP + de modules die Nextcloud nodig heeft
▶

PHP zelf is maar de basis-interpreter. Nextcloud heeft bovendien losse PHP-extensions nodig om foto's te kunnen verwerken (imagick), met MariaDB te praten (mysqlnd), bestanden te uploaden in stukjes, ZIP-bestanden te lezen, enzovoort. Eén ervan — php-imagick — zit niet in de standaard-RHEL-repos en heeft EPEL nodig.

# 1. EPEL = Extra Packages for Enterprise Linux — community-pakketten voor RHEL sudo dnf install epel-release -y # 2. installeer PHP + de Nextcloud-modules in één commando sudo dnf install -y \ php php-cli php-common \ php-mysqlnd php-gd php-mbstring \ php-xml php-zip php-intl \ php-bcmath php-gmp php-imagick # 3. controleer welke versie geïnstalleerd is php -v

Apache laadt PHP via de module mod_php (uit het pakket php). Die module wordt automatisch geactiveerd via /etc/httpd/conf.modules.d/ — maar je moet Apache herstarten zodat hij de module ook echt inlaadt.

sudo systemctl restart httpd
💡 Waar staat PHP's config? Het hoofdbestand is /etc/php.ini. Daar pas je dingen aan als memory_limit, upload_max_filesize, post_max_size — belangrijk voor Nextcloud, want grote uploads worden anders afgekapt. Module-specifieke instellingen staan in /etc/php.d/.
Snelle testpagina: maak even een testbestand:
sudo nano /var/www/nextcloud/info.php
<?php phpinfo(); ?>
Surf naar http://webserverXX.pxl.lan/info.php. Krijg je een grote tabel met PHP-versie en modules → PHP werkt. Verwijder dit bestand daarna meteen — het lekt info aan aanvallers.
✔ Verificatie php -m | grep -Ei 'mysqlnd|gd|imagick|mbstring' moet alle vier de modules tonen. php --version toont PHP 8.x.
Deel 4 — SELinux (de onzichtbare poortwachter)
SELinux Taak 07
Geef Apache de juiste SELinux-rechten op /var/www/nextcloud
▶

SELinux is een extra beveiligingslaag bovenop de gewone Unix-rechten. Het kan een proces (zoals httpd) verbieden om dingen te doen die "niet de bedoeling" zijn — zelfs als de Unix-rechten het zouden toelaten. Standaard mag Apache enkel lezen in /var/www/html. Wij willen dat hij schrijft in /var/www/nextcloud (voor uploads), en het netwerk op kan voor sommige Nextcloud-apps.

De drie SELinux-instellingen die je nodig hebt:

# 1. Apache mag naar buiten verbinden (push-notifications, federated sharing, ...) sudo setsebool -P httpd_can_network_connect on # 2. Apache mag schrijven & lezen in zijn eigen webmappen sudo setsebool -P httpd_unified on # 3. Stel het juiste SELinux-type in op de hele Nextcloud-map # httpd_sys_rw_content_t = "deze map mag httpd lezen EN schrijven" sudo semanage fcontext -a -t httpd_sys_rw_content_t "/var/www/nextcloud(/.*)?" # 4. Pas de regel daadwerkelijk toe op de bestaande bestanden sudo restorecon -Rv /var/www/nextcloud
💡 -P bij setsebool Zonder -P geldt de boolean tot je reboot — daarna is hij weer uit. Met -P (persistent) blijft hij over reboots heen. Vergeet deze vlag niet, anders werkt je server na een reboot plots niet meer en zoek je je dood.
💡 Wat doet semanage fcontext + restorecon precies? semanage fcontext -a -t TYPE "PATH" schrijft een regel in de SELinux-policy: "alle bestanden onder dit pad moeten type X krijgen". Maar bestaande bestanden zijn daarmee nog niet veranderd. restorecon -Rv past die regel toe op de bestanden die er nu staan. De regex (/.*)? betekent "de map zelf én alles eronder, recursief".
Tijdelijke shortcut: in de oefeningen mag je SELinux soms in permissive mode zetten met sudo setenforce 0. Dan logt SELinux nog wél elke overtreding maar blokkeert hij niets. Handig om snel te zien of SELinux je probleem veroorzaakt. Vergeet niet setenforce 1 achteraf — anders heb je de hele beveiliging weggegooid.
✔ Verificatie ls -lZ /var/www/nextcloud | head -3 — de Z-kolom toont nu httpd_sys_rw_content_t op alle bestanden. getsebool httpd_can_network_connect httpd_unified toont beide op on.
Deel 5 — Nextcloud installatie afronden
Nextcloud Taak 08
Eigenaarschap van de webmap goed zetten
▶

Op RHEL draait Apache als gebruiker apache. Voor Nextcloud (uploads, config wegschrijven, app-installs) moet die gebruiker écht eigenaar zijn van alles onder /var/www/nextcloud. Anders krijg je later in de browser-installer een melding dat de map niet schrijfbaar is.

sudo chown -R apache:apache /var/www/nextcloud
💡 Drie lagen rechten, drie verschillende dingen
  • Unix-rechten (chmod/chown) — wie mag wat. Apache moet eigenaar zijn.
  • SELinux-context — welke "rol" heeft het bestand. httpd_sys_rw_content_t = "Apache mag rw".
  • Apache-config (Require, AllowOverride) — wie mag de URL bekijken.
Een file kan met chmod 777 in volle glorie open staan maar nog steeds onbereikbaar zijn omdat SELinux het type verkeerd vindt. Daarom moet je alle drie correct hebben.
✔ Verificatie ls -la /var/www/nextcloud | head — eerste kolommen tonen apache apache als eigenaar/groep.

Nextcloud Test Taak 11
Verbinden vanaf clientXX en trusted_domains aanpassen
▶

Als je nu op clientXX surft naar http://webserverXX.pxl.lan, krijg je waarschijnlijk een melding "Access through untrusted domain". Nextcloud heeft een eigen anti-hijack-mechanisme: enkel hostnames die in config.php als trusted_domains staan, worden geaccepteerd.

sudo nano /var/www/nextcloud/config/config.php

Zoek het stuk 'trusted_domains' => array (...) en breid het uit:

'trusted_domains' => array ( 0 => 'localhost', 1 => '*.pxl.lan', ),

De wildcard *.pxl.lan dekt alle subdomeinen van je lab-zone in één lijn. Sla op, geen Apache-restart nodig (PHP leest config.php elke request).

Ga nu naar clientXX en log in via je browser. Eerste keer doorloop je een korte intro-wizard, daarna ben je binnen.

💡 Waarom geen toegang van buiten? Een NAT-router stuurt verkeer van buiten niet automatisch door naar interne toestellen. Wil je je Nextcloud publiek bereikbaar maken (lab-onafhankelijk), dan moet je op de NAT-router een port forward instellen (extern 80/443 → intern 10.10.10.1) en idealiter ook HTTPS configureren met een echt certificaat. Voor dit labo blijven we intern.
Pas op met de syntax in config.php: dit is gewoon PHP-code. Vergeet je een komma na een entry, dan crasht heel Nextcloud met een wit scherm. Test met sudo php -l /var/www/nextcloud/config/config.php — je moet "No syntax errors" zien.
✔ Verificatie Vanaf clientXX surfen naar http://webserverXX.pxl.lan → je krijgt het Nextcloud-loginscherm, geen waarschuwing. Inloggen met de gewone gebruiker uit Taak 10 → dashboard verschijnt.
Deel 7 — Examenoefeningen (zelf doen)
Exam Taak 12
Oefeningen 1–3: virtual hosting, HTTPS-encryptie, multi-CMS
▶

Oefening 1 — Userdir virtual hosting. Activeer in /etc/httpd/conf.d/userdir.conf de mod_userdir zodat elke Linux-gebruiker automatisch een eigen website krijgt onder ~/public_html/, bereikbaar via http://webserverXX.pxl.lan/~gebruikersnaam. Maak twee gebruikers aan met je voor- en achternaam, plaats een index.html in elk public_html, en bewijs met screenshots dat beide werken.

Hint:
  • In userdir.conf: zet UserDir disabled in commentaar, en zet UserDir public_html aan.
  • SELinux-boolean nodig: sudo setsebool -P httpd_enable_homedirs on.
  • De home-directory zelf moet chmod 711 (execute voor others), public_html/ moet chmod 755.
  • Restorecon op de home-dir of expliciet chcon -R -t httpd_user_content_t ~/public_html.

1. Activeer mod_userdir. Bewerk de config:

sudo nano /etc/httpd/conf.d/userdir.conf
<IfModule mod_userdir.c> # UserDir disabled ← deze regel in commentaar zetten UserDir public_html # ← deze aanzetten </IfModule> <Directory "/home/*/public_html"> Require all granted </Directory>

2. SELinux toelaten dat Apache in homedirs leest:

sudo setsebool -P httpd_enable_homedirs on

3. Twee gebruikers + hun public_html (vervang door je eigen voor-/achternaam):

sudo useradd voornaam sudo useradd achternaam sudo passwd voornaam sudo passwd achternaam # per gebruiker: map aanmaken, rechten zetten, pagina plaatsen sudo mkdir /home/voornaam/public_html echo "<h1>Site van voornaam</h1>" | sudo tee /home/voornaam/public_html/index.html # Apache moet door de home kunnen wandelen (x), en de site lezen sudo chmod 711 /home/voornaam sudo chmod 755 /home/voornaam/public_html sudo chown -R voornaam:voornaam /home/voornaam/public_html # herhaal exact hetzelfde voor 'achternaam'

4. SELinux-context op de content + reload:

sudo restorecon -Rv /home/voornaam/public_html sudo restorecon -Rv /home/achternaam/public_html sudo httpd -t && sudo systemctl reload httpd

5. Testen (screenshots maken voor beide):

curl http://webserverXX.pxl.lan/~voornaam curl http://webserverXX.pxl.lan/~achternaam

Beide moeten hun eigen index.html tonen. De ~ in de URL is precies wat mod_userdir vertaalt naar /home/<naam>/public_html/.

Oefening 2 — Waarom HTTPS zowel symmetrische als asymmetrische encryptie gebruikt. Leg in eigen woorden uit waarom een TLS-verbinding niet gewoon één van de twee gebruikt. Tip: denk aan snelheid, sleuteldistributie en wat er gebeurt tijdens de handshake.

Asymmetrische encryptie (RSA, ECDSA) is traag — voor elke byte van je website zou je honderden CPU-cycli verbranden. Symmetrische encryptie (AES) is snel, maar heeft het probleem dat beide kanten dezelfde geheime sleutel moeten kennen — en je kan die sleutel onmogelijk over het onveilige internet sturen, want iedereen luistert mee.

HTTPS combineert het beste van beide:

  • Handshake (asymmetrisch, traag, maar veilig): de server stuurt zijn publieke sleutel uit het certificaat. De browser bedenkt een willekeurige symmetrische sessie-sleutel, encrypt die met de publieke sleutel, en stuurt ze terug. Alleen de server kan dit decrypten (hij heeft de private sleutel).
  • Daarna (symmetrisch, snel): beide kanten gebruiken die symmetrische sessie-sleutel om de eigenlijke HTTP-data te encrypten met AES. Veel sneller, en geen onderscheppingsrisico meer want de sleutel is al uitgewisseld.

Kortom: asymmetrisch voor sleuteldistributie, symmetrisch voor bulk-data.

Oefening 3 — Drie CMS'en naast elkaar. Maak een nieuwe landing-page in /var/www/html/index.html met links naar drie CMS'en — elk in een eigen subdirectory:

  • /drupal/ → Drupal
  • /joomla/ → Joomla 6
  • /wordpress/ → WordPress NL-BE
Tijdens deze oefening: SELinux in permissive (setenforce 0) en firewall uit (systemctl stop firewalld) volgens de cursus, om eerst CMS-installatie aan de praat te krijgen zonder afleiding. Zet beide achteraf terug aan en los SELinux-problemen op met booleans en fcontexts. Tip om de Joomla-banner weg te krijgen: verwijder media/templates/site/cassiopeia/images/logo.svg.
Werkwijze per CMS:
  1. cd /var/www/html en wget <link>
  2. tar -xzvf <bestand> (gzip) of tar -xjvf voor bzip2
  3. Hernoem de uitgepakte map naar de gewenste naam (mv drupal-X.Y drupal)
  4. chown -R apache:apache op de map
  5. Maak per CMS een aparte database + user in MariaDB (zoals Taak 5)
  6. Loop de webinstaller door op /drupal/, /joomla/, /wordpress/
index.html-skelet:
<!DOCTYPE html> <html><head><title>Mijn CMS-portaal</title></head> <body> <h1>Voornaam Achternaam</h1> <ul> <li><a href="/drupal/">Drupal</a></li> <li><a href="/joomla/">Joomla</a></li> <li><a href="/wordpress/">WordPress</a></li> </ul> </body></html>

1. Landingspagina in /var/www/html/index.html:

<!DOCTYPE html> <html><head><title>CMS-portaal</title></head> <body> <h1>Voornaam Achternaam</h1> <ul> <li><a href="/drupal/">Drupal</a></li> <li><a href="/joomla/">Joomla</a></li> <li><a href="/wordpress/">WordPress</a></li> </ul> </body></html>

2. Per CMS één database + eigen user (in sudo mariadb -u root):

CREATE DATABASE drupal; CREATE USER 'drupal_user'@'localhost' IDENTIFIED BY 'wachtwoord'; GRANT ALL PRIVILEGES ON drupal.* TO 'drupal_user'@'localhost'; -- herhaal identiek voor 'joomla' en 'wordpress' FLUSH PRIVILEGES;

3. Drupal downloaden & uitpakken in een subdirectory:

cd /var/www/html sudo wget https://www.drupal.org/download-latest/tar.gz -O drupal.tar.gz sudo tar -xzvf drupal.tar.gz sudo mv drupal-* drupal sudo chown -R apache:apache drupal

4. Joomla (zelfde patroon):

Oef 4 — MariaDB over SSL. Genereer een self-signed certificaat voor de DB-server, zet require_secure_transport=ON in /etc/my.cnf.d/mariadb-server.cnf, maak een user met REQUIRE SSL, en bewijs dat een onversleutelde verbinding wordt geweigerd terwijl mariadb --ssl-ca=... -u user -p wél werkt.

Stappen kort:
  1. openssl req -x509 -newkey rsa:2048 -nodes -keyout server-key.pem -out server-cert.pem -days 365
  2. Verplaats naar /etc/my.cnf.d/certs/, chown mysql:mysql
  3. In mariadb-server.cnf sectie [mariadb]: ssl-ca, ssl-cert, ssl-key, require_secure_transport=ON
  4. SQL: CREATE USER 'sec'@'localhost' IDENTIFIED BY 'x' REQUIRE SSL;
  5. In de prompt: STATUS; — onderaan zie je nu SSL: Cipher in use is ...

1. Certificaat + key genereren en op hun plaats zetten:

sudo mkdir -p /etc/my.cnf.d/certs cd /etc/my.cnf.d/certs sudo openssl req -x509 -newkey rsa:2048 -nodes \ -keyout server-key.pem -out server-cert.pem -days 365 \ -subj "/CN=webserverXX.pxl.lan" sudo chown -R mysql:mysql /etc/my.cnf.d/certs sudo chmod 600 server-key.pem

2. MariaDB op SSL zetten in /etc/my.cnf.d/mariadb-server.cnf, sectie [mariadb]:

[mariadb] ssl-cert = /etc/my.cnf.d/certs/server-cert.pem ssl-key = /etc/my.cnf.d/certs/server-key.pem ssl-ca = /etc/my.cnf.d/certs/server-cert.pem require_secure_transport = ON
sudo systemctl restart mariadb

3. Gebruiker die SSL verplicht maakt:

CREATE USER 'sec'@'localhost' IDENTIFIED BY 'pxl' REQUIRE SSL; GRANT ALL PRIVILEGES ON nextcloud.* TO 'sec'@'localhost'; FLUSH PRIVILEGES;

4. Bewijs. Zonder SSL wordt geweigerd, met SSL werkt het:

# geweigerd (require_secure_transport=ON blokkeert plain): mariadb -u sec -p --ssl=0 # → ERROR 1045 / "Access denied" of "Secure transport required" # werkt mét certificaat: mariadb -u sec -p --ssl-ca=/etc/my.cnf.d/certs/server-cert.pem # in de prompt: STATUS; # → "SSL: Cipher in use is TLS_AES_256_..."

Oef 5 — Fijnmazige DB-rechten per CMS. Bouw voort op Oef 3. Maak drupal_user, joomla_user, wp_user en geef elk alleen GRANT ALL op zijn eigen database. Log in als drupal_user, doe SHOW DATABASES; — je mag de andere CMS-databases niet eens zien. Probeer daarna SELECT * FROM wp_database.wp_users; → moet falen met Access denied.

De truc zit in GRANT ... ON database.*: door rechten per database te geven, beperk je niet alleen wat een user mag doen, maar ook wat hij mag zien. SHOW DATABASES toont enkel databases waarop je minstens één privilege hebt.

-- elk CMS zijn eigen user, enkel op zijn eigen database: CREATE USER 'drupal_user'@'localhost' IDENTIFIED BY 'pw1'; GRANT ALL PRIVILEGES ON drupal.* TO 'drupal_user'@'localhost'; CREATE USER 'joomla_user'@'localhost' IDENTIFIED BY 'pw2'; GRANT ALL PRIVILEGES ON joomla.* TO 'joomla_user'@'localhost'; CREATE USER 'wp_user'@'localhost' IDENTIFIED BY 'pw3'; GRANT ALL PRIVILEGES ON wordpress.* TO 'wp_user'@'localhost'; FLUSH PRIVILEGES;

Bewijs van isolatie:

mariadb -u drupal_user -p
SHOW DATABASES; -- toont enkel: information_schema, drupal (NIET joomla/wordpress) SELECT * FROM wordpress.wp_users; -- ERROR 1142 (42000): SELECT command denied to user 'drupal_user'@'localhost'

Dit is het principe van least privilege: lekt één CMS, dan blijft de schade beperkt tot één database.

Oef 6 — Caching & performance. Activeer opcache in /etc/php.d/10-opcache.ini, schakel in Apache mod_expires en mod_deflate in (per file-type: ExpiresByType image/jpeg "access plus 1 month", AddOutputFilterByType DEFLATE text/html text/css application/javascript). Meet voor en na met:

ab -n 200 -c 10 http://webserverXX.pxl.lan/ curl -w "@curl-format.txt" -o /dev/null -s http://webserverXX.pxl.lan/

Verwacht: een merkbare daling in Time per request.

1. OpCache (PHP compileert scripts één keer en cachet de bytecode in geheugen) in /etc/php.d/10-opcache.ini:

opcache.enable=1 opcache.memory_consumption=128 opcache.max_accelerated_files=10000 opcache.revalidate_freq=60

2. Apache compressie + caching. Maak /etc/httpd/conf.d/performance.conf:

<IfModule mod_deflate.c> AddOutputFilterByType DEFLATE text/html text/css application/javascript application/json </IfModule> <IfModule mod_expires.c> ExpiresActive On ExpiresByType image/jpeg "access plus 1 month" ExpiresByType text/css "access plus 1 week" ExpiresByType application/javascript "access plus 1 week" </IfModule>
sudo systemctl restart httpd php-fpm 2>/dev/null; sudo systemctl restart httpd

3. Meten. mod_deflate verkleint de transfer (compressie), mod_expires laat browsers cachen (minder requests), OpCache versnelt PHP zelf:

# installeer apache-benchmark indien nodig sudo dnf install httpd-tools -y ab -n 200 -c 10 http://webserverXX.pxl.lan/ # vergelijk "Time per request" en "Transfer rate" voor/na # controleer dat compressie aan staat: curl -H "Accept-Encoding: gzip" -I http://webserverXX.pxl.lan/ # → header "Content-Encoding: gzip" moet verschijnen

Oef 7 — mod_security & mod_evasive. Installeer mod_security (WAF) met de OWASP Core Rule Set, en mod_evasive (anti-DoS). Test een SQL-injectie aanval — bv. surf naar http://webserverXX.pxl.lan/?id=1' OR '1'='1 → moet door mod_security geweigerd worden met 403. Simuleer een DoS met ab -n 1000 -c 100 → mod_evasive moet je IP tijdelijk blokkeren.

1. Installeren (mod_evasive zit in EPEL, dat heb je al uit Taak 6):

sudo dnf install mod_security mod_security_crs mod_evasive -y sudo systemctl restart httpd

2. mod_security staat na installatie standaard al aan in DetectionOnly-modus. Zet hem op blokkeren in /etc/httpd/conf.d/mod_security.conf:

SecRuleEngine On # was: DetectionOnly

De OWASP Core Rule Set (CRS) bevat al kant-en-klare regels tegen SQL-injectie, XSS, enz. — die worden automatisch ingeladen.

3. mod_evasive configureren in /etc/httpd/conf.d/mod_evasive.conf:

<IfModule mod_evasive24.c> DOSPageCount 2 # max hits zelfde pagina / interval DOSSiteCount 50 # max hits hele site / interval DOSPageInterval 1 # interval in seconden DOSBlockingPeriod 10 # hoelang geblokkeerd (sec) </IfModule>
sudo httpd -t && sudo systemctl restart httpd

4. Testen:

# SQL-injectie → mod_security blokkeert met 403 curl -i "http://webserverXX.pxl.lan/?id=1'+OR+'1'='1" # → HTTP/1.1 403 Forbidden # DoS-simulatie → mod_evasive blokkeert je IP tijdelijk ab -n 1000 -c 100 http://webserverXX.pxl.lan/ # → na de drempel: 403's, en regels in /var/log/httpd/error_log
Let op: mod_security kan ook Nextcloud zelf hinderen (false positives). In productie tune je de CRS met exclusion rules voor je app. Voor de oefening volstaat het de blokkering te demonstreren.

Oef 8 — Deploy automatisch met Ansible. Schrijf een playbook lamp.yml dat op een schone RHEL: Apache+MariaDB+PHP+EPEL installeert, de Nextcloud-vhost neerzet, de SELinux-booleans/fcontexts toepast, firewall opent, en optioneel ook Drupal/Joomla/WordPress in subdirs uitpakt met aparte databases. Test op een nieuwe VM met ansible-playbook -i inventory lamp.yml.

Skeleton:
- hosts: webservers become: yes tasks: - name: install LAMP packages dnf: name: [httpd, mariadb-server, php, php-mysqlnd, php-gd, ...] state: present - name: start & enable services systemd: name: "{{ item }}" state: started enabled: yes loop: [httpd, mariadb] - name: SELinux booleans seboolean: name: "{{ item }}" state: yes persistent: yes loop: [httpd_can_network_connect, httpd_unified] - name: firewall firewalld: service: http permanent: yes state: enabled zone: internal notify: reload firewall
Modules om in op te zoeken: community.mysql.mysql_db, community.mysql.mysql_user, ansible.posix.firewalld, ansible.posix.seboolean, ansible.builtin.template voor de vhost-config.

Een werkbaar lamp.yml-playbook. Plaats het op je control-node, met een inventory-bestand dat je webserver bevat onder groep webservers.

--- - hosts: webservers become: yes vars: nc_db: nextcloud nc_user: ncuser nc_pass: "SterkWachtwoordHier" tasks: - name: EPEL repo dnf: name: epel-release state: present - name: LAMP + PHP packages installeren dnf: name: - httpd - mariadb-server - php - php-mysqlnd - php-gd - php-mbstring - php-xml - php-zip - php-intl - php-imagick - python3-PyMySQL # nodig voor de mysql-modules state: present - name: services starten en enablen systemd: name: "{{ item }}" state: started enabled: yes loop: - httpd - mariadb - name: SELinux booleans ansible.posix.seboolean: name: "{{ item }}" state: yes persistent: yes loop: - httpd_can_network_connect - httpd_unified - name: firewall http openzetten ansible.posix.firewalld: service: http permanent: yes immediate: yes state: enabled zone: internal - name: Nextcloud database community.mysql.mysql_db: name: "{{ nc_db }}" encoding: utf8mb4 login_unix_socket: /var/run/mysqld/mysqld.sock - name: Nextcloud db-user community.mysql.mysql_user: name: "{{ nc_user }}" password: "{{ nc_pass }}" priv: "{{ nc_db }}.*:ALL" host: localhost login_unix_socket: /var/run/mysqld/mysqld.sock - name: vhost neerzetten ansible.builtin.template: src: nextcloud.conf.j2 dest: /etc/httpd/conf.d/nextcloud.conf notify: restart httpd handlers: - name: restart httpd systemd: name: httpd state: restarted

Uitvoeren en testen op een schone VM:

# vereiste collections eenmalig installeren ansible-galaxy collection install community.mysql ansible.posix ansible-playbook -i inventory lamp.yml # idempotentie-check: tweede run mag NIETS meer wijzigen (changed=0) ansible-playbook -i inventory lamp.yml

De kracht van Ansible is idempotentie: draai je het playbook twee keer, dan verandert de tweede keer niets (changed=0) omdat alles al in de gewenste staat is. Dat maakt het veilig om herhaaldelijk te draaien.
