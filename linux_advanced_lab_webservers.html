Apache HTTP Server (httpd)

Hands-on labo: Apache installeren op RHEL 10, je eerste website serveren, meerdere sites tegelijk hosten met virtual hosting, de boel beveiligen (bestandsrechten, firewall, wachtwoordbeveiliging), HTTPS opzetten met een zelfondertekend SSL-certificaat, en logs lezen. Sluit af met de examenoefeningen en een troubleshooting-scenario.

📋 Scenario

Je server (10.10.10.1, webserverXX.pxl.lan) draait al met DHCP en je eigen DNS uit de vorige hoofdstukken. Nu zet je er een echte dienst bovenop: een Apache-webserver. Clients in 10.10.10.0/24 moeten via hun browser je website kunnen bekijken op naam. Je host meerdere sites op dezelfde server, beveiligt een deel met login, en zet alles uiteindelijk over HTTPS. Vervang overal XX door je eigen servernummer.

🌐 Wat gebeurt er bij één HTTP-request?

Browser
Stuurt een GET-request naar poort 80 (HTTP) of 443 (HTTPS).
→
Apache (httpd)
Luistert, kiest de juiste VirtualHost o.b.v. Host:-header of poort.
→
DocumentRoot
Zoekt index.html in /var/www/html (of de site-map).
→
Response
Stuurt de pagina terug + een statuscode (200, 403, 404...).
Op poort
Eén IP, meerdere sites onderscheiden via verschillende poorten.
site.com:8080 / site.com:8443
Op hostname (name-based)
Eén IP, meerdere namen. Apache kiest o.b.v. de Host:-header. Meest gebruikt.
site1.lan / site2.lan → zelfde IP
Op IP-adres
Eén site per IP. Nodig wanneer elke site een eigen certificaat/IP vereist.
10.10.10.1 / 10.10.10.2

Deel 1 — Installatie & eerste website
Install Taak 01
Inspecteer het package vóór je installeert
▶

Een goede gewoonte: kijk eerst wát een package meebrengt voordat je het installeert. Download het core-package en stel er vragen aan met rpm.

sudo dnf download httpd-core ls httpd* # -qip = query, info, package-bestand (versie, licentie, beschrijving) rpm -qip httpd-core-*.rpm # -qcp = query, config-files, package: welke .conf-bestanden levert het? rpm -qcp httpd-core-*.rpm
💡 Waarom Apache? Apache (httpd) is open source, draait op vrijwel elke Linux-distributie, en is enorm uitbreidbaar via modules. De grote community en documentatie maken het de standaardkeuze voor traditionele webhosting en CMS'en zoals WordPress. Nginx is sneller bij heel veel gelijktijdige verbindingen; IIS hoort bij de Windows/.NET-wereld. Voor dit labo nemen we Apache.
✔ Verificatie rpm -qip toont o.a. Version : 2.4.x en de URL httpd.apache.org. rpm -qcp toont het hoofd-configbestand /etc/httpd/conf/httpd.conf.
Install Taak 02
Installeer Apache, start en enable de service
▶

De daemon heet httpd — die naam gebruik je overal bij systemctl.

sudo dnf install httpd -y # start nu, en zorg dat hij automatisch start bij boot sudo systemctl start httpd sudo systemctl enable httpd sudo systemctl status httpd
💡 start vs enable start zet de dienst nú aan (tot de volgende reboot). enable koppelt hem aan het opstartproces zodat hij na een reboot vanzelf terugkomt. Je hebt beide nodig: een service die je vergeet te enable-en is na de eerste herstart spoorloos.
✔ Verificatie systemctl status httpd → active (running) én enabled.
Config Taak 03
Zet je eerste pagina in DocumentRoot
▶

Standaard zoekt Apache naar index.html in /var/www/html (de DocumentRoot). Maak die pagina aan.

# Check de twee standaardinstellingen in de hoofdconfig: grep -E "^DocumentRoot|^DirectoryIndex" /etc/httpd/conf/httpd.conf sudo nano /var/www/html/index.html
<!DOCTYPE html> <html> <head><title>Mijn eerste webpagina</title></head> <body><h1>Mijn eerste webpagina</h1></body> </html>
💡 DocumentRoot & DirectoryIndex DocumentRoot = de map waar Apache websitebestanden zoekt. DirectoryIndex = welk bestand hij toont als de URL geen bestandsnaam bevat (dus http://server/ → index.html). Geef je meerdere namen op (index.php index.html), dan pakt hij de eerste die bestaat.
✔ Verificatie Op de server zelf: curl http://localhost toont je HTML. Of surf naar http://127.0.0.1 in de browser. (Externe toegang regelen we in Deel 3.)
Deel 2 — Virtual hosting (meerdere sites)
VHost Taak 04
Twee name-based virtual hosts aanmaken
▶

We hosten twee sites op hetzelfde IP, onderscheiden via hostname. Per site maak je een eigen .conf-bestand in /etc/httpd/conf.d/. Alles in die map wordt automatisch bij de hoofdconfig gevoegd — netjes gescheiden per site.

sudo nano /etc/httpd/conf.d/website1.conf
<VirtualHost *:80> ServerAdmin webmaster@pxl.lan ServerName webserverXX.pxl.lan ServerAlias www.webserverXX.pxl.lan DocumentRoot /var/www/html/website1/ DirectoryIndex index.html </VirtualHost>

Doe hetzelfde voor website2.conf met ServerName webserver2XX.pxl.lan en DocumentRoot /var/www/html/website2/. Maak dan de mappen en een eigen index.html per site (inhoud bv. "website 1" / "website 2"):

sudo mkdir /var/www/html/website1 /var/www/html/website2 sudo nano /var/www/html/website1/index.html sudo nano /var/www/html/website2/index.html # config testen vóór reload — altijd! sudo httpd -t sudo systemctl reload httpd
💡 Hoe kiest Apache welke site? Bij name-based hosting kijkt Apache naar de Host:-header die de browser meestuurt. Surf je naar webserverXX.pxl.lan, dan staat dat in de header en kiest Apache de matchende <VirtualHost>. Zonder match (of bij een rechtstreeks IP) pakt hij de eerste vhost als default. Daarom moet DNS de namen kunnen oplossen (volgende taak).
Let op: de sites zijn nu nog niet extern bereikbaar — de firewall (Deel 3) en bestandsrechten/SELinux moeten nog goed staan. Gebruik tijdens testen een privévenster of Ctrl+F5 tegen browser-cache.
VHost Taak 05
Voeg de hostnames toe aan je DNS-zone
▶

De vhost-namen moeten oplosbaar zijn. Voeg ze toe aan je BIND-zone uit het vorige hoofdstuk en herlaad named.

sudo nano /etc/named/pxl.lan.db
webserverXX IN A 10.10.10.1 www.webserverXX IN CNAME webserverXX.pxl.lan. webserver2XX IN A 10.10.10.1 www.webserver2XX IN CNAME webserver2XX.pxl.lan.
# verhoog het serial in de SOA! anders zien slaves/cache de wijziging niet sudo named-checkzone pxl.lan /etc/named/pxl.lan.db sudo systemctl reload named # controleer beide namen nslookup webserverXX.pxl.lan nslookup webserver2XX.pxl.lan
✔ Verificatie Beide nslookup's geven Address: 10.10.10.1. De CNAME-namen tonen eerst de canonical name, dan het A-record.
VHost Taak 06
Per-gebruiker hosting met mod_userdir
▶

Met mod_userdir krijgt elke gebruiker een eigen webmap. Plaatst gebruiker student bestanden in ~/public_html, dan zijn die bereikbaar via http://server/~student.

# Backup en bewerk de hoofdconfig sudo cp /etc/httpd/conf/httpd.conf /etc/httpd/conf/httpd.conf.orig sudo nano /etc/httpd/conf/httpd.conf

Voeg onderaan toe:

<IfModule mod_userdir.c> UserDir enabled student UserDir public_html </IfModule> <Directory /home/*/public_html> Options Indexes Includes FollowSymLinks Require all granted </Directory>
# Als gebruiker student: mkdir ~/public_html nano ~/public_html/index.html # httpd moet 'door' /home kunnen (execute-bit) — in RHEL10 meestal al ok sudo chmod +x /home /home/* sudo apachectl configtest sudo systemctl reload httpd # test via CLI-browser sudo dnf install lynx lynx http://localhost/~student
💡 Waarom het execute-bit op mappen telt Op een directory betekent de x-rechten niet "uitvoeren" maar "mag erin / mag erdoorheen". Zonder x op /home/student kan het apache-proces de map niet binnengaan, zelfs als de bestanden leesbaar zijn — je krijgt dan een 403. Daarom chmod +x op de home-mappen.
Deel 3 — Beveiliging (rechten, firewall, login)
Secure Taak 07
Bestandsrechten en eigenaarschap
▶

De webinhoud moet leesbaar zijn voor de gebruiker waaronder Apache draait: apache. Geef de webroot het juiste eigenaarschap en rechten.

sudo chown -R apache:apache /var/www/html sudo chmod -R 755 /var/www/html # controleer ls -ld /var/www/html ls -l /var/www/html # Apache draait NIET als root — check de service-user cat /etc/passwd | grep apache
💡 Waarom Apache niet als root draait De daemon draait als de onbevoorrechte gebruiker apache met shell /sbin/nologin (je kunt er niet mee inloggen). Wordt de webserver ooit gehackt, dan zit de aanvaller vast in de rechten van die ene gebruiker — niet die van root. Dit principe heet least privilege: geef een proces nooit meer rechten dan het nodig heeft.
💡 Wat betekent 755? 7 (owner) = rwx, 5 (group) = r-x, 5 (others) = r-x. Mappen hebben de x nodig om "ingegaan" te worden; bestanden hebben genoeg aan r (4) om geserveerd te worden. 755 geeft de eigenaar volledige controle en laat iedereen lezen — precies wat een publieke website nodig heeft.
Service Taak 08
Open de firewall voor HTTP en HTTPS
▶

Apache luistert al op poort 80, maar firewalld blokkeert extern verkeer. Test eerst vanaf de client met nmap dat het dicht zit, open dan de poorten in de interne zone.

# Op de server: luistert httpd echt op :80? sudo ss -tulpn | grep httpd # Op de client: poort 80/443 bereikbaar? nmap -p 80,443 10.10.10.1 # → eerst 'filtered'/down
# Op de server: open http + https in de interne zone sudo firewall-cmd --add-service=http --zone=internal --permanent sudo firewall-cmd --add-service=https --zone=internal --permanent sudo firewall-cmd --complete-reload # Op de client opnieuw scannen nmap -p 80,443 10.10.10.1 # → 80/tcp open http
💡 De service draait ≠ de service is bereikbaar Drie lagen moeten kloppen voordat een client je site ziet: (1) de service draait en luistert (ss), (2) de firewall laat de poort door (firewall-cmd), en (3) SELinux staat het toe. Faalt er één, dan krijg je geen pagina. Test daarom altijd van buitenaf met nmap of curl, niet alleen op localhost.
✔ Verificatie sudo firewall-cmd --zone=internal --list-services bevat http (en https). Vanaf de client: curl http://10.10.10.1 geeft je pagina terug.
Secure Taak 09
Beveilig een map met een wachtwoord (.htaccess + htpasswd)
▶

We maken een map /protected die om een login vraagt. Eerst moet Apache .htaccess-overrides toestaan voor de webroot.

sudo nano /etc/httpd/conf/httpd.conf

Voeg toe (laat .htaccess alleen auth-instellingen overschrijven):

<Directory "/var/www/html"> AllowOverride AuthConfig </Directory>
sudo systemctl reload httpd sudo mkdir /var/www/html/protected sudo nano /var/www/html/protected/.htaccess
AuthType Basic AuthName "Beveiligd onderdeel" AuthUserFile "/var/www/.htpasswd" AuthGroupFile /dev/null require valid-user
# maak het wachtwoordbestand BUITEN de webroot. -c = create (alleen 1e keer!) cd /var/www/ sudo htpasswd -c .htpasswd student # extra gebruiker zonder -c, anders overschrijf je het bestand: sudo htpasswd .htpasswd lector # pagina + rechten sudo nano /var/www/html/protected/protected.html sudo chown -R apache:apache /var/www/html sudo chmod -R 755 /var/www/html sudo systemctl reload httpd
💡 Waarom .htpasswd buiten /var/www/html? Het wachtwoordbestand (met gehashte wachtwoorden) mag nooit zelf via de browser opvraagbaar zijn. Door het in /var/www/ te zetten i.p.v. in de webroot /var/www/html/, kan Apache het wél lezen maar kan een bezoeker het niet downloaden. AuthType Basic stuurt het wachtwoord ongecodeerd mee — daarom hoort dit altijd samen met HTTPS (Deel 4).
✔ Verificatie Surf naar http://webserverXX.pxl.lan/protected/protected.html → je krijgt een loginpop-up. Juiste credentials → pagina verschijnt; foute → 401 Unauthorized.
Deel 4 — HTTPS met SSL/TLS
Config Taak 10
Installeer mod_ssl en bekijk de standaardconfig
▶

HTTPS = HTTP over een versleutelde TLS-verbinding. De module mod_ssl voegt poort 443-ondersteuning toe.

sudo dnf install mod_ssl sudo cat /etc/httpd/conf.d/ssl.conf | grep -E "SSLCertificate"
SSLCertificateFile /etc/pki/tls/certs/localhost.crt SSLCertificateKeyFile /etc/pki/tls/private/localhost.key
💡 De SSL-handshake in het kort (1) Client vraagt een beveiligde sessie. (2) Server stuurt zijn certificaat met daarin zijn publieke sleutel. (3) Client controleert het certificaat tegen vertrouwde CA's. (4) Client maakt een willekeurige sessiesleutel, versleutelt die met de publieke sleutel van de server en stuurt ze door. (5) Beide partijen gebruiken vanaf nu die ene sessiesleutel voor snelle symmetrische encryptie. Asymmetrisch wordt dus alleen gebruikt om de symmetrische sleutel veilig uit te wisselen.
💡 Symmetrisch vs asymmetrisch Asymmetrisch = sleutelpaar: publieke sleutel versleutelt, privésleutel ontsleutelt. Veilig maar traag. Symmetrisch = één gedeelde sleutel voor beide kanten. Snel maar je moet de sleutel eerst veilig delen. TLS combineert het beste van beide: asymmetrisch voor de sleuteluitwisseling, symmetrisch voor de echte data.
Secure Taak 11
Genereer een zelfondertekend certificaat
▶

Voor een intern/testsysteem maak je zelf een certificaat. Het pad komt overeen met wat ssl.conf al verwacht, dus je hoeft die config niet aan te passen.

sudo openssl req -new -newkey ec -pkeyopt ec_paramgen_curve:P-256 \ -nodes \ -keyout /etc/pki/tls/private/localhost.key \ -x509 -days 365 \ -out /etc/pki/tls/certs/localhost.crt

Vul de velden in (Common Name = je hostname!):

Country Name: BE State: Limburg Locality: Hasselt Organization: PXL Common Name: webserverXX.pxl.lan ← moet matchen met de URL!
sudo systemctl reload httpd
💡 De openssl-opties ontleed -newkey ec -pkeyopt ec_paramgen_curve:P-256 = maak een ECC-sleutel (modern, kort, snel). -nodes = sla de privésleutel op zónder wachtwoord, zodat Apache automatisch kan opstarten. -x509 = maak meteen een zelfondertekend certificaat i.p.v. enkel een aanvraag (CSR). -days 365 = één jaar geldig. Laat je -x509 weg, dan krijg je een CSR die je naar een echte CA stuurt.
Verwacht een browserwaarschuwing. Een zelfondertekend certificaat is niet ondertekend door een vertrouwde CA, dus de browser meldt "niet veilig". Voor een intern testsysteem is "risico aanvaarden en doorgaan" prima. Voor een publieke site vraag je een CA-certificaat aan (bv. gratis via Let's Encrypt).
✔ Verificatie Surf naar https://webserverXX.pxl.lan. Na het accepteren van de waarschuwing zie je je site, en het slotje toont je certificaatgegevens. Vanaf de client: curl -k https://10.10.10.1 (-k = negeer cert-waarschuwing).
Deel 5 — Logging
Test Taak 12
Lees de error_log en access_log live mee
▶

Logs zijn je belangrijkste troubleshooting-tool: fouten opsporen, zien wie de server bezoekt, aanvallen herkennen. De twee belangrijkste staan in /var/log/httpd/.

# error_log = wat ging er mis (config-fouten, 403/404/500, opstartproblemen) sudo tail -f /var/log/httpd/error_log # Surf nu naar http://127.0.0.1/onbekendemap → er verschijnt een nieuwe regel
# access_log = elke binnenkomende request (IP, tijd, pad, statuscode, browser) sudo tail -f /var/log/httpd/access_log # Surf afwisselend met Firefox en Chromium → user-agent verschilt per regel
💡 LogLevel verfijnen In httpd.conf bepaalt LogLevel hoeveel detail de error_log krijgt: van emerg (alleen rampen) tot debug (alles). Standaard staat hij op warn; tijdens troubleshooting zet je hem tijdelijk op info of debug en herlaad je Apache. Vergeet niet terug te zetten — debug laat logs snel vollopen.
💡 Snelle access_log-analyse Met awk haal je zo statistieken uit de log. Top-10 IP's: awk '{print $1}' access_log | sort | uniq -c | sort -nr | head. Alle 404's: grep " 404 " access_log. Dit is precies hoe je een verdachte piek of een scan-poging opspoort.
Deel 6 — Examenoefeningen (zelf doen)
Exam Taak 13
Oefeningen 1–4: de volledige keten
▶

Dit zijn de officiële oefeningen. Probeer ze eerst zelf — de aanpak hieronder is een vangnet, geen kopieerwerk. Documenteer je commando's en maak screenshots (dat wordt expliciet gevraagd). Vervang <naam> door je voor-/achternaam en XX door je servernummer.

  • Oef 1: 2 vhosts op poorten 41347 en 1321. Inhoud = voornaam resp. achternaam.
  • Oef 2: 2 vhosts op verschillende IP-adressen, ingesteld via de CLI (niet NetworkManager-GUI).
  • Oef 3: Voeg een login toe aan één site (gebruiker + wachtwoord pxl).
  • Oef 4: Zet die beveiligde site over HTTPS met een eigen SSL-certificaat.
Oef 1 (poorten): naast de <VirtualHost *:41347> moet Apache ook op die poort luisteren — voeg een Listen 41347 en Listen 1321 toe (in de conf), en open ze in de firewall met --add-port=41347/tcp. Oef 2 (IP's): een tweede IP zet je op de interface via nmcli (CLI!), niet via de grafische NetworkManager. Oef 3: hergebruik de .htaccess+htpasswd-aanpak uit Taak 09. Oef 4: hergebruik het zelfondertekende cert uit Taak 11, maar verwijs ernaar in de <VirtualHost *:443> van die specifieke site.

Oef 1 — poort-gebaseerd:

# bovenaan de conf of in httpd.conf: Listen 41347 Listen 1321 <VirtualHost *:41347> DocumentRoot /var/www/html/voornaam </VirtualHost> <VirtualHost *:1321> DocumentRoot /var/www/html/achternaam </VirtualHost>
sudo firewall-cmd --add-port=41347/tcp --zone=internal --permanent sudo firewall-cmd --add-port=1321/tcp --zone=internal --permanent sudo firewall-cmd --reload sudo httpd -t && sudo systemctl reload httpd curl http://localhost:41347 # → voornaam

Oef 2 — IP-gebaseerd (tweede IP via nmcli):

# voeg een tweede IP toe aan de interne interface (pas conn-naam aan) sudo nmcli connection modify ens224 +ipv4.addresses 10.10.10.2/24 sudo nmcli connection up ens224 ip a # controleer beide IP's
<VirtualHost 10.10.10.1:80> ServerName voornaam.local DocumentRoot /var/www/html/voornaam </VirtualHost> <VirtualHost 10.10.10.2:80> ServerName achternaam.local DocumentRoot /var/www/html/achternaam </VirtualHost>

Oef 3 — login: exact de aanpak van Taak 09 (AllowOverride AuthConfig → .htaccess → htpasswd -c), met wachtwoord pxl.

Oef 4 — HTTPS: genereer het cert (Taak 11), en wijs er in de SSL-vhost naar:

<VirtualHost *:443> ServerName achternaam.local DocumentRoot /var/www/html/achternaam SSLEngine on SSLCertificateFile /etc/pki/tls/certs/localhost.crt SSLCertificateKeyFile /etc/pki/tls/private/localhost.key </VirtualHost>

Vergeet de firewall niet: --add-service=https. Test met curl -k https://achternaam.local.

Deel 7 — Troubleshooting Scenario
Debug Taak 14
"Mijn site geeft 403 Forbidden" — vind de oorzaak systematisch
▶

Een collega heeft een vhost opgezet maar krijgt 403 Forbidden in de browser. De service draait, de config-syntax is OK (httpd -t = Syntax OK). Werk de keten systematisch af.

# 1. Draait de service en is de config geldig? sudo systemctl status httpd sudo httpd -t # 2. Luistert hij op de juiste poort? sudo ss -tulpn | grep httpd # 3. Staat de firewall open? sudo firewall-cmd --zone=internal --list-services # 4. Kloppen de bestandsrechten/eigenaarschap? ls -ld /var/www/html /var/www/html/site ls -l /var/www/html/site # 5. Klopt de SELinux-context? ls -Z /var/www/html/site/ # 6. Wat zegt de error_log precies? sudo tail -30 /var/log/httpd/error_log
Een 403 betekent: Apache vindt de bron wel maar mág hem niet serveren. Drie klassieke oorzaken: (1) de map mist het x-bit of het bestand mist r voor 'others'/apache; (2) de SELinux-context is verkeerd (geen httpd_sys_content_t) — gebeurt vaak als je bestanden vanuit je homedir hebt verplaatst i.p.v. gekopieerd; (3) een ontbrekende Require all granted of een Options -Indexes zonder index-bestand.

Meest waarschijnlijke oorzaak: SELinux-context. ls -Z toont bv. user_home_t i.p.v. httpd_sys_content_t. Apache mag wegens SELinux geen bestanden serveren die niet de juiste context dragen, ook al kloppen de gewone Unix-rechten.

# Herstel de standaardcontext op de webroot: sudo restorecon -Rv /var/www/html/ # Permanent een eigen pad als webcontent markeren: sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/html/site(/.*)?" sudo restorecon -Rv /var/www/html/site/

Andere checks als context al klopt:

Rechten: sudo chown -R apache:apache /var/www/html && sudo chmod -R 755 /var/www/html.

Config: zorg dat het <Directory>-blok Require all granted bevat, en dat er een index.html bestaat als directory-listing uit staat (Options -Indexes).

De error_log wijst je trouwens meestal recht naar de oorzaak — lees altijd eerst de laatste regels (tail -30) voor je gaat gokken.
