SaMBa — file sharing tussen Linux en Windows

Tot nu toe deelde je diensten (web, DNS, DHCP) met clients. In dit hoofdstuk deel je bestanden. Je bouwt een Samba-fileserver met drie soorten shares — een publieke map die iedereen mag lezen, een private map enkel voor leden van een groep, en home directories per gebruiker. Werk je in een gemengd Linux/Windows-netwerk, dan is Samba dé manier om dat te doen via het SMB-protocol dat Windows van nature spreekt.

📋 Scenario

Je server (10.10.10.1) krijgt nu een nieuwe rol: NetBIOS-naam ServerXX in de Windows-werkgroep WORKGROUP. Je collega's gebruiken zowel Linux- als Windows-laptops en willen een eenvoudige gedeelde schijf. Je zet drie shares op: public (iedereen mag lezen, leden van nasusers mogen schrijven), private (enkel leden van nasusers) en automatische [homes] per gebruiker. Twee testgebruikers — alice en bob — krijgen toegang. Vanaf clientXX test je alles met smbclient en de GNOME-bestandsverkenner. Vervang overal XX door je eigen servernummer.

📁 Wat ga je delen?

[public]
Lezen: iedereen (ook guest).
Schrijven: enkel groep nasusers.
Pad: /srv/shares/public
[private]
Lezen + schrijven: enkel groep nasusers.
Guest: krijgt ACCESS_DENIED.
Pad: /srv/shares/private
[homes]
Wat: automatisch één share per Samba-user.
Alice ziet //ServerXX/alice, Bob ziet //ServerXX/bob.
Niet zichtbaar in de browse-lijst.

🌐 Hoe komt een client bij een share?

Client
Wil naar //ServerXX/public
→
nmbd

Deel 1 — Voorbereiding
Prep Taak 01
Firewalld actief, nftables uit — en pakketten installeren
▶

RHEL kan firewallregels op twee manieren beheren: firewalld (high-level, met zones en services) of rechtstreeks nftables (low-level, met tables/chains). Beide tegelijk laat je niet draaien — ze schrijven dezelfde kernel-regels en gaan elkaar tegenspreken. Voor Samba gebruiken we firewalld.

# controleer welke draait sudo systemctl status nftables firewalld # als nftables actief is: stoppen + permanent uitschakelen sudo systemctl disable --now nftables # firewalld permanent aanzetten sudo systemctl enable --now firewalld # installeer de Samba-server (en de client-tools die je voor tests nodig hebt) sudo dnf install samba samba-client samba-common -y
💡 Wat zit in welk pakket?
  • samba — de server-daemons smbd en nmbd, en smb.conf.
  • samba-client — de tools smbclient, nmblookup, smbtree. Ook nodig op clientXX.
  • samba-common — gedeelde libraries en testparm (configvalidatie).
✔ Verificatie systemctl is-active firewalld → active. which smbd → /usr/sbin/smbd.
Prep Taak 02
Groep nasusers + gebruikers alice en bob
▶

Je maakt op Linux twee accounts aan en stopt ze in een gemeenschappelijke groep. Belangrijk: Linux-gebruikers zijn niet automatisch Samba-gebruikers — Samba houdt zijn eigen wachtwoord-database bij (tdbsam). Je moet ze apart toevoegen met smbpasswd -a.

# 1. groep aanmaken sudo groupadd nasusers # 2. Linux-users + lid van de groep maken sudo useradd -G nasusers alice sudo useradd -G nasusers bob # 3. Linux-wachtwoord instellen (voor login op de server zelf) sudo passwd alice sudo passwd bob # 4. SMB-wachtwoord instellen (voor toegang tot shares) — kan anders zijn dan #3 sudo smbpasswd -a alice sudo smbpasswd -a bob # controle id alice id bob
💡 Waarom twee wachtwoorden? Het Linux-wachtwoord (in /etc/shadow) is voor SSH/console-login. Het Samba-wachtwoord (in /var/lib/samba/private/passdb.tdb) is voor SMB-verbindingen. Samba kán Linux-wachtwoorden niet rechtstreeks gebruiken omdat die anders gehasht zijn dan wat het SMB-protocol verwacht. In productie zet je beide gelijk via PAM-koppeling — voor dit labo doen we het manueel. -a = add: voeg de gebruiker toe; zonder -a wijzig je een bestaand SMB-wachtwoord.
✔ Verificatie id alice moet nasusers in de lijst groepen tonen, bijvoorbeeld: uid=1001(alice) gid=1002(alice) groups=1002(alice),1001(nasusers). sudo pdbedit -L toont alle Samba-users — alice en bob moeten erin staan.
Prep Taak 03
Maak de share-directories met de juiste rechten
▶

Samba is uiteindelijk maar een doorgeefluik — de echte rechten staan op het Linux-filesystem. Maak de mappen, zet eigenaar/groep correct, en zet g+w (group write) zodat leden van nasusers erin kunnen schrijven.

sudo mkdir -p /srv/shares/public sudo mkdir -p /srv/shares/private # de map blijft van root, maar de groep wordt nasusers sudo chgrp nasusers /srv/shares/public /srv/shares/private # groep mag schrijven (g+w); rest zoals het was sudo chmod 2775 /srv/shares/public sudo chmod 2770 /srv/shares/private ls -ld /srv/shares/public /srv/shares/private
💡 Wat doet die 2 vooraan? 2775 en 2770 hebben een SGID-bit (de "2"). Bij een directory betekent SGID: nieuwe bestanden erven de groep van de map, niet de primary group van de gebruiker. Maakt Alice een bestand in /srv/shares/public, dan wordt de groep automatisch nasusers in plaats van alice. Dat is exact wat je wil voor gedeelde mappen — anders kan Bob het bestand van Alice niet aanpassen.
ℹ Permissions decoded: 2775 = SGID + rwxrwxr-x. Owner (root) en groep (nasusers) hebben volledig, others mogen lezen + binnenwandelen. 2770 = idem maar others hebben niets — strakker.
✔ Verificatie ls -ld /srv/shares/private → drwxrws--- 2 root nasusers .... Het kleine s in plaats van x bij de groep bevestigt het SGID-bit.
Prep Taak 04
SELinux tijdelijk uitschakelen
▶

SELinux blokkeert standaard veel Samba-functionaliteit (bijvoorbeeld lezen buiten /var/lib/samba/). Je leert SELinux in een later hoofdstuk grondig kennen; voor nu zetten we het in permissive: het logt overtredingen wél maar blokkeert ze niet.

sudo setenforce 0 getenforce
Tijdelijk! setenforce 0 overleeft een reboot niet — wel goed nieuws voor je leslokaal-VM. Wil je permanent permissive (afgeraden): pas SELINUX=permissive aan in /etc/selinux/config. Later in de cursus leer je de juiste manier: SELinux aan houden en de juiste booleans + contexts zetten.
💡 De drie SELinux-booleans/contexts voor Samba (voor later)
  • samba_enable_home_dirs = on — laat Samba [homes] serveren.
  • semanage fcontext -a -t samba_share_t '/srv/shares(/.*)?' — markeer je share-mappen.
  • restorecon -Rv /srv/shares — pas die regel toe op bestaande bestanden.
✔ Verificatie getenforce → Permissive.
Deel 2 — smb.conf schrijven
Config Taak 05
Back-up de default, schrijf je eigen /etc/samba/smb.conf
▶

Eerst: maak altijd een back-up vóór je een groot configbestand vervangt. Zo kan je in 5 seconden terug naar de werkende versie.

sudo cp /etc/samba/smb.conf /etc/samba/smb.conf.bak sudo nano /etc/samba/smb.conf

Vervang de inhoud door dit (vervang ServerXX door je echte servernaam):

[global] netbios name = ServerXX workgroup = WORKGROUP server string = Bestandsserver log file = /var/log/samba/samba.log max log size = 5000 security = user passdb backend = tdbsam map to guest = bad user wins support = yes load printers = no printing = bsd printcap name = /dev/null disable spoolss = yes [homes] comment = Home Directories browseable = no writable = yes [public] comment = Openbare share path = /srv/shares/public public = yes write list = +nasusers force group = nasusers create mask = 0660 directory mask = 0770 [private] comment = Privé share path = /srv/shares/private valid users = +nasusers writable = yes force group = nasusers create mask = 0660 directory mask = 0770
💡 De vier secties uitgeschreven
  • [global] — server-brede instellingen. NetBIOS-naam, werkgroep, security mode, logging. Geldt voor de hele server.
  • [homes] — een magische sectie. Samba maakt automatisch een share per Samba-gebruiker met dezelfde naam als de username. Alice ziet //ServerXX/alice, Bob ziet //ServerXX/bob. browseable = no betekent: de share staat niet in de openbare lijst — je moet weten dat hij bestaat.
  • [public] — een gewone share. public = yes + map to guest = bad user in global laat anonieme lezen toe. write list = +nasusers beperkt schrijven tot leden van die groep.
  • [private] — valid users = +nasusers betekent: alleen leden van nasusers mogen überhaupt verbinden. Geen guest-toegang.
💡 De kleinere directives
  • security = user — verplicht inloggen; geen anonieme guest-mode op de hele server.
  • passdb backend = tdbsam — bewaar SMB-wachtwoorden in een TDB-database (eenvoudig, snel).
  • map to guest = bad user — onbekende usernames worden behandeld als guest (i.p.v. login-error). Nodig voor de public-share.
  • wins support = yes — bied NetBIOS-naamresolutie aan (oude Windows-stijl).
  • force group = nasusers — wie ook een bestand maakt, de groep wordt altijd nasusers. Gecombineerd met de SGID-bit op de directory een waterdichte garantie.
  • create mask = 0660 / directory mask = 0770 — nieuwe bestanden krijgen rw-rw----, mappen rwxrwx---. Owner + groep volledig, anderen niets.
  • De + voor nasusers in write list / valid users betekent: de groep. Zonder + zou Samba een gebruiker zoeken met de naam "nasusers".
  • load printers = no, printing = bsd, printcap name = /dev/null, disable spoolss = yes — vier directives om alle printer-functionaliteit dicht te schroeien. Anders zoekt Samba bij elke start naar printers en logt waarschuwingen. Wij doen alleen file sharing.
Config Taak 06
Valideer met testparm
▶

testparm is voor Samba wat httpd -t voor Apache is: het leest smb.conf en geeft syntaxfouten. Eén typo in een sectie-naam tussen vierkante haken en de share verdwijnt geruisloos — testparm ziet dat meteen.

# druk Enter na de eerste output om de "effective" config te zien sudo testparm # tip: -s = "skip" de Enter-prompt sudo testparm -s
💡 Wat moet je zien? Loaded services file OK. bovenaan. Daarna een lijst van je sectie-namen: [global], [homes], [public], [private]. Krijg je waarschuwingen zoals "Unknown parameter encountered", dan heb je ergens een tikfout.
✔ Verificatie Geen errors, geen "Unknown parameter"-waarschuwingen, alle vier de secties opgesomd.
Deel 3 — Services starten en firewall openzetten
Service Taak 07
Start smb én nmb en zet ze enabled
▶

Samba bestaat uit twee daemons. Vergeet je er één, dan werkt de helft niet en wordt foutzoeken een hel.

sudo systemctl enable --now smb sudo systemctl enable --now nmb systemctl status smb nmb --no-pager
💡 smb vs nmb
  • smbd — de echte file server. Spreekt het SMB/CIFS-protocol op TCP-poort 445. Authenticeert gebruikers en serveert bestanden.
  • nmbd — de NetBIOS name service. Luistert op UDP 137 en 138. Antwoordt op vragen als "wie heet ServerXX?" en host de browse-lijst (de "Netwerkomgeving" in oude Windows).
Als smbd draait maar nmbd niet, kan de client de server vinden via IP maar niet via naam. Andersom: hij vindt de naam wel, maar krijgt geen bestanden.
✔ Verificatie Beide services active (running) én enabled. ss -tlnp | grep 445 toont smbd luisterend.
Firewall Taak 08
Open de Samba-service in zone internal
▶

Firewalld kent een voorgedefinieerde service-bundle die alle Samba-poorten in één commando opent (TCP 139, TCP 445, UDP 137, UDP 138). Activeer hem in je interne zone — niet de public zone, want je server hoort niet open te staan naar het internet.

sudo firewall-cmd --permanent --zone=internal --add-service=samba sudo firewall-cmd --reload # controle sudo firewall-cmd --zone=internal --list-services
ℹ Vier poorten in één service: --add-service=samba = 137/udp + 138/udp + 139/tcp + 445/tcp. Wil je losse poorten, dan zou je vier commando's nodig hebben. De firewalld-service-bundle is gewoon een snelkoppeling.
✔ Verificatie firewall-cmd --zone=internal --list-services bevat samba.
Deel 4 — Vanaf clientXX testen
NetBIOS Taak 09
NetBIOS naamresolutie vanaf clientXX testen
▶

Vóór je file-toegang test, controleer eerst of de client de naam ServerXX überhaupt kan vinden. Installeer de tools en open op de client de NetBIOS-poort.

# op clientXX: sudo dnf install samba-client -y # welke firewalld-zone is actief op de client? sudo firewall-cmd --get-active-zones

Stel: actief is zone public op interface ens160. Open UDP-poort 137 in die zone:

# UDP 137 = NetBIOS Name Service sudo firewall-cmd --permanent --zone=public --add-port=137/udp sudo firewall-cmd --reload # test het: nmblookup ServerXX
Werkt het nog niet? Output name_query failed to find name ServerXX is een bekende dwarsligger. Linux blokkeert standaard alle inkomende UDP-137 packets — ook als ze antwoorden zijn op een query die jij hebt gestuurd — omdat UDP-137 een geliefde vector is voor DDoS-amplificatie. Je moet een specifiekere regel toevoegen die antwoorden vanaf je server expliciet toelaat:
sudo firewall-cmd --permanent --zone=public --add-rich-rule=\\ 'rule family="ipv4" source address="10.10.10.1" port port=137 protocol=udp accept' sudo firewall-cmd --reload
Vertaald: "sta inkomend UDP-verkeer toe als het van 10.10.10.1 komt én vanaf bronpoort 137." Dit is een rich rule — fijner dan de gewone service-bundles.
💡 NetBIOS vs DNS NetBIOS dateert uit het OS/2-tijdperk en is de Windows-manier om flat machine-namen (zonder dots) op een lokaal netwerk te resolven. Geen domeinen, geen hiërarchie — gewoon "wie heet hier ServerXX?" via een UDP-broadcast. Tegenwoordig gebruikt iedereen DNS, maar SMB sleept NetBIOS nog mee voor compatibiliteit. nmblookup is de NetBIOS-equivalent van nslookup.
✔ Verificatie nmblookup ServerXX → 10.10.10.1 ServerXX<00>.
Test Taak 10
Lijst de shares op met smbclient -L
▶

Tijd om de shares zichtbaar te maken. smbclient -L vraagt een server "welke shares biedt jij aan?" — en de uitkomst hangt af van wie je bent.

# als alice (krijgt password-prompt) smbclient -L //ServerXX -U alice # als guest (geen wachtwoord) smbclient -L //ServerXX -U % # via IP-adres werkt ook smbclient -L //10.10.10.1 -U alice

Voor alice zie je vier shares: public, private, IPC$, en alice (de home-share). Voor guest zie je er maar drie — geen home-share, want guest heeft er geen.

Sharename Type Comment --------- ---- ------- public Disk Openbare share private Disk Privé share IPC$ IPC IPC Service (Bestandsserver) alice Disk Home Directories <-- alleen voor alice!
💡 Wat is -U %? Het -U-argument is username%password. -U % betekent dus: lege username, leeg wachtwoord = anoniem / guest. Dat werkt alleen omdat we in smb.conf map to guest = bad user hebben gezet.
💡 Waarom verschijnt private in de lijst, ook voor guest? smbclient -L toont gewoon alle shares die bestaan. Guest ziet private maar mag er niet in — bij een poging tot verbinden krijg je NT_STATUS_ACCESS_DENIED (test je in de volgende taak). De browseable-instelling regelt dit, en die staat default op yes. Bij [homes] hebben we expliciet browseable = no gezet — daarom verschijnt het niet in de lijst, ook al kan alice er wel naar verbinden.
ℹ IPC$: de Inter-Process Communication-share. Geen echte map; Windows gebruikt hem om RPC-calls te doen (info opvragen, sessies opzetten). Verbergt zich niet, mag je negeren.
✔ Verificatie Als alice zie je 4 sharenames; als guest zie je er 3. SMB1 disabled in de output is goed nieuws — SMBv1 is onveilig en mag uit.
Test Taak 11
Toegang tot shares testen met smbclient
▶

Maak eerst op de server twee testbestanden zodat er iets te downloaden valt:

# op ServerXX sudo touch /srv/shares/public/pub.txt sudo touch /srv/shares/private/priv.txt sudo chgrp nasusers /srv/shares/public/pub.txt /srv/shares/private/priv.txt sudo chmod g+w /srv/shares/public/pub.txt /srv/shares/private/priv.txt # maak ook een testbestand op clientXX om straks te uploaden # (op clientXX): echo "hallo van client" > ~/testje.txt

Nu ga je vier toegangsscenarios afvinken. Telkens vanaf clientXX:

1. Guest probeert in public te schrijven — moet falen:

smbclient //ServerXX/public -U %
smb: \> pwd Current directory is \\ServerXX\public\ smb: \> ls pub.txt N 0 Tue Apr 15 10:30:55 2025 smb: \> get pub.txt getting file \pub.txt of size 0 ... <-- mag wel downloaden smb: \> mkdir testdir NT_STATUS_ACCESS_DENIED making remote directory <-- mag NIET schrijven smb: \> exit

2. Alice in public — moet wél kunnen schrijven:

smbclient //ServerXX/public -U alice
smb: \> mkdir alicedir <-- werkt, geen error smb: \> ls alicedir D 0 ...

3. Guest in private — mag niet eens verbinden:

smbclient //ServerXX/private -U %
tree connect failed: NT_STATUS_ACCESS_DENIED

4. Alice in private — mag verbinden + uploaden:

smbclient //ServerXX/private -U alice
smb: \> put testje.txt <-- upload werkt smb: \> ls priv.txt N 0 ... testje.txt A 0 ...

Terug op de server controleer je dat het geüploade bestand de juiste groep gekregen heeft:

# op ServerXX ls -l /srv/shares/private/ # -rw-rw---- 1 alice nasusers 0 ... testje.txt
💡 Waarom is de groep nasusers en niet alice? Twee mechanismes werken samen: (1) de SGID-bit op /srv/shares/private uit Taak 3, en (2) force group = nasusers in smb.conf. Beide doen ongeveer hetzelfde, maar op verschillende niveaus — defense in depth. Zonder beide zou Bob het bestand van Alice niet kunnen aanpassen, want het zou groep alice hebben.
✔ Verificatie Alle vier de scenario's gedragen zich zoals verwacht: guest leest public maar schrijft niet; guest komt niet in private; alice schrijft in beide.
Deel 5 — GUI & troubleshooting
GUI Taak 12
Verbind vanuit de GNOME bestandsverkenner
▶

De command line is fijn voor testen en automatisering, maar je collega's willen klikken. GNOME spreekt SMB via GVFS (GIO Virtual File System) — daarvoor moet alleen het pakket gvfs-smb geïnstalleerd zijn (in een desktop-RHEL meestal al het geval).

Stel eerst expliciet welke SMB-versies de server aanbiedt — GNOME houdt soms niet van te oude of te nieuwe protocolversies:

sudo nano /etc/samba/smb.conf

Voeg toe in de [global]-sectie:

server min protocol = SMB2 server max protocol = SMB3
sudo testparm -s sudo systemctl restart smb nmb

Op clientXX (GUI):

  1. Open de bestandsverkenner (Files / Nautilus).
  2. Druk Ctrl+L om de adresbalk te tonen.
  3. Typ smb://ServerXX/public en druk Enter → kies "Anonymous".
  4. Voor de private share: smb://ServerXX/private → log in als alice.
  5. Voor de home-share: smb://ServerXX/alice/ (de credentials van net worden hergebruikt).
SMBv1 is dood. Moderne Samba ondersteunt het oude SMBv1-protocol niet meer standaard. Dat is goed (security), maar betekent dat de oude "Netwerkomgeving"-browse-functie in Windows Explorer niet meer alle hosts vindt. Wat wel blijft werken: rechtstreeks verbinden met een gekende servernaam of IP (\\ServerXX\public op Windows, smb://ServerXX/public op GNOME).
💡 De drie lagen waar toegang aan getoetst wordt
  • Linux-bestandspermissies — owner / group / others, rwx. Dit is de laatste check: zelfs als Samba de gebruiker laat passeren, kan het filesystem nog steeds weigeren.
  • Samba-configuratie — valid users, write list, writeable, public. Dit is de eerste check.
  • SELinux (als enforcing) — context samba_share_t op de bestanden, booleans als samba_enable_home_dirs. Onafhankelijke extra laag bovenop de andere twee.
Werkt iets niet? Check ze in deze volgorde: 1) testparm, 2) ls -l, 3) getenforce + ausearch -m AVC -ts recent.
Debug Taak 13
Logs lezen wanneer iets niet werkt
▶

Drie logbestanden, drie verschillende bronnen:

# algemene Samba-log (uit smb.conf: log file = ...) sudo tail -f /var/log/samba/samba.log # specifiek voor smbd — authenticatie, share-toegang, file ops sudo tail -f /var/log/samba/log.smbd # specifiek voor nmbd — naamresolutie, browse-conflicten sudo tail -f /var/log/samba/log.nmbd

Workflow als iets stuk is:

  1. sudo testparm -s — syntaxfout in smb.conf?
  2. systemctl status smb nmb — draaien ze?
  3. ss -tlnp | grep -E ':(445|139)' — luistert smbd op TCP?
  4. firewall-cmd --zone=internal --list-services — staat samba open?
  5. ls -lZ /srv/shares/ — kloppen Linux- én SELinux-rechten?
  6. tail -n 50 /var/log/samba/log.smbd — wat zegt smbd?
ℹ Common error messages:
  • NT_STATUS_LOGON_FAILURE — verkeerd Samba-wachtwoord. Reset met smbpasswd alice.
  • NT_STATUS_ACCESS_DENIED bij verbinden — gebruiker niet in valid users, of geen Linux-rechten.
  • NT_STATUS_BAD_NETWORK_NAME — sharenaam bestaat niet (typo, of share niet geladen). Check testparm -s.
  • tree connect failed — Samba laat de sessie toe maar niet de share. Meestal valid users.
Deel 6 — Examenoefeningen (zelf doen)
Exam Taak 14
Oefeningen 1–5: IP-restrictie, eigen share, logging, leesgroep, Windows-host
▶

Oefening 1 — Beperk toegang tot één IP. Pas je server aan zodat hij enkel SMB-verkeer accepteert van 10.10.10.10. Test eerst dat je vanaf dat IP wél binnenkomt. Verander dan op de client het IP naar 10.10.10.15 en bewijs dat verbinden mislukt.

Twee manieren:
  • In smb.conf: voeg in [global] of per share toe: hosts allow = 10.10.10.10 en hosts deny = ALL. Restart smb. testparm om te valideren.
  • Via firewalld: rich rule met source address="10.10.10.10" voor service samba, en --remove-service=samba voor de gewone zone.
De smb.conf-aanpak is de gevraagde aanpak ("geef aan wat je aanpast aan smb.conf").

De gevraagde aanpak is via smb.conf. Voeg in de [global]-sectie toe:

hosts allow = 10.10.10.10 hosts deny = ALL

hosts allow is een whitelist; hosts deny = ALL sluit al de rest uit. De allow-regel wint van de deny-regel, dus enkel 10.10.10.10 komt binnen.

sudo testparm # valideer sudo systemctl restart smb nmb

Test 1 — vanaf de client met IP 10.10.10.10:

smbclient -L //ServerXX -U alice # → shares verschijnen, werkt

Test 2 — verander het client-IP naar 10.10.10.15 en probeer opnieuw:

# op de client: IP wijzigen via nmcli sudo nmcli connection modify ens160 ipv4.addresses 10.10.10.15/24 sudo nmcli connection up ens160 smbclient -L //ServerXX -U alice # → NT_STATUS_CONNECTION_REFUSED / "Connection denied"

De server weigert nu alles wat niet van 10.10.10.10 komt — precies de bedoeling.

Oefening 2 — Persoonlijke share. Maak een share share1 op /srv/share1. Enkel gebruiker <jevoornaam> mag erin lezen en schrijven; alle anderen krijgen niets. Toon je smb.conf-sectie en bewijs met screenshots vanaf de client dat upload + download werkt.

smb.conf-sectie:
[share1] comment = Privé share van jevoornaam path = /srv/share1 valid users = jevoornaam writable = yes browseable = no create mask = 0600 directory mask= 0700
Vergeet niet: useradd + passwd + smbpasswd -a, plus chown jevoornaam:jevoornaam /srv/share1 en chmod 700.

1. Gebruiker + share-map (vervang jevoornaam door je echte voornaam):

sudo useradd jevoornaam sudo passwd jevoornaam sudo smbpasswd -a jevoornaam sudo mkdir -p /srv/share1 sudo chown jevoornaam:jevoornaam /srv/share1 sudo chmod 700 /srv/share1

2. smb.conf-sectie (onderaan toevoegen):

[share1] comment = Privé share van jevoornaam path = /srv/share1 valid users = jevoornaam writable = yes browseable = no create mask = 0600 directory mask = 0700

valid users = jevoornaam (geen +, want het is een gebruiker, geen groep) sluit iedereen anders uit. chmod 700 op de map zorgt dat ook op Linux-niveau niemand anders erbij kan.

sudo testparm sudo systemctl restart smb nmb

3. Bewijs vanaf de client (upload + download):

Oefening 3 — Per-client logging. Zorg dat élke verbindingspoging gelogd wordt, en dat elke client een eigen logbestand krijgt. Max log size 100 MB. Onderzoek de log: wat staat erin?

In [global]:
  • log file = /var/log/samba/log.%m — %m is een Samba-variabele voor machine name / IP van de client. Eén bestand per client.
  • max log size = 102400 — in kilobytes, dus 100 MB.
  • log level = 2 of hoger — meer detail in de logs (timestamps, connect/disconnect, file ops).
Daarna: systemctl restart smb, een paar tests doen, en kijken naar ls /var/log/samba/log.*.

Pas in de [global]-sectie drie regels aan:

log file = /var/log/samba/log.%m max log size = 102400 log level = 2

De magie zit in %m: dat is een Samba-substitutievariabele die wordt vervangen door de NetBIOS-naam (of IP) van de connectende client. Het resultaat is dus geen vast bestand maar log.10.10.10.20, log.10.10.10.21, … — één per client. max log size staat in kilobytes, dus 100 MB = 102400. log level = 2 verhoogt het detail (default is 0/1).

sudo testparm sudo systemctl restart smb nmb # laat een paar clients verbinden, dan: ls -lh /var/log/samba/log.*

Wat vind je in de logs? Per verbinding: timestamp, het IP/de naam van de client, welke gebruiker authenticeerde (of faalde), welke share werd geopend (connect to service public), en file-operaties. Authenticatiefouten staan er ook in — handig om brute-force-pogingen te zien.

Oefening 4 — Read-only groepsshare. Maak share share2 waar standaard niemand mag lezen of schrijven. Leden van groep groep1 krijgen enkel leesrechten. Maak 2 gebruikers (<jevoornaam> en <jeachternaam>), beide lid van groep1. Bovendien moeten <jevoornaam>, <jeachternaam> én student een eigen homedirectory kunnen gebruiken. Test vanaf Linux- én Windows-client.

smb.conf-sectie:
[share2] path = /srv/share2 valid users = +groep1 read list = +groep1 writable = no browseable = no
Linux: chmod 750 /srv/share2, chgrp groep1 /srv/share2. Geen schrijfrecht (geen g+w), want het is read-only. Bestaande [homes]-sectie verandert niet — moet alleen wel zorgen dat de drie users een SMB-wachtwoord hebben.

1. Groep + twee gebruikers (vervang door je eigen voor-/achternaam):

sudo groupadd groep1 sudo useradd -G groep1 jevoornaam sudo useradd -G groep1 jeachternaam sudo passwd jevoornaam && sudo passwd jeachternaam sudo smbpasswd -a jevoornaam sudo smbpasswd -a jeachternaam # student moet ook een SMB-wachtwoord hebben voor zijn homedir sudo smbpasswd -a student

2. Share-map, read-only voor de groep:

sudo mkdir -p /srv/share2 sudo chgrp groep1 /srv/share2 sudo chmod 750 /srv/share2 # groep mag lezen+binnenwandelen, NIET schrijven # zet eventueel een testbestand klaar om te lezen echo "alleen lezen" | sudo tee /srv/share2/readme.txt sudo chgrp groep1 /srv/share2/readme.txt

3. smb.conf-sectie:

[share2] comment = Read-only groepsshare path = /srv/share2 valid users = +groep1 read list = +groep1 writable = no browseable = no

valid users = +groep1 laat alleen groepsleden verbinden; writable = no + read list = +groep1 maakt het read-only. De [homes]-sectie uit Taak 5 zorgt automatisch al voor de home-shares — je hoeft alleen te garanderen dat de drie users een SMB-wachtwoord hebben (stap 1).

Oefening 5 — Toegang vanaf je host-Windows. Pas oefening 4 zo aan dat je vanop je echte Windows-computer (de host waar VMware op draait, dus niet de VM) de shares kan bereiken. Maak een screenshot van het resultaat.

Wat zit ertussen? Je host-Windows zit niet op het 10.10.10.0/24-subnet van je labo — dat is een VMware-intern netwerk. Drie mogelijke oplossingen:
  • Bridged networking in VMware: je server krijgt een IP in je echte LAN. Vanaf Windows kan je dan rechtstreeks \\<servers-IP>\share2 openen.
  • Host-only of NAT met port forwarding: forward poorten 137-139 en 445 van je host-Windows naar de VM. Dan werkt \\127.0.0.1\share2 op je host.
  • VMnet aanpassen in VMware Virtual Network Editor zodat de host-machine een interface heeft in 10.10.10.0/24.
Op Windows: in Verkenner adresbalk → \\<IP-van-server>\share2. Login met je Samba-credentials.

Dit is in de kern een VMware-netwerkprobleem, niet een Samba-probleem — je hebt al een werkende server uit Oef 4. Je moet enkel zorgen dat je host-Windows en de VM elkaar kunnen bereiken. De eenvoudigste route is Host-only networking (VMnet1), want daarmee delen host en VM standaard een subnet.

1. In VMware (VM uit, dan instellen):

  • VM Settings → Network Adapter → kies Host-only (of Custom: VMnet1).
  • VMware maakt op je host-Windows automatisch een virtuele adapter "VMware Network Adapter VMnet1" met een IP in datzelfde subnet (bv. 192.168.x.1).

2. In de VM — controleer het nieuwe IP en pas zo nodig de firewall/hosts allow aan zodat de host erbij mag:

ip a # noteer het IP van de VM op VMnet1 sudo firewall-cmd --get-active-zones # staat samba open in die zone?

Had je in Oef 1 een hosts allow staan, voeg dan het host-IP toe (of haal de restrictie weg voor deze test).

3. Op host-Windows — open Verkenner en typ in de adresbalk:

\\<IP-van-de-VM>\share2

Login met je Samba-credentials (jevoornaam + SMB-wachtwoord). Maak je screenshot zodra de share-inhoud verschijnt.

Werkt het niet? Meestal is het (1) de Linux-firewall die de host-zone niet als internal ziet — voeg samba toe aan de juiste zone, of (2) Windows dat SMB-verkeer blokkeert — sta "Bestands- en printerdeling" toe in Windows Defender Firewall. Test eerst connectiviteit met ping <VM-IP> vanaf Windows.
