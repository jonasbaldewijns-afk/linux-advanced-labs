Security Enhanced Linux

In de vorige hoofdstukken mocht je SELinux soms even uitzetten om snel vooruit te gaan. Dat stopt hier. SELinux is een beveiligingslaag in de Linux-kernel die werkt met Mandatory Access Control — strikte, beleidsgedreven regels die zelfs root niet zomaar omzeilt. In dit hoofdstuk leer je hoe het werkt, hoe je de stille fouten ervan opspoort in de logs, en hoe je contexten, booleans en poorten correct aanpast in plaats van SELinux uit te schakelen.

📋 Scenario

Je werkt op je RHEL-server uit de vorige hoofdstukken. Een security-audit heeft vastgesteld dat SELinux op verschillende plaatsen permissief of uitgeschakeld stond — onaanvaardbaar voor productie. Je taak: SELinux overal terug enforcing zetten en alle diensten (Apache, Samba, …) correct laten werken mét SELinux aan. Onderweg leer je waarom een verplaatst bestand plots niet meer geserveerd wordt, hoe een stille blokkering eruitziet in audit.log, en waarom chmod 777 je probleem níét oplost.

🔐 Drie toegangsmodellen — waar SELinux past

DAC
Discretionary Access Control. De klassieke Unix-rechten: de eigenaar beslist wie mag. Flexibel, maar één foute chmod en alles ligt open.
chmod 755 file
ACL
Access Control Lists. Fijner dan DAC: rechten per individuele gebruiker of groep, bovenop de standaard owner/group/other.
setfacl -m u:jan:rwx file
MAC
Mandatory Access Control (= SELinux). Het systeembeleid beslist, niet de gebruiker. Zelfs root wordt beperkt. Afgedwongen door de kernel.
policy-gedreven, automatisch

🏷️ Anatomie van een security context

unconfined_u:object_r:httpd_sys_content_t:s0
unconfined_u — SELinux-gebruiker (MLS, negeren we)
object_r — rol (MLS, negeren we)
httpd_sys_content_t — type: dit telt!
s0 — gevoeligheidsniveau (MLS, negeren we)

⚙️ Hoe een beslissing valt: type-enforcement

Proces (subject)
httpd_t
— mag lezen? →
policy lookup
Bestand (target)
httpd_sys_content_t

Het Apache-proces draait als type httpd_t. Een bestand met type httpd_sys_content_t mag het lezen — want er bestaat een allow-regel. Heeft het bestand een ander type (bv. user_home_t of var_t), dan is er geen allow-regel en blokkeert de kernel — vaak zonder zichtbare foutmelding.

Deel 1 — Modi & status
Modi Taak 01
Controleer de SELinux-status en -modus
▶

SELinux kent drie modi. Eerst kijken in welke jouw systeem staat.

# korte uitvoer: enkel de actieve modus getenforce # volledige status: modus, policy-type, mount, ... sestatus # enkel of het aan/uit is, scriptbaar selinuxenabled && echo "Enabled" || echo "Disabled"
De drie modi
  • Enforcing — beleid wordt afgedwongen, overtredingen geblokkeerd én gelogd. Dit is productie.
  • Permissive — overtredingen worden enkel gelogd, niet geblokkeerd. Ideaal om te troubleshooten: je ziet wat er zou falen zonder dat je dienst stopt.
  • Disabled — SELinux volledig uit. Niet aanbevolen; je verliest de hele laag.
ℹ Targeted policy: sestatus toont ook het policy-type. Standaard is dat targeted: enkel specifieke "interessante" diensten (httpd, sshd, named, …) worden bewaakt, de rest draait unconfined. De alternatieven minimum en mls (Multi-Level Security) zie je zelden.
✔ Verificatie getenforce geeft Enforcing, Permissive of Disabled. sestatus toont o.a. Loaded policy name: targeted.
Modi Taak 02
Wissel tussen modi — tijdelijk én permanent
▶

Er zijn twee niveaus: een runtime-switch (geldt tot reboot) en een permanente instelling in een configbestand.

# RUNTIME (tot de volgende reboot) sudo setenforce 0 # → Permissive sudo setenforce 1 # → Enforcing # mag ook met woorden: setenforce Permissive / Enforcing
# PERMANENT (overleeft reboot) — bewerk het configbestand sudo nano /etc/selinux/config
# In /etc/selinux/config (ook bereikbaar als /etc/sysconfig/selinux): SELINUX=enforcing # of: permissive, disabled SELINUXTYPE=targeted
Let op het verschil: setenforce kan enkel tussen enforcing en permissive schakelen — je kan SELinux niet disablen tijdens runtime. Van/naar disabled gaan vereist het configbestand én een reboot, want de kernel moet alle bestanden opnieuw labelen. En: disable nooit in productie — gebruik permissive om te troubleshooten.
✔ Verificatie Na setenforce 0 toont getenforce → Permissive. Zet daarna terug op 1; je laat dit hoofdstuk verder in enforcing draaien.
Deel 2 — Contexten leren lezen
Context Taak 03
Bekijk contexten van bestanden, processen en poorten
▶

Bijna élke SELinux-tool toont contexten met de vlag -Z. Onthoud die letter — ze komt overal terug.

# bestanden ls -Z /var/www/html/ # processen ps -eZ | grep httpd # je eigen gebruikerscontext id -Z # poorten (welke poort hoort bij welk type) sudo semanage port -l | grep http

Een bestand toont bijvoorbeeld:

/var/www/html/index.html unconfined_u:object_r:httpd_sys_content_t:s0

Een proces toont:

system_u:system_r:httpd_t:s0 37154 ? httpd
Focus op het type Van de vier velden (user:role:type:level) draait in de targeted-policy alles om het type (eindigt op _t). De andere drie zijn vooral relevant bij MLS, dat we niet gebruiken. Onthoud: een proces met type httpd_t mag bij een bestand met type httpd_sys_content_t — dat is het hele spel.
✔ Verificatie Je herkent in elke uitvoer het type-veld (eindigt op _t). Webcontent = httpd_sys_content_t, Apache-proces = httpd_t.
Deel 3 — De kern-demo: waarom een verplaatst bestand breekt
Context Taak 04
Schone start: herinstalleer httpd en maak index.html ter plaatse
▶

Om de demo zuiver te houden, vertrekken we van een verse Apache. Configbestanden worden bij herinstallatie niet overschreven, dus verwijderen we ze eerst expliciet.

# schone lei: weg met config + documentroot, dan httpd opnieuw sudo rm -rf /etc/httpd sudo rm -rf /var/www/html sudo dnf remove httpd -y sudo dnf install httpd -y sudo systemctl enable --now httpd

Surf naar http://localhost → je krijgt de standaard Apache-testpagina. Maak nu zelf een index.html rechtstreeks in de webroot:

sudo nano /var/www/html/index.html
<html> <head><title>mogelijkheid1</title></head> <body><h1>mogelijkheid1</h1></body> </html>

Bekijk het label en vergelijk met het proces:

ls -Z /var/www/html/index.html ps -eZ | grep httpd
unconfined_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html system_u:system_r:httpd_t:s0 37154 ? httpd
Waarom werkt dit meteen? Een bestand dat je aanmaakt in /var/www/html erft automatisch het juiste type httpd_sys_content_t — want voor dat pad bestaat er een regel in de file-context-database. Het proces httpd_t mag dat type lezen → pagina verschijnt. Onthoud dit, want in de volgende taak gaat het mis precies omdat we het bestand ergens anders aanmaken.
✔ Verificatie http://localhost toont "mogelijkheid1". Het bestand draagt httpd_sys_content_t.
Context Taak 05
Het breekpunt: maak index.html in je home en verplaats het
▶

Verwijder het werkende bestand. Maak nu een nieuw index.html in je home directory en verplaats het naar de webroot.

sudo rm /var/www/html/index.html # aanmaken in home (NIET in de webroot) nano ~/index.html
<html> <head><title>mogelijkheid2</title></head> <body><h1>mogelijkheid2</h1></body> </html>

Bekijk eerst het label in je home, en verplaats dan:

ls -Z ~/index.html # → unconfined_u:object_r:user_home_t:s0 index.html sudo mv ~/index.html /var/www/html/

Surf naar http://localhost → het werkt niet. Kijk waarom:

ls -Z /var/www/html/index.html
unconfined_u:object_r:user_home_t:s0 /var/www/html/index.html
Waarom breekt mv het — en cp niet? Bij mv blijft het bestand fysiek hetzelfde inode; het label reist mee. Het bestand staat nu wel in de webroot maar draagt nog steeds user_home_t uit je home. Het proces httpd_t heeft geen allow-regel om user_home_t te lezen → geblokkeerd. Had je cp gebruikt, dan kreeg de nieuwe kopie het type van de doelmap (httpd_sys_content_t) en had het wél gewerkt. Dit is dé klassieke SELinux-valkuil.
Verraderlijk: de gewone Unix-rechten (ls -l) zien er perfect uit. Je kan chmod 777 doen tot je een ons weegt — het lost niets op, want het probleem zit in een andere laag: SELinux.
✔ Verificatie http://localhost faalt, en ls -Z toont user_home_t i.p.v. httpd_sys_content_t. Het probleem is nu zichtbaar gemaakt — in Deel 4 lossen we het op.
Deel 4 — Contexten herstellen: chcon vs semanage
Context Taak 06
Tijdelijke fix met chcon (en waarom het niet blijft plakken)
▶

chcon (change context) zet handmatig een type op een bestand. Snel, maar niet persistent: een herlabeling met restorecon of soms gewoon een reboot overschrijft het weer.

# -t wijzigt het TYPE-deel van de context sudo chcon -t httpd_sys_content_t /var/www/html/index.html # controle + test in de browser ls -Z /var/www/html/index.html
De vier chcon-opties
  • -u — wijzig het user-deel
  • -r — wijzig het role-deel
  • -t — wijzig het type-deel (verreweg het meest gebruikt)
  • -l — wijzig het level-deel (MLS)
  • -R — recursief (op een hele directory)
Waarom dit niet de juiste oplossing is: chcon verandert enkel het huidige label, niet de regel in de database. Draait er ooit een restorecon (handmatig, via een opstartscript, of na een volledige relabel), dan valt je bestand terug op het databasetype — en als dat niet klopt, is je fix weg. Gebruik chcon dus enkel voor snelle tests; voor de echte oplossing → Taak 07.
✔ Verificatie Na chcon toont ls -Z weer httpd_sys_content_t en werkt http://localhost. (Maar het is "fragiel" — daarom Taak 07.)
Context Taak 07
Permanente fix met semanage fcontext + restorecon
▶

De juiste manier bestaat uit twee stappen: (1) een regel toevoegen aan de file-context-database met semanage, en (2) die regel toepassen op de bestaande bestanden met restorecon.

# het pad /var/www/html heeft al een standaardregel in de database, # dus voor DIT pad volstaat restorecon om het label te herstellen: sudo restorecon -Rv /var/www/html/
Relabeled /var/www/html/index.html from unconfined_u:object_r:user_home_t:s0 to unconfined_u:object_r:httpd_sys_content_t:s0

Voor een eigen pad (dat nog geen regel heeft) voeg je die eerst toe:

# 1. regel toevoegen aan de database (de (/.*)? = "map én alles eronder") sudo semanage fcontext -a -t httpd_sys_content_t "/web(/.*)?" # 2. regel toepassen op de echte bestanden sudo restorecon -Rv /web/ # custom regels bekijken / verwijderen sudo semanage fcontext -l -C sudo semanage fcontext -d "/web(/.*)?"
semanage schrijft de regel, restorecon past hem toe Dit is hét punt dat studenten verwarren. semanage fcontext -a voegt enkel een regel toe ("alles onder dit pad hoort type X te zijn") aan de database. De bestanden die er nu al staan veranderen daar niet door. Pas restorecon leest die database en zet het juiste label op de echte bestanden. Vergeet je restorecon, dan lijkt je fix niets te doen.
ℹ De database op schijf: je eigen regels belanden in /etc/selinux/targeted/contexts/files/file_contexts.local. Open je dat bestand, dan zie je je aanpassingen uit de vorige hoofdstukken terug, bijvoorbeeld /srv/shares(/.*)? ... samba_share_t:s0 en /var/www/html(/.*)? ... httpd_sys_content_t:s0.
✔ Verificatie Na restorecon draagt het bestand weer httpd_sys_content_t en blijft dat zo, óók na een reboot of latere relabel. http://localhost toont "mogelijkheid2".
Deel 5 — Booleans & poorten
Boolean Taak 08
Booleans: regels aan/uit zetten zonder de policy te herschrijven
▶

Soms is een type correct, maar verbiedt de policy een hele categorie gedrag — bijvoorbeeld "mag Apache het netwerk op?" of "mag Apache in home-directories lezen?". Daarvoor bestaan booleans: kant-en-klare aan/uit-schakelaars die de policy-makers hebben voorzien.

# alle booleans (heel veel!) — meestal grep je gericht sudo getsebool -a | grep httpd # één specifieke checken getsebool httpd_can_network_connect
# tijdelijk aanzetten (verdwijnt na reboot) sudo setsebool httpd_enable_homedirs on # PERMANENT aanzetten — let op de -P ! sudo setsebool -P httpd_enable_homedirs on # welke booleans heb ik zelf gewijzigd? sudo semanage boolean -l -C
De -P niet vergeten: zonder -P geldt de boolean enkel tot de volgende reboot. Je dienst werkt dan vandaag, maar na een herstart faalt hij plots — en dat is een vervelende bug om te vinden. -P = persistent.
Veelgebruikte httpd-booleans
  • httpd_can_network_connect — Apache mag uitgaande netwerkverbindingen maken (APIs, …)
  • httpd_can_network_connect_db — specifiek naar databases
  • httpd_enable_homedirs — lezen in ~/public_html (userdir)
  • httpd_can_sendmail — mails versturen
  • httpd_use_cifs / httpd_use_nfs — content op een netwerkshare serveren
✔ Verificatie getsebool httpd_enable_homedirs → on. semanage boolean -l -C lijst je gewijzigde booleans op.
Poort Taak 09
Een dienst op een niet-standaard poort toelaten
▶

SELinux labelt ook poorten. Apache mag standaard op 80/443 luisteren omdat die poorten type http_port_t dragen. Wil je Apache op bv. poort 8080 draaien, dan moet je die poort eerst aan dat type koppelen — anders weigert SELinux de bind.

# welke poorten horen al bij http? sudo semanage port -l | grep http_port_t # voeg 8080 toe aan het http-type sudo semanage port -a -t http_port_t -p tcp 8080 # controle sudo semanage port -l | grep 8080
-a / -m / -d semanage port -a voegt toe, -m wijzigt een bestaande, -d verwijdert. Veelgebruikte poort-types: http_port_t (80, 443, 8008, 8443, …), ssh_port_t (22), dns_port_t (53), mysqld_port_t (3306).
ℹ Drie dingen voor een non-standaard poort: (1) de SELinux-poortlabel (hierboven), (2) Listen 8080 in de Apache-config, en (3) de firewall openzetten (firewall-cmd --add-port=8080/tcp). Vergeet je de SELinux-stap, dan start httpd niet en zie je in de log "permission denied" op de poort — heel verwarrend als je niet aan SELinux denkt.
✔ Verificatie semanage port -l | grep 8080 toont http_port_t tcp 8080, ....
Deel 6 — De stille fout opsporen
Debug Taak 10
Maak een stille blokkering en vind ze in de logs
▶

Zet bewust een fout label met chcon om een stille blokkering na te bootsen — dit type fout (var_t) geeft géén "Forbidden" in de browser, hij hangt gewoon.

sudo chcon -t var_t /var/www/html/index.html ls -Z /var/www/html/index.html # → ...:var_t:s0 — Apache mag dit type niet lezen

Stap 1 — kijk eerst in de service-log van httpd zelf:

sudo tail /var/log/httpd/error_log
[core:error] (13)Permission denied: AH00132: file permissions deny server access: /var/www/html/index.html

De httpd-log zegt "permission denied" maar wijst naar de bestandsrechten — dat is een valstrik. Je past de chmod aan en… het werkt nog steeds niet, want het echte probleem is SELinux.

Stap 2 — kijk in het SELinux-auditlog (élke geblokkeerde actie staat hier):

sudo ausearch -m avc -ts recent
type=AVC avc: denied { getattr } for pid=3597 comm="httpd" path="/var/www/html/index.html" scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:var_t:s0 tclass=file permissive=0
Een AVC-denial lezen
  • denied { getattr } — welke actie geweigerd werd (hier: bestandsattributen opvragen)
  • comm="httpd" — welk programma het probeerde
  • scontext … httpd_t — de source: het proces-type
  • tcontext … var_t — de target: het bestands-type (hier het probleem!)
  • permissive=0 — stond in enforcing, dus écht geblokkeerd
Conclusie in één zin: "httpd_t mocht geen getattr doen op een bestand met type var_t." De fix: het juiste type terugzetten.
✔ Verificatie Je vindt in ausearch -m avc -ts recent een regel met denied, comm="httpd" en tcontext=...var_t.
Debug Taak 11
sealert: laat SELinux je de oplossing aanwijzen
▶

AVC-regels lezen is leerzaam maar traag. De tool sealert (uit setroubleshoot) analyseert de denials en stelt concrete oplossingen voor — vaak letterlijk het commando dat je moet uitvoeren.

# installeer de troubleshooter sudo dnf install setroubleshoot-server -y # analyseer alle denials in het auditlog sudo sealert -a /var/log/audit/audit.log
SELinux belet /usr/sbin/httpd getattr toegang op /var/www/html/index.html. ***** Plugin restorecon (94.8 vertrouwen) suggereert *************** Als je het label wilt repareren: Het standaard label moet httpd_sys_content_t zijn. Doe: # /sbin/restorecon -v /var/www/html/index.html

Voer de groene/aanbevolen suggestie uit — hier restorecon:

sudo restorecon -v /var/www/html/index.html
Relabeled /var/www/html/index.html from ...:var_t:s0 to ...:httpd_sys_content_t:s0
GUI of CLI In GNOME krijg je na het vernieuwen van de pagina ook een grafische SELinux-melding (klik door naar de details). De inhoud is identiek aan sealert op de CLI. sealert geeft meestal meerdere suggesties — de eerste (groen, hoogste "vertrouwen") is bijna altijd de juiste. De andere twee proberen het gedrag aan te passen i.p.v. het label te herstellen; doe dat liever niet.
Wees kritisch met sealert-suggesties: de tool stelt soms voor om met audit2allow een nieuwe policy-regel te genereren (zie Taak 12). Dat lost het symptoom op maar verzwakt mogelijk je beveiliging. Kies bijna altijd voor restorecon of een boolean boven een eigen policy-module.
✔ Verificatie Na de suggestie uit te voeren werkt http://localhost weer en draagt het bestand httpd_sys_content_t.
Debug Taak 12
De systematische workflow (+ audit2allow als laatste redmiddel)
▶

De vaste volgorde die je bij élk "werkt niet"-probleem afloopt om te bepalen óf en hoe SELinux betrokken is:

# 1. staat SELinux aan? getenforce # 2. zet tijdelijk permissive en test je dienst opnieuw sudo setenforce 0 # → werkt het nu plots? dan WAS SELinux de boosdoener # 3. zet meteen terug op enforcing (laat het niet uit staan!) sudo setenforce 1 # 4. bekijk de denials sudo ausearch -m avc -ts recent # 5. vraag sealert om een suggestie sudo sealert -a /var/log/audit/audit.log # 6. fix volgens de suggestie: restorecon / setsebool -P / semanage port
Beslisboom in woorden Werkt de dienst niet → permissive zetten en testen. Werkt het dan wel → SELinux was het, ga naar de logs. Werkt het nog steeds niet → het is iets anders (DAC-rechten, firewall, config). Zo sluit je in 30 seconden SELinux in of uit als oorzaak.

Als geen enkele bestaande boolean of context past, kan je als laatste redmiddel een eigen policy-module genereren uit de denials met audit2allow:

# bekijk welke regel nodig zou zijn sudo ausearch -m avc -ts recent | audit2allow # genereer een policy-module + installeer ze sudo ausearch -m avc -ts recent | audit2allow -M mijnpolicy sudo semodule -i mijnpolicy.pp # geïnstalleerde modules bekijken sudo semodule -l
audit2allow is geen gratis "fix": het maakt een regel die exact toelaat wat geweigerd werd — ook als die weigering terecht was (bv. een echte inbraakpoging). Gebruik het alleen als je begrijpt waarom de toegang legitiem is, en als context-/boolean-oplossingen écht niet bestaan. In 95% van de gevallen is restorecon of een boolean de juiste weg.
✔ Verificatie Je kan de hele keten getenforce → setenforce 0 → test → setenforce 1 → ausearch → sealert → fix uit het hoofd opnoemen. Dat is exact wat op het examen gevraagd wordt.
Deel 7 — Examenoefeningen (zelf doen)
Exam Taak 13
Oefeningen 1–3: context lezen, homedirs permanent, mail
▶

Oefening 1. Maak een bestand test.html in je homedirectory. Pas de context van dit bestand aan zodat httpd het kan lezen.

Dit vraagt een tijdelijke context-wijziging op één bestand → chcon -t. Welk type heeft webcontent ook alweer? (zie Taak 6). Let op: het bestand moet ook door httpd bereikbaar zijn — een bestand diep in je home is dat door de map-rechten vaak niet, dus test het door het te serveren vanuit een pad dat httpd mag betreden, of focus puur op de context-wijziging zoals de oefening vraagt.
touch ~/test.html ls -Z ~/test.html # → ...:user_home_t:s0 (default voor home) # context tijdelijk naar webcontent-type zetten: sudo chcon -t httpd_sys_content_t ~/test.html ls -Z ~/test.html # → ...:httpd_sys_content_t:s0

De oefening vraagt expliciet het aanpassen van de context van dat ene bestand — dat is precies wat chcon -t doet. (Wil je het ook echt door Apache laten serveren, dan komt daar het home-directory-vraagstuk bij kijken — dat is net Oefening 2.)

Oefening 2. Pas SELinux zo aan dat httpd bestanden uit je homedirectory permanent kan lezen.

"Permanent" + "homedirectory" + "httpd" → dit is geen context-kwestie maar een boolean. Welke boolean ging ook weer over Apache en home-directories? En welke vlag maakt een boolean blijvend?

Dit is een boolean, geen context. De boolean httpd_enable_homedirs laat Apache in home-directories lezen; -P maakt het permanent:

sudo setsebool -P httpd_enable_homedirs on # controle getsebool httpd_enable_homedirs # → httpd_enable_homedirs --> on

Het verschil met Oef 1: daar herstelde je het label van één bestand; hier zet je een algemene regel aan die toelaat dat httpd_t de hele categorie home-content benadert. Voor een werkende userdir-opstelling combineer je dit doorgaans met httpd_sys_content_t op ~/public_html.

Oefening 3. Zorg ervoor dat httpd mails kan versturen.

Opnieuw een boolean. Zoek met getsebool -a | grep httpd | grep mail naar de juiste naam.
# de juiste boolean vinden getsebool -a | grep httpd_can_sendmail # permanent aanzetten sudo setsebool -P httpd_can_sendmail on

Veel webapplicaties (contactformulieren, wachtwoord-resets) sturen mail. SELinux blokkeert dat standaard omdat een webserver die plots mail verstuurt verdacht is — vandaar een aparte boolean om het bewust toe te laten.

Exam Taak 14
Oefeningen 4–6: rw-content, loggende modus, alles terug enforcing
▶

Oefening 4. Je hebt een website waarbij de directory /var/www/html/platform lees-/schrijfrechten nodig heeft. Hoe wijzig je SELinux zodat die map read-write is?

Normale webcontent is read-only (httpd_sys_content_t). Voor schrijfbare content bestaat een apart type dat eindigt op ..._rw_content_t. Permanent instellen = semanage fcontext + restorecon.

Schrijfbare webcontent krijgt het type httpd_sys_rw_content_t (i.p.v. het read-only httpd_sys_content_t). Permanent via semanage + restorecon:

# 1. regel toevoegen voor de map én alles eronder sudo semanage fcontext -a -t httpd_sys_rw_content_t "/var/www/html/platform(/.*)?" # 2. toepassen op de bestaande bestanden sudo restorecon -Rv /var/www/html/platform/ # controle ls -Zd /var/www/html/platform # → ...:httpd_sys_rw_content_t:s0

Nu mag het httpd_t-proces in die map zowel lezen als schrijven (uploads, caches, …), terwijl de rest van de site read-only blijft. Dat is precies de bedoeling: enkel waar nodig schrijfrecht, nergens anders.

Oefening 5. Je wil SELinux alleen in loggende modus gebruiken. Hoe stel je dit in?

"Loggen maar niet blokkeren" = permissive. Tijdelijk met setenforce, permanent in het configbestand. De oefening vraagt om alleen loggen, dus denk aan de permanente variant.

Loggende modus = permissive: overtredingen worden wél gelogd maar niet geblokkeerd.

# tijdelijk (tot reboot) sudo setenforce 0 # permanent: in het configbestand sudo nano /etc/selinux/config
SELINUX=permissive

Controleer met getenforce → Permissive. Dit is dé manier om te troubleshooten: je ziet alle zou-geblokkeerde acties in audit.log verschijnen zonder dat je diensten effectief stilvallen. Voor productie zet je daarna terug op enforcing.

Oefening 6. Zorg dat in álle oefeningen van de vorige hoofdstukken (waar je SELinux mocht uitschakelen) nu alles werkt mét SELinux aan.

Loop per hoofdstuk de diensten af: Apache (LAMP/CMS in subdirs), Samba (de shares en homes). Voor elk: setenforce 1, dan dienst testen, dan denials in ausearch bekijken en fixen met de juiste context (semanage fcontext+restorecon) of boolean. De Samba-shares hebben type samba_share_t nodig; de homes de boolean samba_enable_home_dirs.

Dit is een opruim-oefening over alle vorige hoofdstukken. Zet eerst overal enforcing aan, en fix dan per dienst.

sudo setenforce 1 # en permanent in /etc/selinux/config: SELINUX=enforcing

LAMP / CMS in subdirectories (Drupal/Joomla/WordPress, Nextcloud):

# webcontent read-only, uploads/data read-write sudo semanage fcontext -a -t httpd_sys_content_t "/var/www/html(/.*)?" sudo semanage fcontext -a -t httpd_sys_rw_content_t "/var/www/nextcloud/data(/.*)?" sudo restorecon -Rv /var/www/ # Nextcloud praat met de DB en het netwerk: sudo setsebool -P httpd_can_network_connect on sudo setsebool -P httpd_can_network_connect_db on

Samba (shares uit het vorige hoofdstuk):

# het juiste type op de share-mappen sudo semanage fcontext -a -t samba_share_t "/srv/shares(/.*)?" sudo restorecon -Rv /srv/shares/ # de [homes]-share werkend krijgen sudo setsebool -P samba_enable_home_dirs on

Werkwijze per dienst, als iets blijft falen: setenforce 0 → testen → werkt het? → setenforce 1 → ausearch -m avc -ts recent → sealert -a /var/log/audit/audit.log → fix volgens suggestie. Herhaal tot elke dienst draait met SELinux enforcing. Dat is meteen ook de samenvatting van dit hele hoofdstuk.
