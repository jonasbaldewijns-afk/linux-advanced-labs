Containers met Podman

Het laatste hoofdstuk. Tot nu toe installeerde je diensten direct op je server: Apache, MariaDB, Samba, … In dit hoofdstuk leer je een radicaal andere manier: applicaties in containers draaien. Eén kernel, gedeeld; één image, herhaalbaar; seconden om op te starten. Je leert eerst waarom dit zo'n revolutie was (van fysieke servers → VM's → containers), en daarna werk je praktisch met Podman — de Red Hat-vriendelijke, daemonless container-engine die bijna identiek is aan Docker.

📋 Scenario

Je bedrijf wil de nieuwe webapplicatie niet meer "klassiek" uitrollen — geen dnf install, geen handmatige config, geen "het werkte op mijn machine"-debacles. In plaats daarvan: één container-image die je dev-team test, jij deployt op productie, en als hij draait op je laptop, draait hij overal. Je begint met een kant-en-klare nginx, bouwt dan zelf een eigen image, en eindigt met geavanceerde scenario's: pods, persistente data, rootless containers, en integratie met systemd. Werk op ServerXX.

Deel 1 — Concepten
Concept Taak 01
VM vs container: wat delen ze, wat niet?
▶

De grafiek hierboven toont de stack visueel. De échte sleutel zit in welke laag wordt gedeeld.

Wat is hetzelfde, wat is anders?
  • VM: elke VM heeft een volledig eigen OS (Linux of Windows), inclusief kernel, drivers, services. De hypervisor (VMware, KVM, Hyper-V) verdeelt de hardware. Zware isolatie maar veel overhead.
  • Container: alle containers delen de kernel van het host-OS. Een container bevat enkel de app + zijn libraries — geen kernel, geen init-systeem, geen gebruikers. Lichte isolatie, minimale overhead.
ℹ Praktisch betekent dat:
  • Opstart: VM = minuten (boot OS). Container = seconden (kernel draait al).
  • Schijfgebruik: VM = GB's per OS. Container = MB's per image.
  • Geheugen: VM = fixed RAM per OS. Container = enkel wat de app gebruikt.
  • Beperking: een Linux-container draait niet op een Windows-host (zonder VM ertussen) — kernel-share betekent kernel-compatibiliteit.
Containers ≠ vervangers van VM's. Voor strikte isolatie (verschillende klanten op dezelfde fysieke server), legacy-systemen, of niet-Linux workloads blijven VM's nodig. In moderne stacks zie je vaak VM's mét containers erin: VM voor isolatie, containers voor flexibele deployment.

Concept Taak 02
Docker vs Podman: waarom Red Hat een eigen tool maakte
▶

Docker startte rond 2013 en werd de standaard voor containers. CLI, image-formaat, Dockerfile — Docker bepaalde de conventies. Red Hat besloot een eigen, technisch betere implementatie te maken die met dezelfde conventies werkt: Podman.

De vier kernverschillen
  • Daemonless — Docker draait een centrale daemon (dockerd) als root die alles uitvoert. Crasht de daemon = al je containers stoppen. Podman heeft géén daemon: elk podman-commando is een gewoon proces. Geen single point of failure.
  • Rootless — Podman-containers kunnen draaien als gewone gebruiker. Docker vereist root (of een sudo-loze docker-groep, wat zelf een security-risico is). Voor een multi-user server is rootless een grote winst.
  • Pods — Podman ondersteunt pods: groepen containers die netwerk delen, geïnspireerd op Kubernetes. Docker kent dit concept niet native.
  • systemd-integratie — Podman kan containers exporteren als systemd-services (podman generate systemd), zodat ze automatisch starten bij boot. Geen extra orchestrator nodig voor simpele setups.
ℹ Wat blijft hetzelfde?
  • De CLI: podman run, podman ps, podman pull, … bijna identiek aan Docker. Tip: alias docker=podman en je oude Docker-tutorials werken meestal direct.
  • Image-formaat: Podman pulled gewoon images van docker.io en andere registries.
  • Dockerfile-syntaxis: FROM, RUN, CMD, … allemaal identiek.
✔ Verificatie Je kan in eigen woorden uitleggen waarom Podman daemonless en rootless veiligheidsvoordelen biedt boven Docker.
Deel 2 — Eerste container: nginx
Podman Taak 03
Installeer Podman + pull je eerste image
▶

Op RHEL 10 zit Podman vaak al in de container-tools. Installeer indien nodig, en haal de officiële nginx-image binnen.

# installeren (of bevestigen dat het er al staat) sudo dnf install podman -y # versie controleren podman --version # de nginx-image downloaden van docker.io podman pull nginx
Resolved "nginx" as an alias (/etc/containers/registries.conf.d/000-shortnames.conf) Trying to pull docker.io/library/nginx:latest... Getting image source signatures Copying blob ... Copying config ... Writing manifest to image destination 07eaf1bfc326ae6184ecd982734e5986962c5e460c1fbe4387d68dfaac2488ef
# welke images heb ik lokaal? podman images
REPOSITORY TAG IMAGE ID CREATED SIZE docker.io/library/nginx latest 07eaf1bfc326 3 days ago 192 MB
Wat is een image precies? Een image is een vooraf verpakte applicatie + alles wat nodig is om hem te draaien (libs, config, eventueel een mini-OS-laag). Een image is read-only en herhaalbaar: pull dezelfde tag op tien servers en je krijgt exact dezelfde bytes. Een container is een lopende instantie van een image — je kan honderden containers draaien op één image.
ℹ Registry shortnames: podman pull nginx resolved naar docker.io/library/nginx:latest. De alias-tabel staat in /etc/containers/registries.conf.d/000-shortnames.conf. Voor productie pull je beter expliciet (podman pull docker.io/library/nginx:1.27): tag latest kan morgen iets anders zijn dan vandaag.
✔ Verificatie podman images toont een entry voor nginx. podman --version toont een versie zoals podman version 5.x.x.
Podman Taak 04
Start de container: -d, --name, -p
▶

Nu draait de image als container. De container krijgt zijn eigen netwerk-interface; je moet expliciet zeggen welke containerpoort je naar buiten wil publiceren op de host.

podman run -d --name web -p 8080:80 nginx
De drie vlaggen, ontleed
  • -d (detached) — start op de achtergrond. Zonder -d blijft je shell hangen aan de container-output.
  • --name web — een herkenbare naam. Anders krijg je auto-gegenereerde namen zoals amused_einstein. De naam gebruik je voor start/stop/logs/rm.
  • -p 8080:80 — port mapping. Host-poort 8080 → container-poort 80. De volgorde is HOST:CONTAINER — verkeerd om en niets werkt.
# draaiende containers podman ps # ook gestopte tonen podman ps -a # test in een browser of met curl curl http://localhost:8080
CONTAINER ID IMAGE COMMAND STATUS PORTS NAMES 07eaf1bfc326 docker.io/library/nginx:latest nginx -g daemon o... Up 30 seconds 0.0.0.0:8080->80/tcp web
ℹ Waarom een aparte poort? De container denkt dat hij op poort 80 luistert (en dat klopt — binnen z'n eigen netwerk-namespace). Maar op de host is poort 80 misschien al gebruikt door iets anders, of je wil niet als root draaien (rootless gebruikers mogen geen poorten <1024). Met -p 8080:80 los je beide op: extern bind je aan 8080, intern blijft alles 80.
Firewall & SELinux: krijg je vanaf clientXX geen verbinding op poort 8080? Dan blokkeert je firewall hem nog: sudo firewall-cmd --add-port=8080/tcp --permanent && sudo firewall-cmd --reload. Of als je nftables gebruikt, voeg de overeenkomstige regel toe (zie firewall-hoofdstuk).
✔ Verificatie curl http://localhost:8080 geeft de nginx welkomspagina. podman ps toont je container als Up.

▶

De vier states

# container stoppen (mag op naam of ID) podman stop web # de webpagina is nu onbereikbaar — maar de container BESTAAT nog podman ps # leeg podman ps -a # toont 'Exited' # weer aanzetten — geen 'run' nodig, dezelfde naam volstaat podman start web # logs bekijken (alles wat naar stdout/stderr ging) podman logs web podman logs -f web # live volgen, zoals tail -f # definitief weg (proces stoppen + container verwijderen in één) podman rm -f web
Stop vs rm — twee verschillende dingen podman stop stopt het proces maar bewaart de container (filesysteem, config, logs). Je kan hem later weer starten met dezelfde naam. podman rm verwijdert de container volledig — alle data binnen de container is dan weg (tenzij je een volume gebruikte, zie de bind-mount-oefening straks). De image die je pulled blijft sowieso staan.
ℹ Veel-gebruikte beheercommando's:
  • podman inspect web — alle details van de container in JSON (IP, mounts, environment, ...).
  • podman exec -it web bash — binnenstappen in een draaiende container, handig om te debuggen.
  • podman stats — live CPU/RAM/net-gebruik per container.
  • podman rmi nginx — verwijder een image (kan niet als er nog containers van bestaan).
✔ Verificatie Je kan de container stoppen, starten en verwijderen. podman logs web toont nginx access-logs. podman exec -it web sh geeft je een shell binnen de container.
Deel 3 — Bouw je eigen image
Image Taak 06
Schrijf een Containerfile en bouw je eigen "Hello, World"
▶

Tot nu toe gebruikte je een kant-en-klare image. Nu maak je er één zelf met een Containerfile (Podman-naam) of Dockerfile (Docker-naam) — beide bestanden hebben dezelfde syntaxis en Podman accepteert beide.

mkdir ~/hallo && cd ~/hallo nano Containerfile
# Gebruik een officiële Fedora image als basis FROM fedora:latest # Werkdirectory binnen de container WORKDIR /app # Wat moet er gebeuren wanneer de container start? CMD ["/bin/bash", "-lc", "echo Hello, World"]
# bouwen — let op de . op het einde (= "kijk in deze directory") podman build -t hallo-test . # Containerfile heet niet 'Dockerfile'? Geef expliciet mee met -f: podman build -f Containerfile -t hallo-test . # controle: image staat in je lokale registry podman images | grep hallo-test # draai een container ervan podman run --rm hallo-test
Hello, World
De drie meest gebruikte instructies
  • FROM — start vanaf een bestaande image als basis. Bijna élke image begint met FROM (anders zou je een eigen kernel-laag moeten meebrengen).
  • WORKDIR — zet de werkdirectory voor alle volgende instructies. Vergelijkbaar met cd.
  • CMD — wat draait er bij het starten van de container? Vorm ["binary", "arg1", "arg2"] (JSON-array) is de aanbevolen vorm.
Andere veel gebruikte: RUN (voer commando uit tijdens build, b.v. RUN dnf install -y httpd), COPY (kopieer bestanden vanaf de buildcontext in de image), EXPOSE (documenteer welke poort de app gebruikt), ENV (omgevingsvariabelen).
ℹ Wat is --rm? Verwijdert de container automatisch zodra hij stopt. Bij een one-shot-commando zoals echo Hello, World is dat handig — anders blijft elke run een gestopte container achter die je later moet opruimen.
ℹ Lagen (layers): elke instructie in je Containerfile maakt een nieuwe laag in de image. Lagen worden gecachet: wijzig je enkel de laatste regel, dan hergebruikt Podman alle vorige lagen. Daarom zet je instructies die weinig veranderen bovenaan (FROM, RUN dnf install), en vaak wijzigende dingen onderaan (COPY ./mycode/). Scheelt minuten bij elke rebuild.
✔ Verificatie podman images | grep hallo-test toont je nieuwe image. podman run --rm hallo-test print Hello, World en stopt.
Deel 4 — Oefeningen tier 1 (standaard)
Tier 1 Taak 07
Oefeningen 1–3: lifecycle, bind mount, rootless
▶

Oef 1. Herstart de nginx-container uit Deel 2. Bekijk status + logs. Stop en verwijder hem volledig. Herstart vanaf scratch. Maak screenshots van podman images voor/na.

# 1. status: draait hij nog? podman ps -a podman logs web # 2. volledig wegvegen podman rm -f web # -f = force: stopt + verwijdert in één commando # 3. controleer dat hij weg is (maar de IMAGE moet nog bestaan) podman ps -a # container weg podman images # image staat er nog # 4. opnieuw vanaf scratch podman run -d --name web -p 8080:80 nginx curl http://localhost:8080

Sleutel: podman rm verwijdert de container, niet de image. De image blijft lokaal staan, dus de tweede podman run hoeft niets opnieuw te downloaden — je ziet hetzelfde aantal images voor en na, maar verschillende container-ID's.

Oef 2. Maak /tmp/mypage aan met een eigen index.html. Start nginx met dat als bind-mount op /usr/share/nginx/html. Test in de browser, wijzig index.html → de wijziging is direct zichtbaar. Extra: laat het werken met SELinux aan.

Bind mount in podman = -v HOST_PAD:CONTAINER_PAD:OPTIES. Voor read-only voeg je :ro toe. Voor SELinux-compatibel: gebruik de speciale optie :Z (hoofdletter) — dat relabelt automatisch de host-bestanden naar het container-context.

1. Bereid de host-directory voor:

mkdir -p /tmp/mypage echo "<h1>Mijn eigen pagina!</h1>" > /tmp/mypage/index.html

2. Met SELinux uit (snel testen):

sudo setenforce 0 # SELinux tijdelijk permissive # oude container weg podman rm -f web 2>/dev/null # start met bind mount, read-only podman run -d --name web -p 8080:80 \ -v /tmp/mypage:/usr/share/nginx/html:ro \ nginx curl http://localhost:8080 # <h1>Mijn eigen pagina!</h1> # wijzig het bestand op de host → direct zichtbaar echo "<h1>Update!</h1>" > /tmp/mypage/index.html curl http://localhost:8080

3. Mét SELinux aan — de juiste oplossing (en wat het examen verwacht): gebruik de :Z-optie. Die zet automatisch het SELinux-type container_file_t op je host-directory, zodat het container-proces (container_t) er bij kan.

sudo setenforce 1 podman rm -f web # let op de hoofdletter Z aan het eind! podman run -d --name web -p 8080:80 \ -v /tmp/mypage:/usr/share/nginx/html:ro,Z \ nginx curl http://localhost:8080 # werkt, zonder SELinux uit te zetten
ℹ Het verschil tussen :z en :Z: kleine z = shared label (meerdere containers mogen erbij). Grote Z = private label (enkel deze ene container). Voor enkele containers met eigen data: Z. Voor een gedeelde docs-map die meerdere containers lezen: z.

Oef 3. Start dezelfde nginx-container als non-root gebruiker op poort 8081. Vergelijk met de root-versie. Wat zijn de voordelen?

Geen sudo meer — gewoon als jezelf podman run … doen. Belangrijke beperking: rootless gebruikers mogen geen privileged poorten (<1024) binden. 8081 is >1024 dus ok. podman info | grep -i rootless bevestigt dat je rootless draait.
# als gewone gebruiker (NIET met sudo) podman run -d --name rootless-nginx -p 8081:80 nginx # controle: image + container leven nu in JOUW home, niet system-wide podman ps ls ~/.local/share/containers/storage/ # jouw private container-storage curl http://localhost:8081

De voordelen ten opzichte van root-containers:

  • Veiliger — als de container gehackt wordt, krijgt de aanvaller maximaal jouw rechten, niet root. Een container die als root draait + ontsnapt = volledige server.
  • Geen daemon — Docker vereist een root-daemon; Podman heeft die helemaal niet, dus rootless is "gewoon" hoe het werkt.
  • Multi-user — elke gebruiker op de server heeft zijn eigen container-omgeving zonder aan elkaars containers te kunnen.
  • Geen sudo nodig voor dev-werk — handig in CI/CD pipelines en dev-omgevingen.

Beperking: rootless mag geen poorten <1024 binden. Wil je per se poort 80 vanuit een rootless container? Gebruik een reverse proxy op de host (nginx/Caddy) die 80 → 8080 forwardt.

Deel 5 — Oefeningen tier 2 (verkennend)
Tier 2 Taak 08
Oefening 4: pods (meerdere containers, één netwerk)
▶

Oef 4. Maak een pod mystack die op poort 8080 luistert. Voeg nginx eraan toe. Voeg dan een tweede container (bv. busybox sleep). Gebruik podman pod ps. Wat zijn de voordelen van een pod t.o.v. losse containers?

Een pod is een container voor containers — ze delen network namespace en kunnen elkaar bereiken via localhost. Maak eerst de pod (podman pod create), voeg dan containers toe met --pod <naam> i.p.v. -p (de poorten zitten al op het pod-niveau).
# pod aanmaken met poortmapping op pod-niveau podman pod create --name mystack -p 8080:80 # nginx toevoegen aan de pod (geen eigen -p meer!) podman run -d --pod mystack --name web nginx # tweede container: busybox die gewoon slaapt podman run -d --pod mystack --name sidecar \ docker.io/library/busybox sleep infinity # overzicht podman pod ps podman ps --pod # containers gegroepeerd per pod
POD ID NAME STATUS CREATED INFRA ID # OF CONTAINERS abc123... mystack Running 10 seconds ago def456... 3

Drie containers in de pod: de twee die jij maakte (web, sidecar) plus de infra-container die Podman zelf aanmaakt om de gedeelde namespaces vast te houden.

Test de gedeelde netwerk-namespace:

# vanuit de sidecar nginx bereiken via localhost (!) podman exec sidecar wget -qO- http://localhost:80 # → de nginx welkomspagina

Voordelen van pods boven losse containers:

  • Shared networking — containers in dezelfde pod bereiken elkaar via localhost. Geen extern netwerk nodig, simpel en snel.
  • Eén poort-mapping — je publiceert poorten op pod-niveau, niet per container. Mooier als de containers samen "één applicatie" vormen.
  • Atomair beheren — podman pod start/stop/rm mystack doet alles tegelijk.
  • Kubernetes-compatibel — Podman-pods volgen het Kubernetes-podconcept, dus de stap naar K8s is klein.

Typisch gebruik: een webapp + een sidecar die metrics ophaalt, of een app + een log-collector — twee containers die "bij elkaar horen".

Tier 2 Taak 09
Oefeningen 5–6: eigen Apache-image + systemd-integratie
▶

Oef 5. Bouw een image vanaf Fedora, installeer httpd, kopieer een eigen config. Start als container op poort 8082. Test de Apache-pagina. Commit eventuele wijzigingen als nieuwe image.

Containerfile met FROM fedora:latest, RUN dnf install -y httpd, een COPY-instructie voor je eigen index.html of httpd.conf, en als CMD een command dat httpd in de voorgrond draait (containers blijven niet leven zonder voorgrondproces!).

1. Maak een werkdirectory + custom content:

mkdir -p ~/my-apache && cd ~/my-apache echo "<h1>Apache draait in een container</h1>" > index.html nano Containerfile
FROM fedora:latest # installeer httpd en ruim de package-cache op (kleinere image) RUN dnf install -y httpd && dnf clean all # onze eigen index.html in de webroot COPY index.html /var/www/html/index.html # documenteer welke poort de container intern gebruikt EXPOSE 80 # httpd in de VOORGROND draaien — anders stopt de container meteen CMD ["/usr/sbin/httpd", "-D", "FOREGROUND"]

2. Bouw + run:

podman build -t my-apache . podman run -d --name apache -p 8082:80 my-apache curl http://localhost:8082 # <h1>Apache draait in een container</h1>

3. commit — een lopende container "bevriezen" als nieuwe image:

# maak een interactieve wijziging in de container podman exec apache bash -c "echo '<h1>v2</h1>' > /var/www/html/index.html" # commit die wijziging als een nieuwe image podman commit apache my-apache:v2 podman images | grep my-apache # my-apache v2 ... net aangemaakt # my-apache latest ... eerder gebouwd
Commit vs Containerfile: podman commit werkt maar is voor uitzonderingen — het resultaat is een "zwarte doos" zonder reproduceerbaarheid. Voor productie: beschrijf álle wijzigingen in je Containerfile en builden. Anders weet niemand over zes maanden waarom v2 anders is dan latest.

Oef 6. Exporteer de nginx-container als systemd-unit. Enable + start hem. Reboot de host en controleer dat hij automatisch start.

podman generate systemd spuugt een systemd-unit-bestand uit. Schrijf het naar ~/.config/systemd/user/ (voor rootless) of /etc/systemd/system/ (voor root). Voor rootless heb je ook loginctl enable-linger nodig zodat services blijven draaien als je niet ingelogd bent.
# 1. zorg dat de container draait podman run -d --name web -p 8080:80 nginx # 2. genereer systemd-unit en zet hem op de juiste plek mkdir -p ~/.config/systemd/user podman generate systemd --name web --files --new # dat schrijft 'container-web.service' in de huidige map mv container-web.service ~/.config/systemd/user/ # 3. activeer de user-systemd en enable de unit systemctl --user daemon-reload systemctl --user enable --now container-web.service # 4. ZONDER deze stap stoppen je user-services bij logout! sudo loginctl enable-linger $USER # 5. controleer systemctl --user status container-web.service

Test met reboot:

sudo reboot # na reboot, log in en controleer: podman ps curl http://localhost:8080 # nginx welkomspagina werkt zonder dat jij iets startte
De --new-vlag is belangrijk Zonder --new maakt systemd elke keer dezelfde bestaande container opnieuw aan met podman start. Met --new creëert het bij elke service-start een verse container vanaf de image. Voordeel: schoon, geen accumulerende staat. Nadeel: container-specifieke data in de container is weg (wat doorgaans toch al een slecht idee was — gebruik volumes).
ℹ Waarom enable-linger? User-systemd-services stoppen standaard wanneer de user uitlogt. Linger zet "deze user mag services laten draaien zonder login" aan. Voor een container die altijd moet draaien, onmisbaar.
Nieuwer alternatief: in moderne Podman (5.x+) gebruik je liever Quadlet — een speciaal soort systemd-unit (.container-bestand) dat directer werkt dan generate systemd. Maar voor het examen volstaat generate systemd.
Deel 6 — Oefeningen tier 3 (uitdagend)
Tier 3 Taak 10
Oefening 7: eigen registry draaien en images pushen
▶

Oef 7. Bouw een eigen image, tag hem als localhost:5000/mijnimage:v1. Start een registry-container op poort 5000. Push/pull de image. Configureer de registry als insecure in /etc/containers/registries.conf. Test door te pullen vanaf een tweede RHEL-systeem.

Er bestaat een officiële registry:2-image die zelf een Docker registry implementeert. Start hem op poort 5000 met persistente storage. podman tag hernoemt een image; podman push stuurt hem naar een registry. "Insecure" = registry zonder HTTPS — moet je expliciet toelaten in registries.conf.

1. Start een eigen registry op poort 5000:

podman run -d --name registry -p 5000:5000 \ -v /var/lib/registry:/var/lib/registry:Z \ docker.io/library/registry:2

2. Tag een bestaande image voor je eigen registry:

# gebruik bv. de hallo-test image uit Taak 6 podman tag hallo-test localhost:5000/mijnimage:v1 podman images | grep mijnimage # localhost:5000/mijnimage v1 ...

3. Configureer Podman om HTTP-registries te accepteren. Pas /etc/containers/registries.conf aan:

sudo nano /etc/containers/registries.conf
[[registry]] location = "localhost:5000" insecure = true

4. Push de image:

podman push localhost:5000/mijnimage:v1 # controleer dat hij echt in de registry zit (REST-API) curl http://localhost:5000/v2/_catalog # {"repositories":["mijnimage"]}

5. Test pull vanaf een tweede RHEL-systeem. Op die andere machine:

# vervang ServerXX met het IP/naam van je registry-host # pas registries.conf aan om ServerXX:5000 als insecure te markeren sudo nano /etc/containers/registries.conf # [[registry]] # location = "ServerXX:5000" # insecure = true podman pull ServerXX:5000/mijnimage:v1 podman images | grep mijnimage

Vergeet niet: firewall opzetten op de registry-host (firewall-cmd --add-port=5000/tcp --permanent) en als je SELinux aan hebt, eventueel de :Z-vlag op het volume voor de registry-data zoals hierboven al staat.

"Insecure" is enkel voor een lab. In productie zet je een private registry achter HTTPS (eigen certificaat of een echt one), eventueel met basic auth (REGISTRY_AUTH=htpasswd). Een HTTP-registry op een gedeeld netwerk is een gat in je beveiliging.
Tier 3 Taak 11
Oefeningen 8–9: SELinux-denials + custom network met gedeeld volume
▶

Oef 8. Identificeer SELinux-denials bij een rootless nginx met ausearch -m avc -ts recent. Maak een custom policy. Test in een multi-user scenario. Documenteer beperkingen.

Dit bouwt direct op het SELinux-hoofdstuk. Stappen: (1) doe iets wat een denial uitlokt (bv. een bind mount zonder :Z); (2) sudo ausearch -m avc -ts recent om de AVC te vinden; (3) sealert -a /var/log/audit/audit.log voor uitleg + suggestie; (4) als er écht geen boolean of context past, genereer een eigen module met audit2allow.

1. Lok een denial uit (bind mount zonder :Z):

mkdir -p /tmp/web-test echo "<h1>test</h1>" > /tmp/web-test/index.html # NIET :Z — nginx kan het niet lezen wegens SELinux podman run -d --name nginx-denial -p 8083:80 \ -v /tmp/web-test:/usr/share/nginx/html:ro \ nginx curl http://localhost:8083 # → 403 Forbidden of een lege response

2. Zoek de denial:

sudo ausearch -m avc -ts recent # > type=AVC ... denied { read } for ... # > scontext=...:container_t:s0... tcontext=...:user_tmp_t:s0...

container_t (het proces) mag user_tmp_t (de host-map) niet lezen → SELinux-blokkade.

3. Vraag sealert om een oplossing:

sudo dnf install setroubleshoot-server -y sudo sealert -a /var/log/audit/audit.log

De suggesties: ofwel het label van /tmp/web-test aanpassen (chcon -t container_file_t), ofwel een eigen policy maken met audit2allow. De beste oplossing is gewoon de bind mount met :Z doen (Oef 2) — dat is exact waarvoor Podman die optie heeft.

4. Als laatste redmiddel — custom policy via audit2allow:

sudo ausearch -m avc -ts recent | audit2allow -M mynginx sudo semodule -i mynginx.pp # controleer dat de module geladen is sudo semodule -l | grep mynginx

Beperkingen documenteren:

  • audit2allow rubberstempelt élke geweigerde actie — inclusief eventueel kwaadaardige. Gebruik enkel als je weet waarom de toegang legitiem moet zijn.
  • In een multi-user scenario waar verschillende rootless users dezelfde host-map willen delen: liever per gebruiker een eigen mount, of een volume in plaats van een bind mount.
  • De netjes oplossing blijft: :Z (private label) of :z (shared label) bij -v.

Oef 9. Maak een custom network mystacknet. Maak een pod met nginx + alpine, en ping nginx vanaf alpine. Voeg een gedeeld volume toe tussen de containers. Test data-uitwisseling.

Custom network: podman network create. Een Podman-volume (in tegenstelling tot een bind mount): podman volume create, en daarna bij run: -v <volumename>:/pad/in/container. Containers binnen één pod zien elkaar via localhost; tussen aparte containers in hetzelfde custom network gebruik je de container-namen als hostname.

1. Custom network + gedeeld volume aanmaken:

podman network create mystacknet podman volume create shared-data

2. Start nginx en alpine in hetzelfde network, met het gedeelde volume:

# nginx — schrijft naar /shared podman run -d --name web \ --network mystacknet \ -v shared-data:/shared:Z \ -p 8084:80 \ nginx # alpine — leest van /shared, blijft draaien podman run -d --name alpine \ --network mystacknet \ -v shared-data:/shared:Z \ docker.io/library/alpine sleep infinity

3. Test container-naam-resolutie (DNS binnen Podman-networks):

# vanuit alpine ping nginx OP NAAM (geen IP nodig!) podman exec alpine ping -c 3 web # → 64 bytes from web (...): icmp_seq=1 ... # vanuit alpine HTTP-request naar nginx podman exec alpine wget -qO- http://web:80 # → de nginx welkomspagina

4. Test data-uitwisseling via het volume:

# schrijf vanuit alpine podman exec alpine sh -c "echo 'hallo van alpine' > /shared/bericht.txt" # lees vanuit nginx podman exec web cat /shared/bericht.txt # → hallo van alpine # overleeft een herstart (in tegenstelling tot data IN een container) podman restart web alpine podman exec web cat /shared/bericht.txt # → nog steeds: hallo van alpine
Volume vs bind mount — waarom beide bestaan
  • Bind mount (-v /tmp/x:/data) — wijst direct naar een host-pad. Jij beheert het pad. Handig voor dev (snel editen op de host, container ziet de wijziging).
  • Volume (-v shared-data:/data) — Podman beheert de storage in ~/.local/share/containers/storage/volumes/. Schoner voor productie: containers weten niets over host-paden, je kan volumes backupen/migreren als eenheden.
Voor data-uitwisseling tussen containers is een volume duidelijk de juiste keuze.

De belangrijkste les: binnen een custom network werkt DNS automatisch — containers vinden elkaar via hun naam (web, alpine). In het default network werkt dat niet en moet je IP's gebruiken of een pod maken. Vandaar dat custom networks de aanbevolen aanpak zijn voor multi-container setups.
