Firewalls (NFTables) & Proxyservers

Twee onderwerpen die op elkaar voortbouwen. Eerst de firewall: je kent firewalld al uit eerdere hoofdstukken, nu duik je naar de laag eronder — nftables — en schrijf je regels rechtstreeks. Daarna zet je twee soorten proxyservers op: een forward proxy (Squid) die uitgaand clientverkeer filtert en cachet, en een reverse proxy (Nginx) die inkomend verkeer naar interne servers verdeelt. De proxy-helft bouwt rechtstreeks verder op je nftables-firewall.

📋 Scenario

Je server (ServerXX, 10.10.10.1) heeft twee interfaces: ens160 (NAT naar internet) en ens224 (privénet 10.10.10.0/24). De security-audit wil dat je weg stapt van de "alles via firewalld"-aanpak en een strak, expliciet nftables-beleid schrijft: standaard alles droppen, enkel toelaten wat nodig is. Daarna draai je ServerXX uit als gateway met NAT, plaats je een Squid-proxy ervoor om studentenverkeer te filteren, en zet je een Nginx reverse proxy voor je interne webserver. clientXX (10.10.10.10) is je testmachine. Vervang overal XX door je servernummer.

🧱 firewalld vs nftables — frontend & backend

firewalld firewall-cmd — hoog niveau: zones & services. Makkelijk, dynamisch, ideaal voor dagelijks beheer.
↓ vertaalt naar ↓
nftables nft — laag niveau: tables, chains, rules. Direct, maximale controle, opvolger van iptables.
↓ draait in ↓
kernel De effectieve pakketfiltering gebeurt in de Linux-kernel. Beide tools schrijven uiteindelijk hierheen.

Belangrijk: firewalld is gewoon een frontend die nftables aanstuurt. Je kan ze daarom niet tegelijk gebruiken — ze schrijven dezelfde kernel-regels en spreken elkaar tegen.

PART A · Firewall firewalld leren kennen, dan rechtstreeks nftables schrijven
Deel 1 — firewalld opfrissen
firewalld Taak 01
Zones: welk vertrouwensniveau hoort bij welke interface?
▶

Een zone is een vertrouwensniveau dat je aan een interface koppelt. Elke zone heeft eigen regels over wat er binnen mag. Bekijk eerst de huidige situatie.

# welke zones zijn actief, en op welke interface? sudo firewall-cmd --get-active-zones # wat is de standaardzone? sudo firewall-cmd --get-default-zone # alles wat in een zone geldt sudo firewall-cmd --zone=internal --list-all
De interface→zone-logica in dit labo
  • ens160 (NAT → internet) → zone external. Naar buiten gericht, dus weinig vertrouwen + masquerading.
  • ens224 (10.10.10.0/24) → zone internal. Privénet, dus meer diensten toegestaan.
ℹ Trust-niveaus van laag naar hoog: drop (alles weg, zelfs geen ICMP-reply) → block → public → external → internal / home / work → trusted (alles toegestaan). Hoe hoger de zone, hoe meer er standaard binnen mag.
✔ Verificatie --get-active-zones toont je twee interfaces met hun zones. --list-all toont welke services al open staan.
firewalld Taak 02
Services vs poorten + het 5-stappen-plan (en de #1 studentenfout)
▶

Een service in firewalld is een voorgedefinieerde bundel poorten — zo hoef je geen poortnummers te onthouden. http = 80/tcp, samba = 139+445/tcp, enz.

# in plaats van poortnummers: sudo firewall-cmd --zone=internal --add-port=80/tcp --permanent # gewoon de servicenaam: sudo firewall-cmd --zone=internal --add-service=http --permanent sudo firewall-cmd --reload
Het stappenplan bij een nieuwe dienst
  1. Installeer de dienst (dnf install httpd)
  2. Configureer hem
  3. Start hem (systemctl start httpd)
  4. Open de firewall (firewall-cmd --add-service=http --permanent)
  5. Reload + test (firewall-cmd --reload, dan curl)
De #1 fout bij studenten: stap 4 vergeten. Je dienst draait perfect op de server zelf, maar vanaf een andere machine is hij onbereikbaar — omdat de firewall de poort dichthoudt. Tweede klassieker: --permanent vergeten, waardoor je regel na een reboot verdwenen is. Regel: altijd --permanent én --reload.
✔ Verificatie firewall-cmd --zone=internal --list-services bevat http. Vanaf clientXX: curl http://10.10.10.1 werkt.
Deel 2 — Overstap naar nftables
nftables Taak 03
firewalld uit, nftables aan
▶

Omdat beide dezelfde kernel-laag aansturen, kan er maar één tegelijk de baas zijn. Schakel firewalld uit en nftables in.

# nftables installeren (vaak al aanwezig) sudo dnf install nftables -y # firewalld stoppen + permanent uitschakelen sudo systemctl disable --now firewalld # nftables starten + permanent inschakelen sudo systemctl enable --now nftables
Pas op met SSH-sessies: als je via SSH op de server zit en je schakelt firewalls om, kan je jezelf buitensluiten. Werk waar mogelijk via de VM-console, of zorg dat je SSH-regel klaarstaat vóór je een default-drop-beleid activeert (Taak 8).
✔ Verificatie systemctl is-active nftables → active, en systemctl is-active firewalld → inactive.
Structuur Taak 04
De opbouw: ruleset → tables → chains → rules
▶

nftables is hiërarchisch opgebouwd. Begrijp je deze structuur, dan begrijp je alle commando's.

table ip filter ← tabel (familie ip = IPv4, soort = filter) chain INPUT ← keten (hook input = binnenkomend verkeer) ip saddr 10.10.10.10 drop ← regel (match + actie)
# de volledige actieve ruleset opvragen sudo nft list ruleset # in het begin leeg — er staat nog niets in /etc/sysconfig/nftables.conf
De drie niveaus
  • Table — een container per soort werk. filter (pakketfiltering), nat (adresvertaling), mangle (headers wijzigen), raw. Heeft een familie: ip (IPv4), ip6, inet (beide).
  • Chain — een lijst regels, gekoppeld aan een hook in de netwerkstack: input (naar de machine zelf), output (van de machine), forward (erdoorheen gerouteerd).
  • Rule — een match (bv. bron-IP, poort) plus een actie (accept, drop).
ℹ Base chain: een chain die je definieert met { type filter hook input priority 0; policy accept; } hangt rechtstreeks aan het netwerkverkeer. hook input = wordt aangeroepen bij binnenkomend verkeer. priority 0 = volgorde als er meerdere chains op dezelfde hook zitten (lager = eerst). policy accept/drop = wat er gebeurt als géén enkele regel matcht.
✔ Verificatie nft list ruleset geeft (nog) lege of minimale output. Je kan de drie niveaus benoemen.
Deel 3 — Eerste regels: blokkeren & beheren
nftables Taak 05
Bouw een table + chain + blokkeerregel (de ping-demo)
▶

We bouwen stap voor stap: eerst een tabel, dan een base chain met policy accept, dan een regel die ping vanaf clientXX (10.10.10.10) blokkeert.

# 1. tabel aanmaken (familie ip, naam filter) sudo nft add table ip filter # 2. base chain INPUT — standaard alles toelaten sudo nft add chain ip filter INPUT { type filter hook input priority 0\; policy accept\; } # test: vanaf clientXX kan je nu pingen (policy accept) # 3. regel: drop alle pakketten met bron-IP 10.10.10.10 sudo nft add rule ip filter INPUT ip saddr 10.10.10.10 counter drop

Vanaf clientXX lukt pingen nu niet meer — en óók geen SSH of welke verbinding dan ook, want de regel dropt al het verkeer van dat IP. Bekijk de ruleset:

sudo nft list ruleset
table ip filter { chain INPUT { type filter hook input priority filter; policy accept; ip saddr 10.10.10.10 counter packets 104 bytes 8204 drop } }
Wat doet counter? Het counter-sleutelwoord telt hoeveel pakketten en bytes door de regel zijn geraakt. Heel handig om te zien of een regel effectief "vuurt". Je ziet het terug in de output (packets 104 bytes 8204).
Niet persistent! Regels die je met nft add toevoegt leven enkel in het kernelgeheugen en verdwijnen bij reboot. Opslaan doe je door de ruleset naar /etc/sysconfig/nftables.conf te schrijven (volgende taak).
✔ Verificatie Vanaf clientXX: ping 10.10.10.1 krijgt geen antwoord meer. nft list ruleset toont je drop-regel met een oplopende counter.
nftables Taak 06
Opslaan, en beheren met handles (rule/chain/table verwijderen)
▶

Opslaan zodat de regels een reboot overleven:

sudo nft list ruleset | sudo tee /etc/sysconfig/nftables.conf # controleer: cat /etc/sysconfig/nftables.conf

Verwijderen gaat via handles — interne nummers die je met -a zichtbaar maakt:

# toon handles sudo nft -a list ruleset
table ip filter { chain INPUT { # handle 1 type filter hook input priority filter; policy accept; ip saddr 10.10.10.10 counter ... drop # handle 2 } }
# verwijder regel met handle 2 sudo nft delete rule ip filter INPUT handle 2 # of alle regels uit een chain wissen: sudo nft flush chain ip filter INPUT # chain verwijderen (moet leeg zijn!) sudo nft delete chain ip filter INPUT # tabel verwijderen (mag geen chains meer hebben) sudo nft delete table ip filter # nucleaire optie: ALLES wissen sudo nft flush ruleset
Volgorde van afbraak Je kan een chain pas verwijderen als er geen regels meer in staan, en een tabel pas als er geen chains meer in staan. Vandaar de volgorde rule → chain → table. Of gebruik nft flush ruleset om in één klap alles leeg te maken.
✔ Verificatie Na het verwijderen van de drop-regel kan clientXX weer pingen. cat /etc/sysconfig/nftables.conf toont je opgeslagen ruleset.
Deel 4 — Een veilig standaardbeleid bouwen
nftables Taak 07
Default-drop + de twee onmisbare basisregels
▶

Best practice voor een server: standaard alles droppen, en dan gericht toelaten. Begin met een verse tabel en een chain met policy drop.

sudo nft flush ruleset sudo nft add table ip filter sudo nft add chain ip filter INPUT { type filter hook input priority 0\; policy drop\; }

Probeer nu vanaf de server te pingen of te surfen → niets werkt, want álle binnenkomende pakketten worden gedropt, inclusief de antwoorden op verkeer dat je zelf aanvroeg. Voeg de twee onmisbare regels toe:

# 1. laat antwoorden op eigen verbindingen toe (stateful) sudo nft add rule ip filter INPUT ct state established,related accept # 2. laat al het loopback-verkeer toe (lo = interne communicatie) sudo nft add rule ip filter INPUT iif "lo" accept
Waarom deze twee?
  • ct state established,related accept — connection tracking. Wanneer jij iets aanvraagt (bv. een DNS-query of een webpagina), moet het antwoord binnen kunnen. Deze regel laat antwoorden op door jou geopende verbindingen toe, zonder de hele wereld binnen te laten.
  • iif "lo" accept — heel veel diensten praten met zichzelf via 127.0.0.1 (loopback). Je eigen DNS-server, databases, … Zonder deze regel breken interne systeemfuncties. iif = input interface.
ℹ Het DNS-symptoom: zonder de loopback-regel lijkt pingen naar een hostnaam soms tóch te werken (via een externe DNS zoals 8.8.8.8) maar traag, met communications error to 127.0.0.1#53: timed out. Dat komt doordat je eigen DNS op 127.0.0.1 geblokkeerd werd. Na iif "lo" accept gebruikt nslookup weer je eigen DNS (10.10.10.1) en gaat alles vlot.
✔ Verificatie Na beide regels kan je vanaf de server vlot pingen/surfen. nft list ruleset toont policy drop met de twee accept-regels eronder.
nftables Taak 08
Diensten en netwerken toelaten (SSH + subnet)
▶

Bovenop het default-drop beleid laat je gericht toe wat je nodig hebt.

# SSH van buitenaf toelaten (nieuwe + bestaande verbindingen) sudo nft add rule ip filter INPUT tcp dport 22 ct state established,new accept # heel het interne subnet toegang geven tot alle diensten op ServerXX sudo nft add rule ip filter INPUT ip saddr 10.10.10.0/24 counter accept
Match-syntax
  • tcp dport 22 — TCP destination port 22 (= SSH die binnenkomt). dport = destination port, sport = source port.
  • ip saddr 10.10.10.0/24 — source address matcht het hele subnet. daddr zou destination zijn.
  • ct state new — een nieuwe verbinding (eerste pakket). Gecombineerd met established dek je het hele verbindingsverloop.
ℹ Vergelijk met firewalld: waar je vroeger firewall-cmd --add-service=ssh deed, schrijf je nu zelf tcp dport 22 ... accept. Meer typewerk, maar je ziet exact wat er gebeurt — en je kan veel fijnere voorwaarden stellen (per IP, per protocol-state, met rate limits, …).
✔ Verificatie Een SSH-verbinding vanaf buiten lukt. clientXX (in het subnet) kan alle diensten op ServerXX bereiken; een machine buiten 10.10.10.0/24 niet.
nftables Valkuil Taak 09
Rate limiting tegen ping-floods — én de volgorde-valkuil
▶

Tegen een DDoS ping-flood beperk je het aantal ICMP echo-requests dat je accepteert:

sudo nft add rule ip filter INPUT icmp type echo-request limit rate 1/second burst 5 packets accept

Maar test je nu vanaf clientXX, dan kan je nog steeds sneller dan 1/seconde pingen! De rate limit lijkt niet te werken. Bekijk de ruleset om te zien waarom:

chain INPUT { type filter hook input priority filter; policy drop; ct state established,related accept iif "lo" accept tcp dport 22 ct state established,new accept ip saddr 10.10.10.0/24 counter accept ← deze matcht ALLE subnet-verkeer eerst! icmp type echo-request limit rate 1/second ... ← wordt nooit bereikt }
De gouden regel: chains worden van boven naar beneden gelezen Zodra een regel matcht én een definitieve actie (accept of drop) uitvoert, stopt de verwerking voor dat pakket. De ping van clientXX komt uit 10.10.10.0/24, matcht dus de bredere accept-regel daarboven, en de rate-limit-regel eronder wordt nooit bereikt. Volgorde is alles.

Dit los je niet netjes op met losse nft-commando's — je herschrijft het configbestand met de regels in de juiste volgorde. Sla eerst op, bewerk dan:

sudo nft list ruleset | sudo tee /etc/sysconfig/nftables.conf sudo nano /etc/sysconfig/nftables.conf
table ip filter { chain INPUT { type filter hook input priority filter; policy drop; iif "lo" accept tcp dport 22 ct state established,new accept # ICMP eerst beperken — specifieke regels BOVEN de brede accept ip saddr 10.10.10.0/24 icmp type echo-request limit rate 1/second burst 5 packets accept ip saddr 10.10.10.0/24 icmp type echo-request drop # dan pas ander subnet-verkeer toelaten ip saddr 10.10.10.0/24 accept ct state established,related accept } }
# pas het configbestand toe sudo nft -f /etc/sysconfig/nftables.conf # of herstart de service sudo systemctl restart nftables
Onthoud voor het examen: specifieke regels (zoals een ICMP-limiet) moeten boven bredere regels (zoals "heel het subnet mag alles") staan. Anders "vangt" de brede regel het pakket eerst weg. Dit is de meest gemaakte denkfout met nftables.
✔ Verificatie Na de herschikking zie je bij pingen vanaf clientXX dat slechts ~1 reply per seconde doorkomt (na de burst van 5). De rate limit werkt nu.
PART B · Proxyservers forward proxy (Squid) & reverse proxy (Nginx) — bouwt voort op je nftables-firewall
Forward proxy · Squid
interne clients → PROXY → internet
Staat vóór de clients. Filtert/cachet/logt uitgaand verkeer.
Client moet ingesteld worden (browser/env-var).
Tools: ACL's, http_access. Voordeel: filtering, caching, logging.
Reverse proxy · Nginx
internet → PROXY → interne servers
Staat vóór de servers. Ontvangt inkomend verkeer, verdeelt het.
Transparant voor de client (geen config nodig).
Tools: proxy_pass, upstream. Voordeel: load balancing, SSL-offload, beveiliging.
Deel 5 — De brug: IP forwarding & NAT
nftables Taak 10
ServerXX als gateway: IP forwarding + NAT (masquerade)
▶

Nu je firewalld weg is, routeert je server het clientverkeer niet meer automatisch naar het internet. Je herstelt dat met IP forwarding (de kernel pakketten laten doorsturen) plus NAT/masquerade (private IP's vertalen naar het externe IP).

# 1. IP forwarding permanent aanzetten sudo nano /etc/sysctl.conf
net.ipv4.ip_forward = 1
# meteen toepassen zonder reboot sudo sysctl -p # of: sudo sysctl -w net.ipv4.ip_forward=1

2. NAT-regel toevoegen aan /etc/sysconfig/nftables.conf — een aparte nat-tabel met een postrouting-chain:

table ip nat { chain postrouting { type nat hook postrouting priority srcnat; policy accept; oifname "ens160" masquerade } }
sudo nft -f /etc/sysconfig/nftables.conf
Waarom postrouting + masquerade?
  • IP forwarding laat de kernel pakketten doorsturen tussen interfaces (van ens224 naar ens160). Zonder dit blijft je server een eindpunt, geen router.
  • masquerade (een vorm van PAT/source-NAT) vervangt het privé bron-IP van de client door het externe IP van de server, zodat antwoorden terug kunnen vinden. oifname "ens160" = enkel op verkeer dat via de internet-interface buitengaat.
  • postrouting is de hook die net voor het pakket de machine verlaat wordt aangeroepen — het juiste moment voor source-NAT.
✔ Verificatie Vanaf clientXX: ping www.google.be krijgt antwoord. Het clientverkeer wordt nu via ServerXX naar internet gerouteerd.
Deel 6 — Forward proxy met Squid
Squid Taak 11
Squid installeren + poort 3128 openzetten
▶

Squid is een caching forward proxy: hij stuurt clientverzoeken door naar internet, logt alles, kan sites blokkeren, en bewaart pagina's in cache om bandbreedte te sparen. Standaardpoort: 3128.

# EPEL + Squid + htpasswd-tool (voor latere authenticatie) sudo dnf install epel-release -y sudo dnf install squid httpd-tools -y squid -v

Open poort 3128 voor het lokale netwerk in je nftables-ruleset:

# in de INPUT-chain, voor het 10.10.10.0/24-netwerk: ip saddr 10.10.10.0/24 tcp dport 3128 accept
ℹ Als je de brede 10.10.10.0/24 accept-regel nog hebt staan uit Part A, dan is poort 3128 al toegankelijk en is deze specifieke regel overbodig. Voor een strak beleid verwijder je de brede regel en laat je enkel de poorten toe die je echt nodig hebt (3128, 22, …).
✔ Verificatie squid -v toont de versie. Poort 3128 staat open voor het subnet.
Squid Taak 12
squid.conf: ACL's en de volgorde van http_access
▶

Maak de cachemap aan, back-up de config en schrijf je beleid:

# cache-structuur initialiseren (eenmalig) sudo mkdir -p /var/spool/squid sudo squid -z sudo cp /etc/squid/squid.conf /etc/squid/squid.conf.bak sudo nano /etc/squid/squid.conf
# == BASIS == http_port 3128 cache_dir ufs /var/spool/squid 100 16 256 # == ACL DEFINITIES == acl localnet src 10.10.10.0/24 acl Safe_ports port 80 443 21 8080 acl SSL_ports port 443 acl CONNECT method CONNECT # == BEVEILIGING (specifieke deny's eerst) == http_access deny !Safe_ports http_access deny CONNECT !SSL_ports # == TOEGANG TOESTAAN == http_access allow localnet # == VANGNET == http_access deny all
# syntax testen, dan starten + enablen sudo squid -k parse sudo systemctl enable --now squid
ACL definiëren, dan toepassen Een acl-regel geeft enkel een naam aan een patroon (een subnet, een poort, een methode). Pas in een http_access-regel doe je er iets mee (allow/deny). cache_dir ufs /var/spool/squid 100 16 256: 100 MB cache, 16 eerste-niveau mappen, 256 submappen.
Volgorde is cruciaal (net als bij nftables!): Squid leest http_access van boven naar beneden en stopt bij de eerste match. Daarom staan specifieke deny's bovenaan, allow localnet in het midden, en deny all als laatste vangnet. Zet je deny all bovenaan, dan komt niemand er nog door.
✔ Verificatie squid -k parse geeft geen fouten. systemctl status squid → active (running).
Squid Taak 13
Client instellen + cache hits/misses lezen
▶

De client moet expliciet naar de proxy verwijzen (dat is het kenmerk van een forward proxy). De snelste manier is een omgevingsvariabele:

# op clientXX — geldt voor de huidige shell export http_proxy=http://10.10.10.1:3128 export https_proxy=http://10.10.10.1:3128 # test — let op de "Via"-header die Squid toevoegt curl -I http://example.com # proxy weer uitzetten: unset http_proxy https_proxy

Andere manieren: via GNOME-netwerkinstellingen (systeembreed) of in de browser zelf (enkel die browser). Bekijk live wat er door de proxy gaat:

# op de proxy (ServerXX) sudo tail -f /var/log/squid/access.log
Cache-status codes
  • TCP_MISS — niet in cache, Squid haalt het vers op. (eerste bezoek)
  • TCP_MEM_HIT / TCP_HIT — uit de cache geserveerd (tweede bezoek, sneller!)
  • TCP_REFRESH_MODIFIED — gecheckt bij de bron, bleek gewijzigd.
  • TCP_TUNNEL — een CONNECT-tunnel (HTTPS): Squid ziet enkel IP/poort/bytes, niet de inhoud. Daarom wordt HTTPS standaard niet gecachet.
ℹ Waarom toont httpbin.org/ip het proxy-IP? Omdat het verzoek vanuit de proxy naar internet vertrekt. De doelwebsite ziet het IP van ServerXX, niet dat van de client — dat is net de bedoeling van een forward proxy (de clients "verbergen" zich achter de proxy).
✔ Verificatie Eerste curl → TCP_MISS in de log. Tweede keer dezelfde pagina → TCP_HIT. De Via-header in het antwoord vermeldt Squid.
Squid Taak 14
Extra's: sites blokkeren, authenticatie, downloadlimiet
▶

Sites blokkeren — voeg een block-ACL toe boven http_access allow localnet:

# == BLOCK BAD SITES == acl badsites dstdomain "/etc/squid/badsites.txt" http_access deny badsites localnet
# bestand met één domein per regel (de punt dekt subdomeinen) echo ".facebook.com" | sudo tee -a /etc/squid/badsites.txt echo ".youtube.com" | sudo tee -a /etc/squid/badsites.txt # herladen zonder herstart sudo squid -k reconfigure

Authenticatie — enkel ingelogde gebruikers mogen de proxy gebruiken:

# maak gebruiker + wachtwoord aan sudo htpasswd -c /etc/squid/passwd student1
# vervang 'http_access allow localnet' door: auth_param basic program /usr/lib64/squid/basic_ncsa_auth /etc/squid/passwd acl auth_users proxy_auth REQUIRED http_access allow auth_users localnet

Downloadlimiet — beperk responses tot 5 MB (handig in een klaslokaal):

# boven '# == TOEGANG TOESTAAN ==' reply_body_max_size 5 MB localnet
sudo squid -k reconfigure
dstdomain en de leidende punt acl badsites dstdomain "/etc/squid/badsites.txt" matcht op het bestemmingsdomein. Een leidende punt (.youtube.com) matcht het domein én alle subdomeinen (www., m., …). Zonder punt match je enkel exact dat ene domein.
✔ Verificatie Na de block-ACL: in de browser werkt facebook.com niet meer, pxl.be wél. Met auth krijg je een wachtwoordprompt. Met de limiet stopt een download > 5 MB.
Deel 7 — Reverse proxy met Nginx
Nginx Taak 15
Backend klaarzetten: httpd op poort 8080
▶

In de reverse-proxy-opstelling draaien op ServerXX twee webservers: nginx (de reverse proxy) op poort 80, en httpd (de echte backend) op poort 8080. Zo vermijd je de fout "port 80 already in use".

# httpd + nginx installeren sudo dnf install httpd nginx -y # een testpagina voor de backend echo "<h1>Testsite via httpd backend</h1>" | sudo tee /var/www/html/index.html # httpd op 8080 laten luisteren sudo nano /etc/httpd/conf/httpd.conf
Listen 8080 # was: Listen 80
sudo systemctl enable --now httpd # open poort 80 (reverse proxy) in nftables — 8080 is enkel intern nodig # lokaal testen of de backend draait: curl http://localhost:8080
✔ Verificatie curl http://localhost:8080 toont "Testsite via httpd backend". ss -tlnp | grep 8080 bevestigt dat httpd daar luistert.
Nginx Taak 16
Nginx als reverse proxy: proxy_pass + de forwarding-headers
▶

Eerst een SELinux-boolean (uit het vorige hoofdstuk!) zodat Nginx naar de backend mag connecteren, dan de config:

sudo setsebool -P httpd_can_network_connect on sudo nano /etc/nginx/conf.d/reverse.conf
server { listen 80; server_name _; location / { proxy_pass http://127.0.0.1:8080/; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto $scheme; } }
sudo nginx -t sudo systemctl enable --now nginx
Wat doen die headers?
  • proxy_pass http://127.0.0.1:8080/ — de kern: stuur alles door naar de backend op 8080.
  • Host $host — geef de originele hostnaam door (anders ziet de backend "127.0.0.1").
  • X-Real-IP $remote_addr — het echte client-IP, anders logt de backend enkel het proxy-IP.
  • X-Forwarded-For — de hele keten van IP's (client → proxy → backend), standaard voor logging.
  • X-Forwarded-Proto $scheme — http of https, handig als de proxy SSL afhandelt.
Zonder deze headers denkt de backend dat álle verzoeken van 127.0.0.1 komen.
ℹ Het echte client-IP loggen in httpd: de backend ziet standaard 127.0.0.1. Wil je het echte IP in de httpd-logs, dan gebruik je RemoteIPHeader X-Forwarded-For en RemoteIPInternalProxy 127.0.0.1 in een VirtualHost, met een aangepast LogFormat dat %a gebruikt.
✔ Verificatie Vanaf clientXX: curl http://10.10.10.1 (poort 80) toont de backend-pagina — maar nu geserveerd via Nginx. Client weet niet dat er een backend op 8080 draait: dat is "transparant".
Deel 8 — Examenoefeningen: NFTables
Exam Taak 17
NFTables oefeningen 1–5 (incl. XMAS packet)
▶

Bij elke oplossing geef je het resultaat van nft list table ip filter mee (code + screenshot). Gebruik telkens nft flush ruleset om schoon te starten.

Oefening 1. Zorg dat er vanaf de eerste seconde maar 1 ping-aanvraag per seconde mag komen vanuit het lokale netwerk.

"Vanaf de eerste seconde" is de sleutel: een gewone limit rate 1/second burst 5 staat eerst 5 pings toe. Wil je echt vanaf seconde 1 beperken, zet dan burst 0 packets (of laat burst weg). En denk aan de volgorde-valkuil uit Taak 9: de ICMP-regel moet boven een eventuele brede subnet-accept staan.
sudo nft flush ruleset sudo nft add table ip filter sudo nft add chain ip filter INPUT { type filter hook input priority 0\; policy accept\; } # 1 ping/s zonder burst — meteen beperkt vanaf seconde 1 sudo nft add rule ip filter INPUT ip saddr 10.10.10.0/24 icmp type echo-request limit rate 1/second burst 0 packets accept sudo nft add rule ip filter INPUT ip saddr 10.10.10.0/24 icmp type echo-request drop

De eerste regel laat exact 1 echo-request per seconde door (geen burst); de tweede dropt de rest. Test vanaf clientXX: je ziet hooguit 1 reply/seconde. Had je burst 5 gebruikt, dan kwamen de eerste 5 pings nog door — vandaar burst 0.

Oefening 2. Blokkeer al het binnenkomend verkeer behalve SSH vanaf enkel clientXX (10.10.10.10) en verkeer dat je zelf op de machine aanvroeg.

Default policy drop. Dan drie accept-regels: established/related (eigen verkeer), loopback, en SSH maar enkel met source-IP 10.10.10.10 — combineer ip saddr 10.10.10.10 met tcp dport 22.
sudo nft flush ruleset sudo nft add table ip filter sudo nft add chain ip filter INPUT { type filter hook input priority 0\; policy drop\; } sudo nft add rule ip filter INPUT ct state established,related accept sudo nft add rule ip filter INPUT iif "lo" accept # SSH enkel vanaf clientXX: sudo nft add rule ip filter INPUT ip saddr 10.10.10.10 tcp dport 22 accept

Alles wat niet matcht valt op policy drop. Test: SSH vanaf 10.10.10.10 lukt; SSH of ping vanaf een ander IP wordt gedropt; eigen uitgaand verkeer (en de antwoorden) blijft werken dankzij established,related.

Oefening 3. Stel in dat enkel verkeer van 10.10.10.10 geblokkeerd wordt; al het andere verkeer is toegestaan.

Dit is het omgekeerde van een default-drop: hier is policy accept de basis, met één enkele drop-regel voor dat ene IP. Precies de demo uit Taak 5.
sudo nft flush ruleset sudo nft add table ip filter sudo nft add chain ip filter INPUT { type filter hook input priority 0\; policy accept\; } sudo nft add rule ip filter INPUT ip saddr 10.10.10.10 counter drop

Policy accept laat standaard alles toe; de enige regel dropt verkeer van 10.10.10.10. Test: pingen vanaf je host (ander IP) → werkt; pingen vanaf clientXX (10.10.10.10) → geblokkeerd.

Oefening 4. Accepteer al het verkeer van buiten naar ServerXX, maar blokkeer ICMP-verkeer.

Policy accept, met één drop-regel die matcht op het ICMP-protocol. Match met ip protocol icmp (of meta l4proto icmp).
sudo nft flush ruleset sudo nft add table ip filter sudo nft add chain ip filter INPUT { type filter hook input priority 0\; policy accept\; } # al het ICMP droppen sudo nft add rule ip filter INPUT ip protocol icmp drop

Alles is toegestaan (policy accept) behalve ICMP, dat expliciet gedropt wordt. Test: pingen naar ServerXX faalt, maar SSH/HTTP/… werken nog. Wil je enkel echo-requests blokkeren en bv. wel destination-unreachable toelaten, dan match je specifieker op icmp type echo-request.

Oefening 5 (theorie). Wat is een XMAS-packet? Hoe bescherm je je ertegen? Leg in eigen woorden uit hoe een hacker hierbij te werk gaat en waarom.

Denk aan de TCP-vlaggen (flags): FIN, PSH, URG. Een "XMAS"-packet heeft er ongewoon veel tegelijk aan staan — als een opgelichte kerstboom. Waarvoor zou een aanvaller dat gebruiken? (verkenning/scanning). Beschermen = zulke vreemde vlag-combinaties droppen.

Wat het is: een XMAS-packet (kerstboom-pakket) is een TCP-segment waarbij ongewoon veel vlaggen tegelijk aanstaan — typisch FIN, PSH en URG. Het pakket "licht op als een kerstboom". Zo'n combinatie komt in normaal verkeer nooit voor.

Hoe een hacker het gebruikt: bij een XMAS-scan (bv. met nmap -sX) stuurt de aanvaller deze pakketten naar poorten van het doel. Volgens de oude TCP-standaard antwoordt een gesloten poort met een RST, terwijl een open poort niets terugstuurt. Zo kan de aanvaller in kaart brengen welke poorten open zijn — een vorm van verkenning — terwijl het ongewone pakket vaak onopgemerkt door simpele logging glipt en geen volledige verbinding opzet (stealthy).

Bescherming met nftables: drop pakketten met die ongeldige vlag-combinatie. Je matcht op de TCP-flags:

# drop XMAS-pakketten (FIN+PSH+URG samen gezet) sudo nft add rule ip filter INPUT tcp flags '& (fin|psh|urg) == (fin|psh|urg)' drop # breder: drop ook NULL-scans en andere onzinnige combinaties sudo nft add rule ip filter INPUT tcp flags '& (fin|syn|rst|psh|ack|urg) == 0' drop

Omdat zo'n vlag-combinatie nooit in legitiem verkeer voorkomt, kan je ze zonder risico droppen. Daarmee blokkeer je deze scan-techniek én de informatie die een aanvaller eruit zou halen.

Deel 9 — Examenoefeningen: Proxy
Exam Taak 18
Proxy-oefeningen: ACL-volgorde, IP-restrictie, reverse routing & load balancing
▶

Oefening A — Waarom is de volgorde van http_access-regels belangrijk? (uit de Squid block-oefening)

Squid leest http_access-regels van boven naar beneden en stopt bij de eerste match — net als nftables. Gevolgen:

  • Een deny badsites moet boven allow localnet staan. Anders matcht allow localnet eerst en is de site al toegestaan vóór de block-regel bekeken wordt.
  • deny all hoort altijd onderaan als vangnet. Zet je het bovenaan, dan wordt al het verkeer geblokkeerd en komt geen enkele allow nog aan bod.

Vuistregel: specifieke deny's bovenaan, allows in het midden, deny all als laatste.

Oefening B — IP-gebaseerde toegang. Geef enkel client1 (één specifiek IP) toegang tot de proxy, weiger de rest van het subnet. Waarom werkt de ene volgorde wel en de andere niet?

Twee ACL's: localnet (het hele subnet) en client1 (één IP). De volgorde van http_access allow client1 t.o.v. http_access deny localnet bepaalt alles — en client1 zit zélf in localnet.

Werkt NIET (deny eerst):

acl localnet src 10.10.10.0/24 acl client1 src 10.10.10.10 http_access deny localnet # client1 zit in localnet → hier al geweigerd http_access allow client1 # wordt nooit bereikt

Werkt WEL (allow eerst):

http_access allow client1 # specifiek IP eerst toelaten http_access deny localnet # dan de rest van het subnet weigeren

Omdat client1 (10.10.10.10) óók in localnet (10.10.10.0/24) zit, moet de specifieke allow eerst komen. Anders vangt deny localnet het verkeer van client1 al weg. Zakelijk nut: enkel bepaalde machines (bv. de boekhouding, of een management-werkstation) door de proxy laten, of net één server uitsluiten van internettoegang.

Oefening C — Padgebaseerde routing (reverse proxy). Stuur /app1/ naar backend1 en /app2/ naar backend2.

Twee location-blokken in het Nginx server-blok, elk met een eigen proxy_pass naar een andere backend-poort. De backends draaien bv. op 8081 en 8082.

Twee backends (bv. httpd-instances op 8081 en 8082), twee location-blokken:

server { listen 80; location /app1/ { proxy_pass http://127.0.0.1:8081/; } location /app2/ { proxy_pass http://127.0.0.1:8082/; } }
sudo nginx -t && sudo systemctl reload nginx # test vanaf client curl http://10.10.10.1/app1/ # → backend1 curl http://10.10.10.1/app2/ # → backend2

Headers wijzigen → onmiddellijk? Een wijziging in een backend-index.html is meteen zichtbaar (geen caching standaard). Verwijder je proxy_set_header Host, dan krijgt de backend de Host-header van de proxy i.p.v. de originele — meestal merk je niets bij één simpele site, maar virtuele hosts die op hostnaam matchen kunnen dan de verkeerde site serveren.

Oefening D — Load balancing met upstream. Verdeel /api over meerdere backends. Waarom least_conn i.p.v. round_robin?

Definieer een upstream-blok met meerdere server-regels, en verwijs ernaar met proxy_pass http://naam. least_conn stuurt naar de backend met de minste actieve verbindingen.
upstream backend_pool { least_conn; server 127.0.0.1:8081; server 127.0.0.1:8082; } server { listen 80; location /api { proxy_pass http://backend_pool; } }
# test: 20 requests, kijk hoe ze verdeeld worden over de backends for i in {1..20}; do curl -s http://10.10.10.1/api; done

Waarom least_conn boven round_robin? Round-robin stuurt strikt om beurten, ongeacht hoe druk een backend het heeft. Als sommige requests veel langer duren dan andere, kan één backend overbelast raken terwijl een andere idle is. least_conn stuurt elk nieuw verzoek naar de backend met de minste actieve verbindingen — eerlijker bij ongelijke verwerkingstijden. Test failover door één backend te stoppen: het verkeer gaat dan automatisch naar de overige.

Squid Taak 19
Squid: sites blokkeren, downloadlimiet & cache-logs lezen
▶

De cursus-oefeningen 2 en 4 gecombineerd: je blokkeert bepaalde sites via een ACL-bestand, stelt een downloadlimiet in, en leert de Squid access-log ontcijferen. Dit is de proxy-configuratie die in een echte schoolomgeving of bedrijfsnetwerk gebruikt wordt.

Stap 1 — Blokkeerlijst als extern bestand

Waarom een extern bestand? Zodat je de blokkeerlijst kan aanpassen zonder squid.conf aan te raken. In een bedrijf beheert een andere afdeling die lijst.

# Maak een blokkeerlijst aan sudo nano /etc/squid/badsites.txt # Voeg toe (één domein per lijn, punt vooraan = ook subdomains): # .facebook.com # .tiktok.com # youtube.com # Voeg de ACL toe aan squid.conf VÓÓR de allow localnet regel: sudo nano /etc/squid/squid.conf
acl badsites dstdomain "/etc/squid/badsites.txt" http_access deny badsites localnet # moet VOOR allow localnet staan! http_access allow localnet
# Herladen zonder restart (actieve verbindingen blijven) sudo squid -k reconfigure # Testen vanaf client (moet geblokkeerd zijn): curl -x http://10.10.10.1:3128 http://youtube.com # Bevestig in de logs: sudo grep TCP_DENIED /var/log/squid/access.log

Stap 2 — Downloadlimiet instellen

Squid kan downloads beperken via delay_pools. Nuttig om te voorkomen dat één student de hele bandbreedte opslokt.

# Voeg toe aan squid.conf: delay_pools 1 delay_class 1 1 delay_parameters 1 1048576/1048576 # max 1 MB/s delay_access 1 allow localnet
sudo squid -k reconfigure # Test: download een bestand en observeer de snelheid export http_proxy=http://10.10.10.1:3128 curl http://ipv4.download.thinkbroadband.com/5MB.zip -o /dev/null

Stap 3 — Access-log lezen

De Squid access-log heeft een vast formaat. Elk veld heeft een betekenis — dit is de informatie die een netwerkbeheerder dagelijks leest.

sudo tail -20 /var/log/squid/access.log

Een logboek-regel ziet er zo uit:

# tijdstempel vertraging client-IP resultaat/status bytes methode URL MIME 1719000000.123 245 10.10.10.10 TCP_MISS/200 12345 GET http://example.com/ text/html
Veld Betekenis
TCP_MISS/200 Niet in cache, opgehaald van internet — HTTP 200 OK
TCP_MEM_HIT/200 Uit de RAM-cache geleverd — geen netwerk gebruikt
TCP_DENIED/403 Geblokkeerd door ACL — toegang geweigerd
TCP_REFRESH_MODIFIED In cache maar verlopen — opnieuw opgehaald en bijgewerkt
# Tijdstempel omzetten naar leesbare datum: date -d @1719000000 # Of filter op specifiek IP: sudo grep 10.10.10.10 /var/log/squid/access.log | tail -10

Squid herladen vs herstarten: squid -k reconfigure herlaadt de configuratie zonder actieve verbindingen te verbreken. systemctl restart squid verbreekt alles. Gebruik reconfigure voor config-wijzigingen in productie.

ACL-volgorde: de blokkeerregel moet vóór allow localnet staan. Squid stopt bij de eerste match — staat allow localnet boven de deny, dan komt de deny nooit aan bod.

Nginx Taak 20
Nginx: SSL-terminatie, snelheidsbeperking & failover
▶

De cursus-oefeningen 12–14: je voegt HTTPS toe aan de reverse proxy (SSL-terminatie), beperkt het aantal requests per seconde (rate limiting), en test automatische failover als een backend uitvalt. Dit zijn de drie meest gevraagde functies van Nginx in productie.

Stap 1 — Self-signed certificaat + HTTPS

SSL-terminatie betekent dat Nginx de HTTPS-verbinding afhandelt en intern gewoon HTTP doorstuurt naar de backend. De backend hoeft niets te weten van SSL.

# Genereer een self-signed certificaat (geldig 365 dagen) sudo openssl req -x509 -nodes -days 365 -newkey rsa:2048 \ -keyout /etc/nginx/ssl/server.key \ -out /etc/nginx/ssl/server.crt \ -subj "/CN=serverXX.pxl.lan" # (maak de map eerst aan als die niet bestaat) sudo mkdir -p /etc/nginx/ssl
# Bewerk /etc/nginx/conf.d/reverse-proxy.conf: server { listen 443 ssl; server_name serverXX.pxl.lan; ssl_certificate /etc/nginx/ssl/server.crt; ssl_certificate_key /etc/nginx/ssl/server.key; location / { proxy_pass http://127.0.0.1:8080/; proxy_set_header Host $host; proxy_set_header X-Real-IP $remote_addr; } } server { # HTTP → HTTPS redirect listen 80; return 301 https://$host$request_uri; }
sudo nginx -t && sudo systemctl reload nginx # Test: -k negeert de self-signed waarschuwing curl -k https://10.10.10.1 # Controleer de redirect: curl -v http://10.10.10.1 2>&1 | grep "Location:"

Stap 2 — Rate limiting

Rate limiting beschermt je backend tegen request-floods (bv. brute-force op een login-pagina). Nginx telt requests per IP en geeft een 429 Too Many Requests terug als het limiet overschreden wordt.

# Voeg toe aan /etc/nginx/nginx.conf, in het http { } blok: limit_req_zone $binary_remote_addr zone=api_limit:10m rate=5r/s; # In je server/location blok: location /api { limit_req zone=api_limit burst=10 nodelay; proxy_pass http://127.0.0.1:8080/; }
sudo nginx -t && sudo systemctl reload nginx # Test: stuur snel veel requests (verwacht 429 na de burst) for i in {1..20}; do curl -s -o /dev/null -w "%{http_code}\n" http://10.10.10.1/api; done

Wat betekent burst=10 nodelay? Burst staat toe dat tot 10 extra requests onmiddellijk verwerkt worden zonder vertraging. Requests bóven de burst krijgen een 429. Zonder nodelay zouden burst-requests vertraagd worden in plaats van geblokkeerd.

Stap 3 — Failover simuleren

Met een upstream-blok en meerdere backends kan Nginx automatisch overschakelen als een backend uitvalt. Dit heet passive failover.

upstream backend_pool { server 127.0.0.1:8081; server 127.0.0.1:8082 backup; # enkel als 8081 uitvalt } server { listen 80; location / { proxy_pass http://backend_pool; } }
# Start twee eenvoudige backends op verschillende poorten: echo "Backend 8081" | sudo tee /tmp/b1/index.html (cd /tmp/b1 && python3 -m http.server 8081 &) echo "Backend 8082" | sudo tee /tmp/b2/index.html (cd /tmp/b2 && python3 -m http.server 8082 &) sudo nginx -t && sudo systemctl reload nginx # Stuur requests — normaal gaat alles naar 8081: curl http://10.10.10.1/ # Stop backend 8081, test failover naar 8082: kill %1 curl http://10.10.10.1/ # moet nu "Backend 8082" tonen

SELinux en Nginx SSL: als Nginx geen bestanden kan lezen in /etc/nginx/ssl/, voer dan uit: sudo restorecon -Rv /etc/nginx/ssl/. Nginx moet ook poort 443 mogen openen: sudo setsebool -P httpd_can_network_connect 1.

Poort 443 in nftables: vergeet niet een regel toe te voegen voor HTTPS als je default-drop hebt: tcp dport 443 accept.
