Processen & Logging — kijken wat er gebeurt

Twee onmisbare skills voor een sysadmin: weten wat er nu draait op je server, en terugzien wat er gebeurd is. Eerst leer je processen oplijsten, prioriteren en beëindigen (ps, top, nice, kill). Daarna duik je in het logging-systeem van RHEL — journald voor snel filteren, rsyslog voor klassieke tekstlogs, plus logger en logrotate. Samen geven ze je het volledige beeld: live monitoring én historische diagnose.

📋 Scenario

Een collega meldt dat de server "traag" aanvoelt. Je moet uitzoeken welk proces de CPU opslokt, eventueel iets afsluiten of in prioriteit verlagen. Een dag later — andere zaak — ontdek je dat iemand 's nachts heeft proberen inloggen via SSH met een verkeerd wachtwoord. Wie was het, vanaf waar, wanneer precies? Beide vragen los je op met de tools uit dit hoofdstuk. Werk op ServerXX; voor de logging-oefeningen test je vanaf clientXX.

🌳 Wat is een proces? Parent & child

└─ systemd (PID 1, de "moeder van alle processen") ├─ sshd (daemon, draait als root) │ └─ sshd: student@pts/0 (child: jouw SSH-sessie) │ └─ bash (child: jouw shell) │ └─ nano file.txt (child: jouw editor) ├─ httpd (parent) │ ├─ httpd (worker child 1) │ ├─ httpd (worker child 2) │ └─ httpd (worker child 3) └─ NetworkManager

Elk proces krijgt een unieke PID en wordt gestart door een parent. Children erven omgevingsvariabelen, rechten en open file descriptors. Start je nano 15 keer? Dan zijn dat 15 aparte processen met 15 verschillende PID's, allemaal children van je bash.

PART A · Processen & services wat draait er, wie heeft prioriteit, hoe stop je het netjes
Deel 1 — Processen bekijken
ps Taak 01
ps: snapshot van actieve processen
▶

ps geeft een momentopname van wat er draait — niet live, gewoon "op dit moment". De command-line opties komen uit drie tradities (BSD, UNIX, GNU) die door elkaar gebruikt worden, wat soms verwarrend is.

# enkel je eigen processen in deze shell ps # meer detail: user, %cpu, %mem, status, command ps u # ALLE processen op het systeem (incl. daemons zonder terminal) ps aux
USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND root 1 0.0 0.3 171944 12892 ? Ss 10:00 0:02 /usr/lib/systemd/systemd student 1389 0.0 0.1 9120 5748 pts/0 Ss 10:37 0:00 -bash student 7593 0.1 0.0 10068 1564 pts/0 R+ 11:20 0:00 ps aux
De kolommen die je echt nodig hebt
  • PID — uniek nummer; gebruik je voor kill of renice.
  • USER — wie heeft het proces gestart? Belangrijk voor rechten en SELinux.
  • %CPU / %MEM — verbruik. Snel zien welke processen "duur" zijn.
  • VSZ / RSS — virtueel geheugen vs werkelijk RAM-verbruik. RSS is meestal de relevante.
  • STAT — R running, S sleeping, T stopped, Z zombie. Plus modifiers: + foreground, s sessieleider.
  • COMMAND — het commando dat het proces startte.
# enkel specifieke kolommen tonen ps -eo pid,user,nice,comm # sorteer op geheugengebruik, hoogste eerst ps aux --sort=-%mem | head # sorteer op CPU ps aux --sort=-%cpu | head
ℹ Het -teken bij --sort: met --sort=-%mem sorteer je aflopend (hoogste eerst). Zonder min-teken (--sort=%mem) is het oplopend.
✔ Verificatie ps aux | wc -l toont hoeveel processen er draaien. ps -eo pid,user,comm --sort=-%mem | head toont de top geheugengebruikers met enkel de kolommen die je vroeg.
top Taak 02
top: live monitoring met sneltoetsen
▶

Waar ps een foto is, is top een video. Het scherm ververst zich elke paar seconden en je kan tijdens de weergave sorteren en zelfs ingrijpen. Druk q om te stoppen.

top
De sneltoetsen die je moet kennen
  • M — sorteer op geheugengebruik (Memory).
  • P — sorteer op CPU-gebruik (de standaard, Processor).
  • R — sorteervolgorde omkeren (Reverse).
  • 1 — elke CPU-core apart tonen i.p.v. één gemiddelde.
  • k — een proces killen (vraagt PID + signaal).
  • r — een proces reprioriteren (renice; vraagt PID + nice-waarde).
  • h — help. q — quit.
ℹ Modernere alternatieven: htop (gekleurde, scrollbare versie, vaak met dnf install htop beschikbaar) en btop (zelfs mooier). Voor het examen blijft top de standaard die altijd aanwezig is.
✔ Verificatie Open top, druk M → bovenaan staat het proces met het meeste geheugen. Druk P → hetzelfde maar nu voor CPU. Druk q om af te sluiten.
Deel 2 — Achtergrond, voorgrond en prioriteit
jobs Taak 03
Voorgrond ↔ achtergrond schakelen
▶

Een commando dat je gewoon intypt blokkeert je terminal tot het klaar is — dat is voorgrond. Wil je het laten doorlopen terwijl jij wat anders doet, dan zet je het in de achtergrond.

# & aan het eind = meteen in achtergrond starten sleep 300 & # [1] 1676 ← job-nummer + PID # welke jobs heeft deze shell op de achtergrond? jobs # [1]+ Running sleep 300 & # haal job 1 terug naar voorgrond fg %1 # shell is weer geblokkeerd door sleep ... # pauzeer het voorgrondproces met Ctrl+Z # ^Z → [1]+ Stopped sleep 300 # laat het verder draaien, maar in de achtergrond bg %1
De cyclus visueel Start (voorgrond) → Ctrl+Z → gestopt → bg → draait in achtergrond → fg → terug voorgrond → klaar.

job-nummer vs PID: jobs geeft een lokaal nummer (%1, %2) dat alleen in deze shell geldt. Een PID is systeembreed uniek. fg %1 en fg 1676 doen hetzelfde voor een proces in jouw shell.
Achtergrondjobs en je shell: sluit je je terminal, dan stoppen achtergrondjobs standaard mee (SIGHUP). Wil je een proces dat een logout overleeft, gebruik dan nohup commando &, of beter nog systemd-run --user of een screen/tmux-sessie.
✔ Verificatie Je kan een sleep achter elkaar starten (&), terughalen (fg), pauzeren (Ctrl+Z) en hervatten (bg). jobs toont de huidige status.
nice Taak 04
nice en renice: CPU-prioriteit regelen
▶

Elke proces krijgt een nice-waarde die zijn voorrang op de CPU bepaalt. Het bereik is -20 tot +19. Lager = hogere prioriteit (egoïstischer); hoger = lagere prioriteit ("aardiger" voor anderen).

De nice-schaal — lager = meer voorrang

-20 (hoogste prio)0 (default)+19 (laagste prio)
enkel root
0
iedereen mag
Gewone gebruiker: kan enkel nice-waarde verhogen (0 → 19), niet verlagen.
Root: kan elk proces beide kanten op zetten (-20 → 19).
# een proces starten MET een nice-waarde nice -n 10 sleep 300 & ps -o pid,nice,comm # PID NI COMMAND # 1679 10 sleep # de nice-waarde van een DRAAIEND proces aanpassen sudo renice -n -5 -p 1679 # 1679 (process ID): oude prioriteit is 10, nieuwe prioriteit is -5
Waarom een proces "nice" maken? Een lange, niet-urgente taak (een back-up, een grote videoconversie) wil je niet je interactieve werk laten vertragen. Geef hem nice +10 of +15 en hij krijgt enkel CPU als niemand anders ze gebruikt. Een latentie-gevoelige dienst (audio, real-time) kan je als root juist -5 meegeven. Wees voorzichtig met negatieve waarden: ze kunnen systeemdaemons en je shell vertragen.
Asymmetrie voor gewone gebruikers: jij kan een eigen proces wel "minder belangrijk" maken (nice verhogen), maar je kan het niet meer terugdraaien naar een lagere waarde dan je het hebt gezet. Enkel root mag nice verlagen. Dit voorkomt dat een gewone gebruiker zijn programma's voorrang kan geven op systeemtaken.
✔ Verificatie ps -o pid,nice,comm toont de NI-kolom met je gewenste waarde. Een gewone gebruiker krijgt "permission denied" bij renice -n -1; met sudo lukt het wel.
Deel 3 — Processen beëindigen (en pauzeren)
kill Taak 05
kill, killall en het hele palet aan signalen
▶

"Kill" is misleidend: het commando stuurt eigenlijk een signaal naar een proces. Sommige signalen vragen netjes "wil je stoppen?", andere forceren onmiddellijk de dood. Daar zit het meeste leerwerk.

# standaard signaal = SIGTERM (15) — "stop netjes als je kan" kill 1679 # SIGKILL (9) — niet te negeren, niet op te vangen kill -9 1679 # killall stuurt naar ALLE processen met die naam killall nano # signaal met naam in plaats van nummer (gelijkwaardig) kill -SIGTERM 1679 kill -SIGKILL 1679
SignaalNr.Wat het doet
SIGHUP1"Herlaad je config" — of: je terminal is weg. Veel daemons interpreteren dit als "lees config opnieuw".
SIGINT2Onderbreek — het signaal van Ctrl+C.
SIGKILL9Onmiddellijk + onvoorwaardelijk doden. Kan niet opgevangen of genegeerd worden.
SIGTERM15Standaard van kill. "Sluit netjes af." Proces krijgt kans om op te ruimen.
SIGSTOP19Pauzeer het proces — niet te negeren. Geen kill, maar een echte vriespauze.
SIGTSTP20Terminal stop — het signaal van Ctrl+Z. Vriendelijker variant van SIGSTOP.
SIGCONT18Hervat een gepauzeerd proces.
SIGTERM vs SIGKILL — gebruik altijd eerst de zachte kill PID (= SIGTERM) geeft het proces de kans om openstaande bestanden te flushen, verbindingen netjes te sluiten, tijdelijke bestanden op te ruimen. Een database die je met kill -9 doodt, kan corrupte data achterlaten. Gebruik -9 alleen als kill niet helpt.
ℹ Alle signalen op je systeem: kill -l toont de volledige lijst. Nummers kunnen ietsje verschillen tussen Unix-varianten, dus deze lijst is je referentie voor de actieve machine.
SIGSTOP/SIGCONT is geen kill: SIGSTOP bevriest het proces alsof iemand op pauze heeft gedrukt — het verbruikt geen CPU, maar leeft nog. Pas met SIGCONT speelt het verder. Probeer dit zelf met gedit: open gedit, doe in een andere terminal kill -SIGSTOP <PID>, typ in gedit (niets verschijnt), dan kill -SIGCONT <PID> — al je toetsaanslagen komen plots tevoorschijn.
✔ Verificatie kill -l lijst alle signalen op. Je begrijpt het verschil tussen SIGTERM (vragen), SIGKILL (forceren) en SIGSTOP (pauzeren).
Deel 4 — Examenoefeningen: processen
Exam Taak 06
Oefeningen 1–6: oplijsten, sorteren, top, killen
▶

Oef 1. Lijst alle processen op met volledige kolommen, pipe naar less.

ps aux | less

aux = alle processen (ook van andere users) + extended user-kolommen + ook die zonder controlling x-terminal (daemons). less opent een pager waarin je kan scrollen met pijltjes/PgUp/PgDn, zoeken met /term, afsluiten met q.

Oef 2. Lijst alle processen op, gesorteerd per gebruiker, naar less.

De --sort-optie van ps accepteert kolomnamen. Hoe heet de user-kolom?
ps aux --sort=user | less

Geen min-teken vooraan, dus alfabetisch oplopend (a→z). Wil je z→a: --sort=-user.

Oef 3. Lijst alle processen op met enkel: PID, user, nice-waarde, commando.

-o = output format. Geef de gewenste kolomnamen met komma's gescheiden: pid,user,nice,comm. Gebruik -e om alle processen te krijgen (anders krijg je enkel die van je shell).
ps -eo pid,user,nice,comm

-e = every proces, -o = output enkel deze kolommen. Tip: comm toont het commando zonder argumenten; cmd (of args) toont het volledige commando.

Oef 4. Start top, sorteer eerst op CPU, dan op geheugen.

Druk top → daarna P (sorteren op Processor/CPU, standaard al actief) → vervolgens M (sorteren op Memory). Afsluiten: q.

Oef 5. Start nano in de achtergrond als jezelf (niet als root). Gebruik top om dit proces te stoppen.

Achtergrond = &. Binnen top: k vraagt om een PID en signaal.
nano & # [1] 12345 top

In top: druk k → tik de PID (12345) → Enter → tik signaal (laat leeg of 15 voor SIGTERM) → Enter. Het nano-proces is weg.

Oef 6. Start nano 20 keer in de achtergrond. Stop ze allemaal met één commando.

Bash heeft een for-loop, en er bestaat een commando dat alle processen met een bepaalde naam in één klap stopt.
# 20 nano-processen starten for i in {1..20}; do nano & done jobs | wc -l # controleer: 20 # allemaal tegelijk stoppen op naam killall nano

killall stuurt standaard SIGTERM naar élk proces met die naam. Voorzichtig: elk nano sterft, ook eventueel echt werk-in-uitvoering.

Exam Taak 07
Oefeningen 7–11: nice/renice + SIGSTOP/SIGCONT
▶

Oef 7. Start nano met nice-waarde 5, als gewone gebruiker.

nice -n 5 nano & ps -o pid,nice,comm # PID NI COMMAND # 12345 5 nano

Positieve waarde → werkt zonder sudo (je verlaagt prioriteit, mag iedereen).

Oef 8. Verander de nice-waarde van dat nano-proces naar 7. Controleer.

# renice mag (waarde verhogen, eigen proces) renice -n 7 -p 12345 ps -o pid,nice,comm -p 12345

Van 5 → 7 = verhogen (= minder prioriteit). Mag zonder sudo, want je gaat de "verkeerde" kant op vanuit het perspectief van de gebruiker.

Oef 9. Verander de nice-waarde van datzelfde nano naar -7. Controleer.

Negatieve nice-waarde = méér prioriteit = enkel root mag.
sudo renice -n -7 -p 12345 ps -o pid,nice,comm -p 12345 # PID NI COMMAND # 12345 -7 nano

Zonder sudo: "permission denied". Met sudo: lukt, want root mag elke kant op. Dit toont meteen de asymmetrische regel uit Taak 4.

Oef 10. Start gedit, gebruik kill om het te pauzeren. Probeer te typen — er gebeurt niets.

"Pauzeren" = SIGSTOP (niet doden). Welk signaalnummer is dat?
# start gedit (in achtergrond, anders blokkeert het je shell) gedit & # [1] 23456 # pauzeer met SIGSTOP (= signaal 19) kill -SIGSTOP 23456 # of: kill -19 23456

gedit is nu "bevroren": het bestaat nog, maar reageert niet. Klik in gedit en typ wat — er gebeurt niets, want het proces verwerkt geen events. ps -o pid,stat,comm -p 23456 toont de T-status (stopped).

Oef 11. Gebruik killall om gedit te hervatten. De getypte tekst verschijnt opeens.

"Hervatten" = SIGCONT.
killall -SIGCONT gedit # of: killall -18 gedit # of: kill -SIGCONT 23456

De getypte tekst — die het OS in de input-buffer had bewaard — wordt nu in één klap verwerkt en verschijnt. Mooi bewijs dat SIGSTOP de tijd letterlijk stilzet voor dat proces.

PART B · Logging journald, rsyslog, logger, logrotate — terugzien wat er gebeurd is

🔌 De RHEL log-pipeline

kernel · services · apps
Sturen meldingen via /dev/log, sockets of de syslog-API.
→
systemd-journald
Verzamelt alles. Binaire DB (/var/log/journal/). Snel filterbaar via journalctl.
→
rsyslog
Krijgt events van journald. Schrijft klassieke tekstlogs.
→
/var/log/*
messages, secure, cron, maillog, boot.log, …

journald verzamelt, rsyslog verspreidt naar tekstbestanden. Beide tegelijk: voor snel filteren gebruik je journalctl, voor read-only forensics op een kapotte schijf zijn de tekstbestanden in /var/log handiger.

Deel 5 — journald & journalctl
journald Taak 08
journald: status + persistent vs volatile storage
▶

systemd-journald is de service die alles verzamelt. Check eerst dat hij draait, dan bekijk je waar logs bewaard worden.

systemctl status systemd-journald
Volatile vs persistent De belangrijkste optie heet Storage= in journald.conf:
  • volatile — logs enkel in RAM (/run/log/journal). Verdwijnen bij reboot. Snel maar geen geheugen.
  • persistent — logs op schijf (/var/log/journal). Blijven bewaard.
  • auto (default op RHEL) — persistent als /var/log/journal bestaat, anders volatile. Dus: zorg dat die map bestaat.
# bestaat de persistente map? ls -ld /var/log/journal # bestaat hij niet? aanmaken + journald herstarten sudo mkdir -p /var/log/journal sudo systemctl restart systemd-journald # config aanpassen — kopieer eerst de standaard naar /etc sudo cp /usr/lib/systemd/journald.conf /etc/systemd/journald.conf sudo nano /etc/systemd/journald.conf
Storage=persistent # haal de # voor de regel weg om de waarde te activeren
ℹ Drie configniveaus voor systemd-services:
  • /usr/lib/systemd/journald.conf — pakketstandaard. Nooit bewerken (overschreven bij update).
  • /etc/systemd/journald.conf — jouw wijzigingen, één bestand voor alles.
  • /etc/systemd/journald.conf.d/*.conf — drop-ins per afzonderlijke wijziging. Schoner als je veel aanpassingen doet.
✔ Verificatie systemctl status systemd-journald → active (running). ls /var/log/journal/ toont een directory per machine-ID; logs overleven nu een reboot.
journalctl Taak 09
Filteren met journalctl: -u, -b, -p, --since, -x, -f
▶

Het systeemlogboek is enorm. De kunst is filteren. Eerst de anatomie van een logregel:

dec 10 18:12:05 ServerXX gnome-shell[1784]: Detected async api for thumbnails
  • tijdstempel — wanneer.
  • hostname — welke machine.
  • proces[PID] — welk programma genereerde de regel.
  • bericht — de eigenlijke melding.
De zes filteropties die je echt nodig hebt
  • -e / --pager-end — spring meteen naar het einde (recentste). Bijna altijd gebruiken.
  • -u UNIT — enkel events van één service: journalctl -u sshd (Tab-completion werkt!).
  • -b — alleen sinds laatste boot. -b -1 = vorige boot, -b -2 = die ervoor. --list-boots toont een overzicht.
  • -p PRIO — enkel events van die prioriteit of hoger (zie Taak 11). journalctl -p warning -b.
  • --since / --until — tijdsbereik: --since "2025-04-27 09:00", --since yesterday, --since "5 hours ago".
  • -x — voeg extra uitleg (catalog) toe aan elke regel, indien beschikbaar.
  • -f — follow: live updates, zoals tail -f. Stop met Ctrl+C.
  • --dmesg — enkel kernel-berichten.
# de klassieke "wat is er gisteren misgegaan met ssh" sudo journalctl -u sshd --since yesterday # services die crashten sinds deze boot sudo journalctl -p err -b # live volgen tijdens troubleshooting sudo journalctl -f # 5 regels van NetworkManager, drie boots geleden sudo journalctl -u NetworkManager -b -3 -n 5 --no-pager # events binnen één dag sudo journalctl --since "2025-04-27" --until "2025-04-28"
ℹ Wie ziet wat? Root ziet alles, gewone gebruikers vooral hun eigen processen. Wil je een gewone gebruiker volledig inzage geven (zonder sudo)? Voeg hem toe aan de systemd-journal-groep:
sudo usermod -aG systemd-journal student
ℹ Geldige tijdsformaten voor --since/--until: "2022-11-23 23:02:15", "2022-09-01", "12:00", now, today, yesterday, "5 hours ago", "-5 min".
✔ Verificatie Je kan de logs van sshd sinds gisteren tonen, errors in deze boot vinden, en live nieuwe events volgen. Tab-completion na -u toont een lijst van services.
Prioriteit Taak 10
De 8 prioriteitsniveaus — wat is "normaal" en wat is "brandend"
▶

Elke logregel krijgt een severity level, van bijna-niets tot ramp. Bij journalctl -p X krijg je alles vanaf dat niveau en hoger.

Van triviaal naar catastrofaal

7debugZeer gedetailleerde info — alleen relevant bij actieve foutopsporing.
6infoNormale operationele meldingen. "Service gestart."
5noticeOpvallend maar niet fout. "Config herladen."
4warningIets klopt niet helemaal. Goede startfilter bij troubleshooting.
3errFout, maar service draait nog. "Kan bestand niet schrijven."
2critErnstige fout in een belangrijk onderdeel.
1alertOnmiddellijke actie nodig.
0emergSysteem onbruikbaar. *.emerg :omusrmsg:* = stuur het naar elke ingelogde user.
# standaard troubleshoot-filter: warning en erger sudo journalctl -p warning -b # zwaarste alleen sudo journalctl -p crit -b # één voorbeeld: sudo zonder rechten genereert een 'notice' journalctl | grep "NOT in sudoers"
dec 10 01:54:59 ServerXX sudo[5753]: jacob : user NOT in sudoers ; TTY=pts/0 ; PWD=/home/student ; COMMAND=/usr/sbin/useradd jef
Kleurweergave in journalctl Veel terminal-themes kleuren automatisch:
  • grijs/wit — debug, info, notice (de ruis)
  • geel — warning
  • rood — err, crit, alert, emerg (waar je naar zoekt)
Bij een storing scan je dus eerst op rode regels.
✔ Verificatie journalctl -p err -b toont enkel error en zwaarder. journalctl -p debug toont werkelijk alles (vaak duizenden regels).
Deel 6 — rsyslog: de tekstlogs in /var/log
rsyslog Taak 11
De klassieke logbestanden in /var/log/
▶

rsyslog krijgt events van journald en schrijft ze naar tekstbestanden. Waarom ook tekst, als journald al alles in een DB heeft? Omdat tekst altijd leesbaar is — zelfs als je de harddisk uit een kapotte server haalt en in een andere machine prikt, kan je less /var/log/messages doen. Met een binaire journald-DB lukt dat niet zo makkelijk.

ls -l /var/log/
De vier bestanden die je moet kennen op RHEL
  • /var/log/messages — algemene systeemmeldingen.
  • /var/log/secure — authenticatie & beveiliging: SSH-logins, sudo-gebruik, mislukte authenticatie. Eerste plek bij een hack-vermoeden.
  • /var/log/cron — geplande taken (wat draaide, wanneer, met welke output).
  • /var/log/boot.log — meldingen tijdens de opstart.
# bestanden zijn niet wereldleesbaar — gebruik sudo sudo less /var/log/secure sudo tail -20 /var/log/messages # mislukte SSH-pogingen vinden sudo grep "Failed password" /var/log/secure # sudo-gebruik bekijken sudo grep sudo /var/log/secure
Dec 10 01:54:59 ServerXX sudo: jacob : user NOT in sudoers ; TTY=pts/0 ; PWD=/home/student ; COMMAND=/usr/sbin/useradd jef Dec 10 18:36:26 ServerXX sudo: student : TTY=pts/0 ; COMMAND=/usr/bin/dnf install tree
ℹ Welk gereedschap voor welke vraag? Weet je het keyword waarop je zoekt → grep in /var/log/secure is snel. Weet je het niet → journalctl met filters (per service, per tijd) is efficiënter. In de praktijk gebruik je beide door elkaar.
✔ Verificatie ls /var/log/ toont in elk geval messages, secure, cron. Je vindt je eigen sudo-gebruik terug in /var/log/secure.
rsyslog Taak 12
rsyslog.conf: facilities × prioriteiten = bestemming
▶

Wat komt in welk bestand terecht? Dat wordt geregeld in /etc/rsyslog.conf in de sectie #### RULES ####. Elke regel matcht op facility.priority en routeert naar een bestand (of remote host).

sudo nano /etc/rsyslog.conf
#### RULES #### # Log alles vanaf 'info', behalve mail/authpriv/cron, naar /var/log/messages *.info;mail.none;authpriv.none;cron.none /var/log/messages # Authenticatie- en beveiligingsberichten gaan naar /var/log/secure authpriv.* /var/log/secure # Alle mail-events mail.* -/var/log/maillog # Geplande taken cron.* /var/log/cron # Noodgevallen: stuur naar elke ingelogde gebruiker *.emerg :omusrmsg:* # Boot-meldingen naar boot.log local7.* /var/log/boot.log
De syntax in één zin facility.priority bestemming. Facility = welke "afdeling" stuurde het bericht (mail, cron, authpriv, kern, local0-7, of *). Priority = hoe ernstig (zie Taak 10), waarbij * alles is en none niets. Bestemming kan een bestand zijn, of @host voor een remote syslog-server, of :omusrmsg:* voor "stuur naar alle gebruikers".
ℹ De minteken-truc: -/var/log/maillog (met streepje vooraan) betekent: "schrijf asynchroon, zonder elke regel meteen naar disk te flushen". Sneller voor logs met veel volume zoals mail. Nadeel: bij een crash kan je de laatste paar regels missen.
ℹ Remote logging: de @-prefix stuurt naar een centrale logserver — handig in een bedrijf met veel machines:
# alle errors naar een centrale logserver *.err @logger.pxl.be # UDP *.err @@logger.pxl.be # TCP (betrouwbaarder)
ℹ Drop-ins: onderaan rsyslog.conf staat include(file="/etc/rsyslog.d/*.conf" mode="optional"). Bestanden in die map worden automatisch ingelezen. Voor eigen regels maak je liever /etc/rsyslog.d/10-mijneigen.conf dan dat je /etc/rsyslog.conf rechtstreeks bewerkt.
✔ Verificatie Je vindt de RULES-sectie en kan voorspellen welk bestand een bepaalde melding zal ontvangen. Een SSH-login → /var/log/secure. Een cron-job → /var/log/cron. Een normale info-melding → /var/log/messages.
Deel 7 — Eigen logs schrijven & logs onderhouden
logger Taak 13
logger: zelf logs schrijven vanuit een script
▶

Wil je jouw eigen scripts of cron-jobs sporen achterlaten in het systeemlog? Het commando logger stuurt een bericht door als ware het een echte log-event, met facility, priority en al.

# simpel: bericht naar het systeemlog logger "system going down for maintenance" # controleer in journalctl journalctl -n 5 --no-pager
dec 11 09:45:47 ServerXX student[34023]: system going down for maintenance
# met expliciete prioriteit + tag logger -p user.err -t backup-script "Backup of /home failed!" # vaak gebruikt in scripts: # #!/bin/bash # logger -t mijnscript "Run gestart" # ... werk ... # logger -t mijnscript -p user.err "Iets ging mis"
Waarom is dit handig? Scripts die ergens 's nachts in cron draaien moeten ergens hun sporen achterlaten. Schrijven naar een eigen tekstbestand kan, maar dan zoek je later op tien plekken. Met logger komt het in het systeemlog en kan je het filteren met journalctl -t mijnscript of grep mijnscript /var/log/messages. Eén centrale plek voor diagnose.
ℹ Format: logger -p facility.priority -t tag "bericht". Tags zoals backup-script maken het later makkelijk filteren. Veelgebruikte facilities voor eigen scripts: user, local0 tot local7.
✔ Verificatie Na logger "test123" vind je het terug met journalctl | grep test123 én in /var/log/messages.
logrotate Taak 14
logrotate: logs onderhouden zonder dat ze je schijf opvreten
▶

Een logbestand waar nooit iets uit verwijderd wordt, groeit oneindig. Daarom draait er dagelijks een logrotate-cron die oude logs roteert (hernoemt, comprimeert) en de oudste verwijdert.

sudo nano /etc/logrotate.conf
# rotate log files weekly weekly # keep 4 weeks worth of backlogs rotate 4 # create new (empty) log files after rotating old ones create # use date as a suffix of the rotated file dateext # uncomment if you want your log files compressed #compress # packages drop log rotation information into this directory include /etc/logrotate.d
Wat doet elke directive?
  • weekly — roteer wekelijks (alternatieven: daily, monthly, size 100M).
  • rotate 4 — bewaar 4 oudere versies; de 5de wordt verwijderd.
  • create — maak meteen een nieuw, leeg logbestand aan met dezelfde rechten.
  • dateext — geef de geroteerde bestanden een datumsuffix (messages-20250428) i.p.v. .1, .2, …
  • compress — gzip de oude bestanden (bespaart enorm veel schijf).
  • include /etc/logrotate.d — per pakket eigen regels: /etc/logrotate.d/httpd, .../nginx, .../syslog, …
# bekijk wat logrotate per pakket geconfigureerd heeft ls /etc/logrotate.d/ # forceer een rotate-run nu (handig om je config te testen) sudo logrotate -fv /etc/logrotate.conf # dry-run: laat zien wat ER ZOU gebeuren, zonder iets aan te raken sudo logrotate -d /etc/logrotate.conf
✔ Verificatie Na ls /var/log/ zie je bestanden zoals messages-20250420 of messages.1.gz — bewijs dat rotatie werkt.
Deel 8 — Examenoefeningen: logging
Exam Taak 15
Oefeningen 1–9: journalctl filteren
▶

Oef 1. Bekijk je systeemlogs.

sudo journalctl # navigeer met pijltjes/PgUp/PgDn, zoek met /, sluit af met q # sneller: spring meteen naar het einde sudo journalctl -e

Oef 2. Vind het eerste voorkomen van "file system" met less.

journalctl opent standaard met de pager less. In less zoek je met / gevolgd door de zoekterm.
sudo journalctl # druk: /file system (en Enter) # spring naar volgend voorkomen: n (vorige: N)

De pager opent bij het begin van de logs; /file system springt naar de eerste hit. n = next match. q sluit af.

Oef 3. Alle log-events van NetworkManager.

sudo journalctl -u NetworkManager # de .service mag je weglaten # tip: na -u kan je Tab-completion gebruiken

Oef 4. Alle logs met prioriteit critical of hoger.

sudo journalctl -p crit

-p crit = crit én alles erger (alert + emerg). Een schone server heeft hier hopelijk weinig output.

Oef 5. Events van de allereerste boot, geschreven naar ~/first_boot.

Gebruik --list-boots om de offset van de oudste boot te vinden, en redirect met > naar een bestand.
# overzicht van alle bewaarde boots — noteer de hoogste offset sudo journalctl --list-boots # bv. oudste = -12, dan: sudo journalctl -b -12 > ~/first_boot # controleer head -5 ~/first_boot

journalctl --list-boots lijst alle opstartsessies met hun offset (-0 = huidige, -1 = vorige, …). Hoe ver terug je kan gaan hangt af van je storage-instelling (Taak 8).

Oef 6. Alle events voor de week van 26 februari.

sudo journalctl --since "2024-02-26" --until "2024-03-04" # maandag t/m zondag van die week

Datumformaat is YYYY-MM-DD. Wil je ook tijd: "2024-02-26 09:00". --until is exclusief, dus om de hele zondag mee te nemen tot "2024-03-04" (= maandag 00:00).

Oef 7. Toon minstens 20 events van NetworkManager.

sudo journalctl -u NetworkManager -n 20 --no-pager

-n 20 = laatste 20 regels. --no-pager = niet openen in less (handig om de output meteen te zien/te kopiëren).

Oef 8. Alle events van de week van 26 februari met prioriteit warning of hoger.

sudo journalctl --since "2024-02-26" --until "2024-03-04" -p warning

Combineer gewoon --since/--until met -p — filters stapelen.

Oef 9. Alle events van de auth-facility (rsyslog).

Filteren op rsyslog-facility doe je met SYSLOG_FACILITY=. Welke nummer hoort bij auth? (zie man journalctl of een tabel: auth=4, authpriv=10).
# auth-facility heeft nummer 4 in syslog sudo journalctl SYSLOG_FACILITY=4 # authpriv (privé authenticatie) = 10 sudo journalctl SYSLOG_FACILITY=10

journalctl ondersteunt veld-filters in de vorm FIELD=value (zonder streepje). Andere voorbeelden: _PID=1234, _UID=1000, _HOSTNAME=ServerXX. De manpage van journalctl en systemd.journal-fields heeft de volledige lijst.

Exam Taak 16
Oefening 10: aparte logfile voor authpriv-info via SSH-test
▶

Oef 10. Maak /etc/rsyslog.d/10-myauth.conf aan dat alle authpriv-berichten vanaf info opslaat in /var/log/myauth. Herstart rsyslog, log dan vanaf de client in via SSH met een fout wachtwoord, en controleer dat het in myauth staat.

Eén configregel met de syntax facility.priority /pad/naar/log. Plaats hem in /etc/rsyslog.d/ — die map wordt automatisch ingelezen door de include()-regel in rsyslog.conf. Daarna systemctl restart rsyslog en test met ssh student@server1 + opzettelijk fout wachtwoord.

1. Configbestand aanmaken op de server:

sudo nano /etc/rsyslog.d/10-myauth.conf
# alle authpriv-berichten vanaf info-niveau authpriv.info /var/log/myauth

authpriv.info = facility "authpriv", prioriteit "info" en hoger. SSH-authenticatie loopt over deze facility.

2. rsyslog herladen zodat de nieuwe regel actief wordt:

sudo systemctl restart rsyslog # controleer dat het bestand nog niet bestaat (rsyslog maakt het bij eerste write) ls -l /var/log/myauth 2>/dev/null || echo "bestaat nog niet, normaal"

3. Vanaf de client een SSH met fout wachtwoord:

# op clientXX ssh student@ServerXX # tik bewust 2-3 keer een fout wachtwoord, dan Ctrl+C

4. Op de server controleren:

sudo cat /var/log/myauth
May 28 14:22:01 ServerXX sshd[3421]: Failed password for student from 10.10.10.10 port 51234 ssh2 May 28 14:22:01 ServerXX sshd[3421]: Failed password for student from 10.10.10.10 port 51234 ssh2 May 28 14:22:05 ServerXX sshd[3421]: Disconnected from authenticating user student 10.10.10.10 port 51234 [preauth]
Waarom dit een nuttige skill is In een echte omgeving wil je vaak één specifiek soort log apart hebben — bv. enkel SSH-pogingen — om makkelijker te monitoren of door te sturen naar een SIEM. Met één rsyslog-regel in een drop-in bestand voeg je die filter toe zonder de hoofdconfig te raken. Dit is exact hetzelfde patroon als /etc/firewalld/zones/ of /etc/systemd/system/: nooit de hoofdconfig bewerken, altijd een eigen bestand in de .d-map droppen.
ℹ Dezelfde events staan ook in /var/log/secure (door de standaardregel authpriv.* /var/log/secure). Je nieuwe regel dupliceert ze — rsyslog past élke matchende regel toe, niet enkel de eerste. Dat is anders dan bij http_access in Squid of bij nftables-chains.
