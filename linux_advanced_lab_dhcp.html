PXL Linux Advanced · DHCP Lab

Dynamic Host Configuration Protocol

Hands-on labo: Kea DHCP server installeren en configureren, IP-adressen automatisch uitdelen aan de client, reservaties instellen op basis van MAC-adres, en geavanceerde opties verkennen. Vertrek vanuit de PAT-situatie van het vorige hoofdstuk.

📋 Scenario

Je server fungeert al als router voor het interne netwerk (10.10.10.0/24) dankzij de PAT-configuratie uit het vorige hoofdstuk. Nu installeer je Kea DHCP op de server zodat de client zijn IP-adres automatisch ontvangt in plaats van het statisch te moeten instellen. De server deelt adressen uit in het bereik 10.10.10.150–200, geeft de juiste gateway en DNS mee, en onthoudt via een reservatie dat de client altijd hetzelfde adres krijgt.

📡 Het DHCP DORA-proces

D Discover Client roept: "Is er een DHCP-server?" (broadcast)
O Offer Server biedt een IP aan: "Gebruik dit?"
R Request Client accepteert: "Ja, ik neem dat IP"
A Acknowledge Server bevestigt: "Jij hebt het, lease loopt X uur"

Deel 1 — Installatie & Voorbereiding
Install Taak 01
Installeer Kea DHCP op de server
▶

Op de server: je gebruikt Kea, de moderne opvolger van ISC DHCP die de cursus aanbeveelt. Eén commando volstaat.

sudo dnf install -y kea
💡 Waarom Kea en niet dhcpd? De klassieke ISC DHCP server (dhcpd) is end-of-life. Kea is de actief onderhouden opvolger van dezelfde organisatie. De configuratie is in JSON-formaat (in plaats van een eigen syntax), wat makkelijker te valideren is en beter integreert met moderne automatiseringstools.
✔ Verificatie rpm -q kea toont het geïnstalleerde pakket met versienummer. De service bestaat nu maar draait nog niet: systemctl status kea-dhcp4 toont inactive (dead) — dat is normaal.
Install Taak 02
Controleer de netwerktopologie (vereiste beginsituatie)
▶

Voordat je DHCP configureert moet je zeker zijn dat het netwerk correct staat. De server moet een statisch IP hebben op ens224 (het interne netwerk), want de DHCP-server luistert op die interface. Als de server zelf via DHCP een IP zou krijgen op die interface, zou het adres kunnen veranderen — chaos.

# Controleer of ens224 een statisch IP heeft (10.10.10.1/24) ip addr show ens224 # Controleer of de connection 'Internal' actief is nmcli connection show --active
💡 Gouden regel Een DHCP-server heeft altijd een statisch IP-adres. Logisch: als hij zijn eigen adres via DHCP zou krijgen, heeft hij bij het opstarten nog geen netwerk — en dan kan hij ook geen DHCP aanbieden. Kip-en-ei probleem.
✔ Verificatie ens224 heeft het adres 10.10.10.1/24. Is dit niet zo? Herhaal dan taak 14 van het Netwerkbeheer-labo (de Internal-connection configureren).
Deel 2 — Kea DHCP Configureren
Config Taak 03
Maak een backup en schrijf de basisconfig (Oefening 1)
▶

Het configuratiebestand van Kea is /etc/kea/kea-dhcp4.conf en is in JSON-formaat. Maak eerst een backup van het origineel, dan schrijf je de nieuwe config.

# Stap 1: Backup sudo mv /etc/kea/kea-dhcp4.conf /etc/kea/kea-dhcp4.conf.orig # Stap 2: Schrijf de configuratie sudo nano /etc/kea/kea-dhcp4.conf

Voeg de volgende configuratie toe. Lees elke sectie — de uitleg staat hieronder.

{ "Dhcp4": { /* Op welke interface luistert Kea? */ "interfaces-config": { "interfaces": [ "ens224" ] }, /* Hoe lang mag een lease leven? */ "renew-timer": 900, "rebind-timer": 1800, "valid-lifetime": 3600, /* DNS en domeinnaam voor ALLE clients */ "option-data": [ { "name": "domain-name-servers", "data": "8.8.8.8, 8.8.4.4" }, { "name": "domain-name", "data": "example.local" } ], /* Het subnet en de IP-pool */ "subnet4": [ { "id": 1, "subnet": "10.10.10.0/24", "pools": [ { "pool": "10.10.10.150 - 10.10.10.200" } ], "option-data": [ { "name": "routers", "data": "10.10.10.1" } ] } ], /* Waar worden logs geschreven? */ "loggers": [ { "name": "kea-dhcp4", "output-options": [ { "output": "/var/log/kea/kea-dhcp4.log" } ], "severity": "INFO" } ] } }
💡 De drie tijdwaarden begrijpen Denk aan een lease als een huurcontract met verlenging.

valid-lifetime: 3600s (1 uur) — het contract loopt na 1 uur af.
renew-timer: 900s (15 min) — na 15 min probeert de client te verlengen bij dezelfde server (T1).
rebind-timer: 1800s (30 min) — lukt dat niet, vraagt hij na 30 min bij elke DHCP-server (T2).

Loopt alles af zonder verlenging → client verliest zijn IP.
✔ Verificatie — syntax checken vóór je start sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf
Geen output = geen fouten. Bij JSON-fouten zie je een duidelijke foutmelding met regelnummer.
Config Taak 04
Stel bestandsrechten in en maak de logdirectory aan
▶

Kea draait als een beperkte gebruiker (kea). Het configuratiebestand mag niet door iedereen leesbaar zijn (bevat gevoelige netwerkinfo), en de logdirectory moet bestaan.

# Eigenaar instellen: root schrijft, kea mag lezen sudo chown root:kea /etc/kea/kea-dhcp4.conf sudo chmod 640 /etc/kea/kea-dhcp4.conf # Logdirectory aanmaken als die niet bestaat sudo mkdir -p /var/log/kea sudo chown kea:kea /var/log/kea
💡 chmod 640 — wat betekent dat? 6 = rw voor root (eigenaar), 4 = r voor kea (groep), 0 = niets voor de rest. De service kan de config lezen maar niet aanpassen, en anderen kunnen er helemaal niet bij. Dit is een principe van least privilege: geef een proces alleen de rechten die het echt nodig heeft.
✔ Verificatie ls -la /etc/kea/kea-dhcp4.conf moet tonen: -rw-r----- 1 root kea
Deel 3 — Service Starten & Firewall
Service Taak 05
Start Kea en open de firewall voor DHCP
▶

De 5-stappen aanpak: start de service, enable hem voor autostart, en open de firewall. DHCP gebruikt UDP-poort 67 (server) en 68 (client).

# Start de service sudo systemctl start kea-dhcp4 # Enable voor autostart bij reboot sudo systemctl enable kea-dhcp4 # Controleer of hij draait sudo systemctl status kea-dhcp4 # Open de firewall op de interne zone (ens224 zit in 'internal') sudo firewall-cmd --zone=internal --add-service=dhcp --permanent sudo firewall-cmd --reload
💡 Waarom de firewall op 'internal' en niet 'external'? De DHCP-server luistert op ens224, die we in het vorige hoofdstuk aan de internal zone hebben gekoppeld. Externe clients (via ens160) mogen geen DHCP-aanvragen doen — die interface is voor internet. Zones zijn precies bedoeld voor dit soort scheiding.
✔ Verificatie sudo systemctl status kea-dhcp4 → active (running)
sudo ss -ulnp | grep :67 → Kea luistert op poort 67
sudo firewall-cmd --zone=internal --list-services → bevat dhcp
Deel 4 — Testen op de Client
Test Taak 06
Schakel de client van statisch naar DHCP (Oefening 2)
▶

Op de client: verwijder het statische IP-adres en schakel de connection om naar automatisch (DHCP). De client zal dan een IP aanvragen bij de server.

# Pas de connection aan: wis statisch adres, zet op auto sudo nmcli connection modify Connection \ ipv4.method auto \ ipv4.addresses "" \ ipv4.gateway "" # Herstart de interface om het nieuwe adres op te halen sudo nmcli connection down Connection sudo nmcli connection up Connection # Controleer het ontvangen IP-adres ip addr show ens160
💡 Wat gebeurt er op de achtergrond? Door ipv4.method auto in te stellen laat je NetworkManager weten dat hij via DHCP een adres moet aanvragen. De lege strings voor addresses en gateway verwijderen de eerder statisch ingestelde waarden. Zonder die lege strings houd je een hybride configuratie die verwarring geeft.
✔ Verificatie ip addr show ens160 toont een adres in het bereik 10.10.10.150–200.
ip route show default toont via 10.10.10.1 als gateway.
ping -c 4 www.google.be — internet werkt nog steeds via de server!
Test Taak 07
Bekijk de lease-database op de server (Oefening 4)
▶

Terug op de server: Kea slaat alle uitgedeelde IP-adressen op in een CSV-bestand. Zo kun je altijd zien welke client welk adres heeft gekregen.

# Bekijk alle leases (actieve én verlopen) sudo cat /var/lib/kea/kea-leases4.csv # Alleen actieve leases (kolom 4 = "1" betekent actief) awk -F, '$4=="1" {print $0}' /var/lib/kea/kea-leases4.csv # Logs bekijken (hier zie je het DORA-proces terug) sudo journalctl -u kea-dhcp4 -n 30
💡 Wat staat er in die CSV? De kolommen zijn: IP-adres, MAC-adres, hostname, actief (1/0), vervaltijd, subnet-ID, ... Het MAC-adres is de sleutel: zo weet de server aan wie hij welk adres heeft gegeven. In de logs zie je het DORA-proces expliciet: DHCPDISCOVER, DHCPOFFER, DHCPREQUEST, DHCPACK.
✔ Verificatie Je ziet minstens één regel met het IP dat de client heeft ontvangen, het MAC-adres van de client, en kolom 4 = 1 (actief). Herken je het MAC-adres? Vergelijk met ip link show ens160 op de client.
Deel 5 — Vaste IP via MAC-reservatie
Config Taak 08
Reserveer een vast IP voor de client op basis van MAC (Oefening 3)
▶

Een DHCP-reservatie koppelt een MAC-adres aan een vast IP — de client krijgt altijd hetzelfde adres, terwijl je toch DHCP blijft gebruiken. Geen handmatige statische config nodig op de client.

Stap 1 — Zoek het MAC-adres van de client:

# Op de CLIENT: ip link show ens160 # Let op de regel "link/ether xx:xx:xx:xx:xx:xx"

Stap 2 — Voeg de reservatie toe in de config op de SERVER:

sudo nano /etc/kea/kea-dhcp4.conf

Voeg een reservations-blok toe binnen het subnet4-object, naast de bestaande pools:

"subnet4": [ { "id": 1, "subnet": "10.10.10.0/24", "pools": [ { "pool": "10.10.10.150 - 10.10.10.200" } ], "option-data": [ { "name": "routers", "data": "10.10.10.1" } ], /* Nieuw: reservatie voor de client */ "reservations": [ { "hw-address": "xx:xx:xx:xx:xx:xx", ← vervang dit! "ip-address": "10.10.10.50" } ] } ]
# Syntax controleren sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf # Herstart om de wijziging actief te maken sudo systemctl restart kea-dhcp4
💡 Waarom buiten de pool? Het gereserveerde IP (10.10.10.50) ligt buiten de pool (150–200). Dat is niet verplicht, maar wel slim: zo kan Kea het adres niet per ongeluk aan een andere client geven vóór de gereserveerde client er om vraagt. Houd statische adressen (servers, printers, ...) altijd buiten de DHCP-pool.
✔ Verificatie Op de client: herstart de interface (nmcli con down Connection && nmcli con up Connection). Het IP moet nu 10.10.10.50 zijn in plaats van een willekeurig adres uit 150–200.
Client krijgt nog steeds een oud adres? De client heeft mogelijk nog een actieve lease. Forceer een nieuwe: sudo nmcli connection down Connection && sudo nmcli connection up Connection. Wacht een paar seconden tussen de twee commando's. Als het adres nog niet verandert, check of het MAC-adres in de config exact overeenkomt (hoofdlettergevoelig, formaat xx:xx:xx:xx:xx:xx).
Deel 6 — Geavanceerde Instellingen
Geavanceerd Taak 09
Pas de lease-tijd aan naar een half uur (Oefening 5)
▶

In een labo- of testomgeving wil je kortere leases zodat adressen sneller vrijkomen. Pas de drie tijdwaarden aan naar 30 minuten (1800 seconden) als maximum.

De drie waarden die je moet aanpassen zijn valid-lifetime, renew-timer en rebind-timer. De verhoudingen T1 = 50% en T2 = 87.5% van de valid-lifetime zijn een standaard aanbeveling. Voor 1800s valid-lifetime: T1 ≈ 900s, T2 ≈ 1575s. Daarna: syntax testen en herstarten.

Pas de waarden aan in de config:

sudo nano /etc/kea/kea-dhcp4.conf
"renew-timer": 900, "rebind-timer": 1575, "valid-lifetime": 1800,
# Testen en herstarten sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf sudo systemctl restart kea-dhcp4
✔ Verificatie Vraag op de client een nieuwe lease aan (nmcli con down/up) en bekijk de lease in de CSV: sudo cat /var/lib/kea/kea-leases4.csv. De vervaltijd (Unix timestamp) zou nu ~1800 seconden in de toekomst moeten liggen.
Debug Taak 10
Troubleshoot een niet-werkende DHCP-setup
▶

Een collega heeft deze config gemaakt maar de client krijgt geen IP. Analyseer de problemen en stel een troubleshooting-checklist op voordat je kijkt naar de analyse.

/* Problematische config: */ { "Dhcp4": { "interfaces-config": { "interfaces": [ "ens160" ] ← ! }, "valid-lifetime": 3600, "subnet4": [ { "id": 1, "subnet": "192.168.10.0/24", ← ! "pools": [ { "pool": "10.10.10.150 - 10.10.10.200" } ← ! ], "option-data": [ { "name": "routers", "data": "10.10.10.1" } ] } ] } }

Gebruik deze commando's om systematisch te debuggen:

# Stap 1: draait de service? sudo systemctl status kea-dhcp4 # Stap 2: is de config syntactisch geldig? sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf # Stap 3: luistert Kea op de juiste poort en interface? sudo ss -ulnp | grep :67 # Stap 4: staat de firewall open? sudo firewall-cmd --zone=internal --list-services | grep dhcp # Stap 5: wat zeggen de logs? sudo journalctl -u kea-dhcp4 -n 50
Kijk goed naar drie dingen: 1) Op welke interface luistert de server? Is dat de interne interface waar de client op zit? 2) Klopt het subnet (192.168.10.0/24) met de interface die luistert? Kea weigert aanvragen als het subnet niet overeenkomt met het IP van de luisterende interface. 3) Klopt de pool (10.10.10.x) met het opgegeven subnet (192.168.10.x)?

Drie problemen in deze config:

1. Verkeerde interface: ens160 is de externe interface (naar internet). De client zit op het interne netwerk via ens224. DHCP-aanvragen van de client bereiken ens224 nooit als Kea alleen op ens160 luistert.

2. Subnet klopt niet: 192.168.10.0/24 bestaat niet op de server. Kea vergelijkt het subnet met het IP-adres van de luisterende interface (ens224 heeft 10.10.10.1). Geen match → Kea logt "no suitable subnet" en geeft niets uit.

3. Pool buiten het subnet: De pool (10.10.10.150–200) ligt niet in het opgegeven subnet (192.168.10.0/24). Dat is een configuratiefout die Kea weigert te starten.

# Gecorrigeerde versie: # interfaces: [ "ens224" ] # subnet: "10.10.10.0/24" # pool: "10.10.10.150 - 10.10.10.200"
