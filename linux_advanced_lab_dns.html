PXL Linux Advanced · DNS Lab

Domain Name System (BIND)

Hands-on labo: BIND installeren en configureren als authoritatieve DNS-server voor het domein pxl.lan, een forward- en reverse zone opzetten, SELinux correct instellen, de setup testen met dig, en DNS via DHCP uitrollen naar de client.

📋 Scenario

Je netwerk draait al met DHCP (Kea) en PAT. Nu voeg je een eigen DNS-server toe. Clients in 10.10.10.0/24 moeten namen als www.pxl.lan of ns1.pxl.lan kunnen opzoeken, en ook de omgekeerde richting moet werken (IP → naam). Externe namen (google.com) worden doorgestuurd naar Google DNS via forwarding. Tot slot update je de DHCP-config zodat clients automatisch jouw DNS-server krijgen.

🌐 De DNS-hierarchie — hoe een naam wordt opgelost

Root (".")
13 root-serverclusters wereldwijd. Weten wie verantwoordelijk is voor elke TLD.
dig . NS
TLD — .lan / .be / .com
Top Level Domain servers weten welke nameservers verantwoordelijk zijn voor een domein.
nslookup -type=NS pxl.be z.nsset.be
Authoritatieve server — jouw BIND
Jouw server is de autoriteit voor pxl.lan. Hij geeft definitieve antwoorden voor jouw zone.
dig @10.10.10.1 www.pxl.lan
Client (resolver)
Vraagt een naam op. Krijgt antwoord uit de cache of via de volledige resolutieketen.
ping www.pxl.lan
A
Naam → IPv4-adres.
www → 10.10.10.30
PTR
IP → naam (reverse DNS).
30 → www.pxl.lan.
SOA
Start of Authority. Metadata van de zone: primaire NS, serial, timers.
NS
Welke server is authoritative voor deze zone.
CNAME
Alias. ftp → www (verwijst naar A-record).
MX
Mail Exchange. Welke server ontvangt e-mail voor het domein.
TXT
Vrije tekst. Gebruikt voor SPF, DMARC, verificatie.

Deel 1 — Installatie & Basisconfig
Install Taak 01
Installeer BIND en start de service
▶

Op de server: installeer bind. De daemon heet named (name daemon) — dat is de naam die je bij alle systemctl-commando's gebruikt.

sudo dnf install bind # Start en enable direct sudo systemctl enable named sudo systemctl start named sudo systemctl status named
💡 BIND vs named — twee namen, één ding BIND is de softwarenaam (Berkeley Internet Name Domain). De achterliggende daemon die er op Linux voor draait heet named. Dat is de naam die je bij systemctl en alle config-bestanden ziet. Historisch staat de "d" voor "daemon" — een achtergrondproces.
✔ Verificatie systemctl status named → active (running). De service draait nu als caching-only resolver (luistert alleen op localhost). Dat gaan we de volgende stap openbreken.
Config Taak 02
Pas named.conf aan: luisteren op het interne IP + forwarding
▶

Maak een backup van de originele config, open daarna /etc/named.conf en pas het options { }-blok aan. Je hoeft niet de hele file te herschrijven — alleen de gemarkeerde regels aanpassen of toevoegen.

sudo cp /etc/named.conf /etc/named.conf.orig sudo nano /etc/named.conf

Zoek het bestaande options { ... };-blok en pas de volgende regels aan (ze staan er al, maar met andere waarden):

options { directory "/var/named"; ... listen-on port 53 { 127.0.0.1; 10.10.10.1; }; // ← aanpassen allow-query { localhost; 10.10.10.0/24; }; // ← aanpassen allow-recursion { localhost; 10.10.10.0/24; }; // ← toevoegen forwarders { 8.8.8.8; 8.8.4.4; }; // ← toevoegen ... };
💡 Wat doen deze vier opties? listen-on: op welke IP's luistert BIND naar DNS-queries? We voegen 10.10.10.1 toe zodat interne clients ons kunnen bereiken. allow-query: wie mag vragen stellen? Alleen ons interne subnet. allow-recursion: wie mag de server vragen om externe namen op te zoeken (Google, GitHub...)? Ook alleen intern — anders word je een open resolver die door aanvallers misbruikt kan worden. forwarders: als BIND een naam niet zelf kent, stuurt hij de query door naar Google DNS in plaats van zelf door de hele boom te klimmen.
# Syntax controleren (geen output = geen fouten) sudo named-checkconf # Herstart om wijzigingen te activeren sudo systemctl restart named
✔ Verificatie sudo ss -tulnp | grep :53 → named luistert nu op 127.0.0.1:53 én 10.10.10.1:53. Vroeger was het alleen localhost.
Service Taak 03
Open de firewall voor DNS (poort 53)
▶

DNS gebruikt zowel UDP (voor gewone queries) als TCP (voor zone transfers en grote antwoorden). De firewalld DNS-service opent beide automatisch.

# DNS toevoegen aan de interne zone (ens224) sudo firewall-cmd --permanent --zone=internal --add-service=dns sudo firewall-cmd --reload # Controleer sudo firewall-cmd --zone=internal --list-services
💡 UDP vs TCP voor DNS De meeste DNS-antwoorden passen in één UDP-pakket (max 512 byte), dus UDP is de standaard — snel en zonder handshake. Antwoorden die te groot zijn (DNSSEC, zone transfers) vallen automatisch terug op TCP. Beide moeten open staan in de firewall, en firewall-cmd --add-service=dns doet dat in één keer.
✔ Verificatie sudo firewall-cmd --zone=internal --list-services bevat dns.
Deel 2 — Forward Zone (naam → IP)
Zone Taak 04
Definieer de zone pxl.lan in named.conf
▶

Voeg onderaan /etc/named.conf de zone-definitie toe. Hiermee zeg je tegen BIND: "voor het domein pxl.lan ben ik de master, en de records staan in dit bestand."

sudo nano /etc/named.conf

Voeg toe aan het einde van het bestand:

zone "pxl.lan" { type master; file "/etc/named/pxl.lan.db"; allow-query { any; }; allow-transfer { none; }; };
💡 type master vs slave type master betekent dat dit de primaire bron is van de zone-data. Een slave (of secondary) kopieert de zone via een zone transfer van de master. In productie heb je altijd minstens twee nameservers voor redundantie — hier werken we met één master. allow-transfer none verbiedt zone transfers naar anderen (veilig voor een labo-setup).
Zone Taak 05
Maak het zone-bestand aan met alle records
▶

Maak het zone-bestand aan op /etc/named/pxl.lan.db en voeg de records toe. Lees elk onderdeel — er staat veel meer informatie in dan het lijkt.

sudo nano /etc/named/pxl.lan.db
$TTL 8h ; SOA: wie is de autoriteit voor deze zone? @ IN SOA ns1.pxl.lan. administrator.pxl.lan. ( 2025052601 ; Serial: YYYYMMDDNN — verhoog bij elke wijziging! 1d ; Refresh: secundaire server checkt updates 3h ; Retry: als refresh faalt, probeer opnieuw na 3d ; Expire: secondary stopt na 3d zonder contact 3h ) ; Minimum TTL: hoe lang negatieve antwoorden cachen ; Nameservers en mailservers IN NS ns1.pxl.lan. IN MX 10 mail.pxl.lan. ; A-records: naam → IP ns1 IN A 10.10.10.1 www IN A 10.10.10.30 mail IN A 10.10.10.40 webserver IN A 10.10.10.1 ; TXT-record (optioneel) pxl.lan. IN TXT "DNS lab - pxl.lan zone actief"
⚠ Vergeet de trailing dot niet! Elke volledig gekwalificeerde domeinnaam (FQDN) in een zone-bestand eindigt op een punt: ns1.pxl.lan. Schrijf je ns1.pxl.lan zonder punt, dan voegt BIND de zone-naam toe en krijg je ns1.pxl.lan.pxl.lan — een veelgemaakte fout die moeilijk te zien is.
# Rechten instellen (root bezit, named mag lezen) sudo chown root:named /etc/named/pxl.lan.db sudo chmod 640 /etc/named/pxl.lan.db # Syntax controleren sudo named-checkzone pxl.lan /etc/named/pxl.lan.db
💡 Het serial-nummer — waarom is het zo belangrijk? Het serial-nummer in de SOA is de versie van je zone. Secundaire DNS-servers vergelijken hun serial met die van de master. Is de master hoger? Dan halen ze een nieuwe kopie op (zone transfer). Is je serial niet verhoogd na een wijziging, dan denken secondaries dat er niets veranderd is en zien de wijziging nooit. Het YYYYMMDDNN-formaat is een conventie: datum + volgnummer van die dag.
✔ Verificatie named-checkzone eindigt met OK. Elke andere uitvoer bevat de regelnummer van de fout.
Zone Taak 06
SELinux-context corrigeren en BIND herstarten
▶

SELinux bewaakt welke processen welke bestanden mogen lezen. BIND mag alleen bestanden lezen met het label named_zone_t. Bestanden die je zelf aanmaakt kunnen een verkeerd label hebben — restorecon herstelt dit.

# Herstel SELinux-context op /etc/named/ sudo restorecon -Rv /etc/named/ # Controleer het label (moet named_zone_t zijn) ls -Z /etc/named/pxl.lan.db # Herstart BIND sudo systemctl restart named sudo systemctl status named
💡 Waarom is SELinux zo vaak de schuldige? SELinux kent bestanden een beveiligingslabel toe op het moment van aanmaken, gebaseerd op de map. Als je een bestand aanmaakt in /tmp en het daarna verplaatst naar /etc/named/, houdt het het label van /tmp. BIND krijgt dan een "permission denied" zelfs al zijn de gewone bestandsrechten in orde. restorecon kijkt in de SELinux-policy op welk label een bestand zou moeten hebben op die locatie, en corrigeert het.
✔ Verificatie sudo journalctl -u named -n 20 — geen fouten over permissions of zones. named is active (running).
Deel 3 — Reverse Zone (IP → naam)
Zone Taak 07
Definieer de reverse zone en maak het PTR-bestand aan
▶

Reverse DNS werkt via een speciale zone genaamd in-addr.arpa. De naam ziet er raar uit: de octetten van het netwerk staan omgekeerd. Voor 10.10.10.0/24 is de zone-naam 10.10.10.in-addr.arpa.

Stap 1 — Zone-definitie in named.conf:

sudo nano /etc/named.conf
zone "10.10.10.in-addr.arpa" { type master; file "/var/named/10.10.10.in-addr.arpa.zone"; allow-query { any; }; allow-transfer { none; }; };

Stap 2 — Maak het zone-bestand aan:

sudo nano /var/named/10.10.10.in-addr.arpa.zone
$TTL 8h @ IN SOA ns1.pxl.lan. administrator.pxl.lan. ( 2025052601 ; Serial 1d ; Refresh 3h ; Retry 3d ; Expire 3h ) ; Minimum TTL IN NS ns1.pxl.lan. ; PTR-records: alleen het LAATSTE octet 1 IN PTR ns1.pxl.lan. 30 IN PTR www.pxl.lan.
💡 Waarom zijn de octetten omgekeerd? In een normale A-record-zone gaan namen van algemeen naar specifiek: www.pxl.lan (links = specifiek, rechts = algemeen). In de DNS-hierarchie werkt het omgekeerd. Om IP-adressen in hetzelfde systeem te passen, worden de octetten gespiegeld: 10.10.10.1 wordt 1.10.10.10.in-addr.arpa. In je zone-bestand gebruik je alleen het laatste octet (1) omdat de rest al in de zone-naam zit.
# Rechten instellen sudo chown root:named /var/named/10.10.10.in-addr.arpa.zone sudo chmod 640 /var/named/10.10.10.in-addr.arpa.zone # Syntax check voor de reverse zone sudo named-checkzone 10.10.10.in-addr.arpa /var/named/10.10.10.in-addr.arpa.zone # Full check: beide zones + named.conf sudo named-checkconf sudo systemctl restart named
✔ Verificatie Beide named-checkzone-aanroepen eindigen met OK. named herstart zonder fouten.
Deel 4 — Testen met dig
Test Taak 08
Test forward lookup, reverse lookup en externe forwarding
▶

Gebruik dig om je DNS-server grondig te testen. Het @10.10.10.1-argument dwingt dig om specifiek jouw server te bevragen — anders gebruikt het de system-resolver.

## Test 1: Forward lookup (naam → IP) dig @10.10.10.1 www.pxl.lan ## Snellere output (alleen het antwoord) dig @10.10.10.1 www.pxl.lan +short ## Test 2: Reverse lookup (IP → naam) dig @10.10.10.1 -x 10.10.10.30 dig @10.10.10.1 -x 10.10.10.1 +short ## Test 3: Forwarding (externe naam via Google DNS) dig @10.10.10.1 www.google.com +short ## Test 4: SOA en NS records dig @10.10.10.1 pxl.lan SOA dig @10.10.10.1 pxl.lan NS ## Test 5: MX record dig @10.10.10.1 pxl.lan MX
💡 dig lezen — de ANSWER SECTION De uitvoer van dig heeft secties: QUESTION (wat werd gevraagd), ANSWER (het antwoord), AUTHORITY (welke server is authoritative), ADDITIONAL (extra info). Kijk naar status: NOERROR voor succes. NXDOMAIN = naam bestaat niet. SERVFAIL = server had een intern probleem (vaak zone-bestandsfout of SELinux). REFUSED = query niet toegestaan (allow-query of allow-recursion).
✔ Verwachte resultaten Test 1: 10.10.10.30 · Test 2: www.pxl.lan. · Test 3: een geldig Google IP-adres · Test 4: SOA met serial 2025052601 · Test 5: 10 mail.pxl.lan.
Test Taak 09
Update DHCP zodat clients jouw DNS krijgen (Oefening 4)
▶

Clients krijgen hun DNS-server via DHCP. Pas de Kea-config aan zodat ze niet langer 8.8.8.8 krijgen maar jouw eigen server.

sudo nano /etc/kea/kea-dhcp4.conf

Zoek de domain-name-servers optie en pas het adres aan:

# Van: { "name": "domain-name-servers", "data": "8.8.8.8, 8.8.4.4" } # Naar: { "name": "domain-name-servers", "data": "10.10.10.1" } # Optioneel: ook de domeinnaam meegeven { "name": "domain-name", "data": "pxl.lan" }
# Syntax check en herstart sudo kea-dhcp4 -t /etc/kea/kea-dhcp4.conf sudo systemctl restart kea-dhcp4
💡 Wat doet de domain-name optie? Als je domain-name: pxl.lan meegeeft, voegt de client dit als zoekdomein toe aan /etc/resolv.conf. Dat betekent dat ping www automatisch wordt omgezet naar ping www.pxl.lan. Handig in een labo, maar pas op in productie — onbedoelde DNS-queries kunnen verwarrend zijn.
✔ Test op de client Op de client: herstart de interface (nmcli con down/up Connection). Daarna: cat /etc/resolv.conf moet nameserver 10.10.10.1 tonen. Dan: dig www.pxl.lan (zonder @) → antwoord via jouw server.
Deel 5 — Extra Records & Aanpassingen
Zone Taak 10
Voeg hostnames toe voor server en client (Oefening 3)
▶

Voeg A-records toe voor je eigen server- en clientnamen. De conventie in de cursus is server[JouwInitialen] en client[JouwInitialen]. Vervang hieronder XX door jouw initialen.

Drie stappen: 1) Open het zone-bestand (/etc/named/pxl.lan.db), voeg twee A-records toe, verhoog het serial-nummer. 2) Voeg PTR-records toe in het reverse zone-bestand als je ook de reverse lookup wil. 3) Valideer met named-checkzone en reload met sudo rndc reload (je hoeft niet volledig te herstarten — rndc herlaadt alleen de zones).

In /etc/named/pxl.lan.db:

; Verhoog serial: 2025052601 → 2025052602 serverXX IN A 10.10.10.1 clientXX IN A 10.10.10.50 ← jouw client-IP
sudo named-checkzone pxl.lan /etc/named/pxl.lan.db sudo rndc reload # Testen dig @10.10.10.1 serverXX.pxl.lan +short dig @10.10.10.1 clientXX.pxl.lan +short
✔ Verificatie dig serverXX.pxl.lan +short geeft 10.10.10.1. Vergeet de zone ook te herladen op de client (nmcli con down/up) als je getest hebt met de zoek-domeinnaam.
Zone Taak 11
Voeg een CNAME-alias toe (Oefening 7)
▶

Een CNAME-record maakt een alias: ftp.pxl.lan kan verwijzen naar www.pxl.lan zonder een apart IP-adres. Zo kun je meerdere namen voor dezelfde server hebben zonder A-records te dupliceren.

CNAME-syntax: alias IN CNAME echtenaam. De "echtenaam" mag een naam binnen de zone zijn (zonder trailing dot) of een FQDN (met trailing dot). Let op: je kunt geen CNAME maken voor de zone-top (@), en een CNAME mag niet tegelijk met andere records voor dezelfde naam bestaan. Verhoog ook hier het serial.

In /etc/named/pxl.lan.db:

ftp IN CNAME www blog IN CNAME www
sudo named-checkzone pxl.lan /etc/named/pxl.lan.db sudo rndc reload dig @10.10.10.1 ftp.pxl.lan +short

Output van dig voor een CNAME toont twee regels: eerst de CNAME-referentie, dan het uiteindelijke A-record.

Deel 6 — Troubleshooting Scenario
Debug Taak 12
Analyseer een kapotte DNS-setup systematisch
▶

Een collega heeft deze config geschreven. dig @10.10.10.1 www.pxl.lan geeft SERVFAIL. Gebruik de systematische troubleshooting-volgorde om de fouten te vinden.

; Probleemzone — vind de fouten $TTL 8h @ IN SOA ns1.pxl.lan administrator.pxl.lan. ( ← (1) 2025052601 1d 3h 3d 3h ) IN NS ns1.pxl.lan. IN MX 10 mail.pxl.lan www IN A 10.10.10.30 ns1 IN A 10.10.10.1 10 IN PTR www.pxl.lan. ← (2)

Gebruik deze commando's om te debuggen:

# Stap 1: werkt named überhaupt? sudo systemctl status named # Stap 2: zone-file syntax sudo named-checkzone pxl.lan /etc/named/pxl.lan.db # → toont regelnummer van fouten # Stap 3: named.conf syntax sudo named-checkconf # Stap 4: logs sudo journalctl -u named -n 30 # Zoek naar: REFUSED, permission denied, zone not loaded # Stap 5: firewall sudo firewall-cmd --zone=internal --list-services | grep dns # Stap 6: SELinux sudo ausearch -m avc -ts recent | grep named
Kijk naar twee klassieke zone-bestandsfouten: 1) De SOA-regel heeft geen punt aan het einde van ns1.pxl.lan — wat doet BIND dan met die naam? 2) Een PTR-record staat in de forward zone-file — daar hoort het niet. PTR-records horen in de reverse zone (in-addr.arpa), en dan ook alleen met het laatste octet, niet het volledige IP. 3) De MX-record einidgt zonder trailing dot — wat gaat er mis?

Drie fouten in deze zone-file:

1. SOA — ontbrekende trailing dot: ns1.pxl.lan zonder punt wordt ns1.pxl.lan.pxl.lan. BIND accepteert dit soms maar de zone is incorrect. Fix: ns1.pxl.lan.

2. PTR-record in de forward zone: 10 IN PTR www.pxl.lan. staat in het forward zone-bestand. PTR-records horen in de reverse zone (in-addr.arpa). Hier zorgt het voor een parseerfout of onverwacht gedrag. Fix: verwijder uit de forward zone, voeg toe aan de reverse zone.

3. MX-record — ontbrekende trailing dot: mail.pxl.lan zonder punt → mail.pxl.lan.pxl.lan. Fix: mail.pxl.lan.

# Na de fixes altijd: sudo named-checkzone pxl.lan /etc/named/pxl.lan.db sudo rndc reload dig @10.10.10.1 pxl.lan MX
